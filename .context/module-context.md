# harness
*Harness* is the framework every other part of CDD is built on: it holds the annotations an author types, the channels they publish to, and the one way a name is written in every case (harness/annotations), starts and stops long-running processes (harness/process), keeps a class's words in markdown beside it (harness/markdown), turns an ordinary class into operations an agent can use (harness/agent_tools), gives each channel its writer and finds a repository's toolsets (harness/installation), publishes to every chat through the one `cdd` MCP server (harness/mcp) and the hook server (harness/hooks), installs all of it into each IDE (harness/installation), makes a practice one class plus its markdown (harness/guidance), gives every guidance action the same start (harness/guidance_actions), and reads a working copy into graphs that rules check (harness/graph). The modules are listed lowest first: each depends only on modules before it. Above them, harness/diagnostics probes an install and harness/chat lets the board reach a live Claude Code chat and send it a command.
On top of the framework sit its applications: the chat's board plugin and server health band (harness/chat-ui/pane; the report it shows comes from harness/diagnostics), the generated catalog (harness/catalog_generator), and Claude Design canvases (harness/design_canvas). Each of these folders owns its own card in `{folder}/.context/module-context.md`.

- **Purpose:** Give practices, actions, and tools one framework for publishing classes to agents and IDEs, and the applications that show the work.
- **Seam (terms):** the annotations `@agent_toolset`, `@agent_tool`, `@agent_instructions`, `@markdown`, `@mcp`, `@skill`, `@command`, `@rules`, `@hook`; *PracticeGuidance*; *GuidanceAction*; *Graph*; `python scripts/install.py --ide {IDE}`
- **Dependencies (one-way):** inside harness the modules depend one way, lowest first as listed above. harness, space, and tools are the lower layer together and may import each other, so something they share, such as the file viewer in space, is written once and used by the framework's own apps. Nothing in them imports cdd_guidance, which is built on them: where the framework needs what it keeps, it declares a seam and they register with it — space/session registers how a *ToolCall* opens its session, tools/prompt_notify registers the notifier that shows a hook's toast, each practice's *PracticeGuidance* says what the knowledge graph reads from it, and `cdd_guidance/practices`, `cdd_guidance/actions`, and `cdd_guidance/patterns` register their classes with *PracticeCatalogue*, *ActionCatalogue*, and the graph's *PatternOverlays* when their packages are imported, so the framework holds no module string or folder path of theirs. The stage names every fidelity is in are framework vocabulary (`harness/guidance/stages.py`).

## Constraint

Import a child package (`harness.agent_tools`, `harness.guidance`, ...); this folder adds no seam of its own. Keep practice-specific parsing and rules in the practice that owns them, not in the framework, so the framework does not have to change for every practice. Leave `harness/` off `PYTHONPATH`, so `import mcp` loads the MCP SDK.

# cdd_guidance
*CDD guidance* is what an agent follows: the practices (`cdd_guidance/practices` — Stories, DDD, UX, Clean Engineering, BDD, and agent BDD), each a *PracticeGuidance* with its fidelities, rules, templates, and examples; the actions that run on them (`cdd_guidance/actions` — generate, validate, document, sketch, grill, partition, render, satisfy, iterate, repair, diagnose), each a *GuidanceAction*; the stack patterns that add rules for one kind of solution (`cdd_guidance/patterns` — LERN, MERN, CDD web domain access, Claude Code mods); the builders that start a new toolset or practice (`cdd_guidance/builders`); and context setup, which turns documents or a live app into indexed context (`cdd_guidance/context_setup`). `cdd_guidance/rules` and `cdd_guidance/references` are installed into every IDE, and `cdd_guidance/agents` are the role prompts. `cdd_guidance/practices`, `cdd_guidance/actions`, `cdd_guidance/patterns`, `cdd_guidance/builders`, and `cdd_guidance/context_setup` keep their own cards in `{folder}/.context/module-context.md`; `rules`, `references`, `agents`, and `catalog` hold no code and are covered by this one.

- **Purpose:** Hold the practices, actions, and patterns an agent follows to deliver work, as classes plus markdown the installer publishes.
- **Seam (terms):** each practice's and fidelity's instructions, published under its slug (`stories`, `clean-engineering-model`); each action's MCP operations (`generate.generate`, `validate.validate`, ...); each pattern's instructions
- **Dependencies (one-way):** harness (agent_tools, graph, guidance, guidance_actions, installation, markdown, mcp, design_canvas). Nothing in harness imports the practices, patterns, or actions; each practice keeps the spec support that runs its rules on examples in its own `rules/` folder. space imports some of them (the session diagnostics probe runs generate and validate, and the board reads the saved graph through validate's reader); nothing in cdd_guidance imports space: agent BDD (`cdd_guidance/practices/agent_bdd`) opens the session its agent runs in through `ToolCall.session_in`, the opener space/session registers with the framework. The dependency runs one way, space to cdd_guidance.

## Constraint

Run an action on a practice by passing the practice to the action (`generate` with `guidance: stories`), never by putting the action on the practice, so every practice gets every action the same way. Keep a practice's words in its `{practice}.md` and its format adapters under `{practice}/model/{format}/`.
