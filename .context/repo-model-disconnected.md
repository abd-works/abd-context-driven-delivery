**Repository model: disconnected classes and runtime relationships**

A review of `.context/repo-model.md` against the code. It lists every class the model showed with no relationship to another class (inheritance aside), and every runtime relationship traced from the code (`.context/repo-runtime.md`), each judged by how the code reaches the other object. Nothing here has been changed in the code; the refactor runs from this list.

How each relationship is judged:

- **R — right as a dependency.** The two objects are independent and one asks the other to act through a public operation: a collaborator it holds or is handed, a registry it registers with, an annotation an author typed, a named failure it raises, or a part it creates once for itself.
- **W — wrong shape in the code.** The caller builds the other object on each call from strings or names it pulls from elsewhere, looks it up again by name or path instead of holding it, or constructs inside its own constructor what should be handed to it. The fix makes the relationship a held part (composition) or a held collaborator (association) of the owning object, and the call becomes a read of what it holds.

The judgement is made from how the code reaches the other object (created per call, created in the constructor, looked up through a class method, held, or handed in), and each entry names the line it read. A W that names the source as the owner of a value such as `Name` or `Format` means the source should keep that value as a property made once from its own state.
