# Grill Answers

### CatalogGenerator's top-level orchestration is a @tool, not an @action

`@action` bodies are never executed — `primitives/actions/action.py`'s `_ActionExpander` AST-walks them into markdown instructions an agent must carry out step by step, because the step requires agentic judgment between calls (deciding what to write, asking a question, branching on natural-language content — e.g. `BaseContextTool.grill`/`sketch`, or `AgentSkills.deploy_tools_as_skills`'s "ask: Which IDE?" / "Present the filtered list and ask to confirm" steps). CatalogGenerator's job — scrape existing manifests/markdown/examples-config into a canonical model, render deterministically, write/embed — has zero such judgment points; every step is a fixed, deterministic pipeline. So the top-level orchestration (`generate_catalog`) is a plain `@tool` that runs for real, called directly by `generate_cdd_catalog.py`; no `@action`, no `@agentic_toolset`.

### No parallel data model at all — render classes wrap the real object model directly

The initial design (`CatalogModel` / `PracticeEntry` / `FidelityEntry` / `LifecycleActionEntry` / `UtilityEntry` as a scraped canonical schema, separate from a renderer) was rejected outright — not just the interface question about it. The real object model already has everything needed: `Toolset.tools` (`dict[str, _Tool]`), `AgenticToolset.actions` (`Mapping[str, Action]`), `Toolset.signature`/`.manifest_path`, and `BaseContextTool.fidelities`. There is no separate scrape-then-model-then-render pipeline. Instead, a small family of thin renderer classes wraps each real primitive one-for-one and exposes exactly one method, `generate_catalog(...)`, that renders that node and composes its children's `generate_catalog(...)` calls directly against the live objects: `CatalogTool` (wraps a `_Tool`), `CatalogAction` (wraps an `Action`, composing `CatalogTool` for each of its `signature_entry["tools"]`), `CatalogFidelity` (wraps a fidelity name on a `BaseContextTool` instance, composing `CatalogAction` for the shared lifecycle actions), `CatalogContextTool` (wraps a `BaseContextTool` instance, composing `CatalogFidelity` per `owner.fidelities.values()`), `CatalogUtility` (wraps a plain utility `Toolset` instance), and `Catalog` (top-level, owns output/git-URL config, composes everything into the hub board). No `I{Class}` interfaces on any of them, following `utilities/agent_skills/agent_skills.py`'s own precedent (a closer analog than `class_model`'s multi-language channel classes — there is no polymorphism here, no second implementation of the same contract).
