What the pieces are

Context tools are lenses on the work. Each one owns a perspective.

  • /stories — who does what, in what sequence.
  • /clean-engineering — module boundaries and OO design.
  • /ux — navigation, screens, front end.
  • /bdd — observable behavior and tests.
  • /ddd — bounded contexts and domain building blocks.
  • /cdd — orchestrates all child tools at one stage.

Actions are what you do with a context tool. Every tool shares the same lifecycle verbs.

  • /partition — index source material and extract chunks.
  • /document — describe existing code, tests, or docs.
  • /generate — produce the full formal artifact in one shot.
  • /grill — context-grounded Q&A.
  • /sketch — grill plus create a rough draft.
  • /iterate — generate one small slice at a time.
  • /validate — scan and report pass/fail.
  • /satisfy — validate, fix, validate again until clean.
  • /repair — root-cause and fix why the tool produced a violation.
  • /improve — log mistake, repair, capture regression.

Fidelities control how deep you go. Each context tool maps three stages to its own concrete names.

  • /discovery — wide and shallow (Stories: story_map, CE: modules, UX: ia, DDD: bounded_context).
  • /specification — narrower and deeper (Stories: scenarios, CE: model, UX: mockup, BDD: behavior, DDD: building_blocks).
  • /engineering — narrowest and deep (Stories: acceptance_tests, CE: code, UX: front_end_code, BDD: development, DDD: tactics).

Utilities are session helpers, not lenses.

  • /handoff — compact the session for a fresh agent.
  • /diagnose — stuck RED / bug-fix loop.

How to use them

Compose a command as /{context tool} /{action} /{fidelity}.

Example: /stories /sketch /discovery — sketch the Stories tool at discovery (resolves to story_map).

You can also pass the tool's concrete fidelity directly: /stories /sketch story_map.

Scenario 1 — Turn source documentation into context

Use when you have a handbook, spec, wiki, or any prose you want the system to reason from.

  • Partition the docs through your first lens.
    Pick the lens that matters most right now and run partition to index the source and extract verbatim chunks.
    /clean-engineering /partition modules — indexes by module boundaries.
    /stories /partition story_map — indexes by epics and user interactions.
    /ux /partition ia — indexes by screens and navigation.
  • Add more lenses to the same index.
    Each subsequent partition adds its own columns and chunks to the existing index. Nothing is wiped.
    Run partition again with a different tool for each perspective you need.
  • Sketch the design from those chunks.
    Once partitioned, draft a rough shape interactively before committing to formal output.
    /clean-engineering /sketch modules
    /stories /sketch story_map
    /ux /sketch ia
  • Generate the formal artifact.
    Produce the real deliverable at the chosen fidelity.
    /clean-engineering /generate modules
  • Close the gaps with satisfy.
    Validate the artifact, fix every reported violation, and validate again until it passes.
    /clean-engineering /satisfy modules
  • Deepen fidelity and repeat the loop.
    When discovery is solid, move to the next stage and sketch → generate → satisfy again — same steps, tighter scope.
    /stories /sketch scenarios → /stories /generate scenarios
    /clean-engineering /sketch model → /clean-engineering /generate model
    Or set the stage with /specification or /engineering on the tool already in scope.

Scenario 2 — Document an existing codebase or test suite

Use when the system already exists and you want to add structured context files without inventing a new design.

  • Observe and describe what is there with document.
    Document reads the code and produces a neutral description. Scanner violations are flagged but not fixed.
    /clean-engineering /document code
    /bdd /document development
  • Add context files based on what you observed.
    Create or update .context/module-context.md files using the document output as your source of truth.
  • Generate or satisfy against those context files.
    Now that context exists, generate formal artifacts or run satisfy to close gaps.
    /clean-engineering /generate modules
    /bdd /satisfy development

Scenario 3 — Design something new (greenfield)

Use when nothing exists yet and you need to shape the solution before building it.

  • Sketch the shape.
    Grill open decisions and create a rough draft. The sketch is saved to disk after each refinement — never left only in chat.
    /stories /sketch story_map
  • Generate the formal artifact.
    Produce the deliverable from the sketch and context.
    /stories /generate story_map
  • Iterate one slice at a time.
    For large artifacts, iterate generates one small validated slice per tick instead of dumping everything at once.
    /stories /iterate scenarios
  • Run all child tools at one stage with CDD.
    When you want every lens at the same depth, use the CDD orchestrator.
    /cdd /sketch discovery — sketches Stories + Clean Engineering + UX + DDD at discovery.
    /cdd /generate spec — generates all child tools at spec fidelity.

Scenario 4 — Fix and improve existing artifacts

Use when artifacts already exist but have violations or need refinement.

  • Validate without editing.
    Scan and report pass/fail per rule. Nothing is changed.
    /clean-engineering /validate modules
  • Satisfy all violations.
    Fix the artifact — validate, close every gap, validate again until it passes.
    /clean-engineering /satisfy modules
  • Repair the root cause.
    Fix why the context tool produced the violation (context, example, template, or scanner) — not the asset in isolation. Requires a scan/validate signal; drafts a surgical change and waits for approval.
    /clean-engineering /repair modules
  • Improve when the mistake should stick.
    Log the mistake, log the correction, then launch repair and capture a regression fixture so the same failure does not recur.
    /clean-engineering /improve modules
