# Generate

1. Read the **Session** section at the end of these instructions, which names the session's root and where each listed practice writes. Name every path from the project's root, or absolute.
2. **MUST — read before asking.** Before any grill/iterate question (and before inventing options or story/module names):
   - Identify **every relevant context file referenced or implied** by the decision — not one favorite type. Typical set: `{workspace}/.context/context-index.md`, owning `*-segment.md`, `module-context.md`, grill-answers, sketches, peer story-context, build-order, and any path the plan or prior answers cite. Do not treat a consumed handoff (or `handoffs/` archive) as current state. Include index/overlay only for structure hints; **never** treat mid-epic stub columns as inventory.
   - **Read each of those files with the Read tool** (chunk through large ones). Grep, title lists, memory, or primer-only skims **do not count**.
   - **Prove it in the question turn:** name the path(s) read and ground options in concrete terms from them. If you cannot cite specifics from the relevant files, you have not read them — go read before asking.
   - Asking from a skim is a **defect**, same class as dumping a whole artifact in one iterate cycle.
2a. **Stories in the session's scope.** A session's ticket names its stories (its `Story:` headings); they are the increment. Every one of them is generated and validated with the patterns its content is generated with: generate uses the session's overlays and records them in `.context/patterns.md` at the root of each folder it writes, with the roles the folder holds of a pattern whose layers sit in several folders; validate reads that file. Stories the ticket does not name belong to other increments: leave them alone, and do not judge or report them. Write only the modules and tests those stories need, and validate with paths naming exactly those files, so the check measures the increment, not the repository.
2b. **`do-not-invent-requirements`** — Do not invent features, requirements, or status/maintenance signals absent from source / the ask. Prefer the existing gap/fallback over minting a new state. Asking how a described behaviour acts at its edges is required, and is not invention: where the practice's rules ask for edge and error cases (Stories, `edge-and-error-cases-have-scenarios`), write them as part of the work, as scenarios of the story or stories of the sub-epic, and take what should happen from the source, the running product, or the person. Where a case plainly applies and all three are silent, ask the person in the chat in place of a guess and write the scenario from the answer, because an edge nobody asked about ships undecided.
3. **`sources-scoped-to-generated-context`** — Hang `**Sources / context:**` on the node they ground: epic / sub-epic / module, or a lower item (scenario, class, screen, component, …). Root or parent-level Sources are fine when those files apply to the **entire** artifact or subtree.
4. Apply all guidance and named rules in each **context** — each bullet is a requirement.
5. Match practice **examples** for notation, naming, depth, and tone. Take the artifact's structure, such as how many epics, modules, or screens it has and how they nest, from the sources, never from an example, a template, or an artifact of another session or test fixture, because their structure belongs to their own domain and copying it makes every artifact the same shape.
6. **Code from another format — render the scaffold first.** This step applies only when the artifact you are writing is code and the source artifact is another format (markdown or a diagram). Call the Render action before any implementation: MCP tool `render.render(guidance, format, content, source)` or slash command `/render`. Pass `format` as the code format, `source` as the source artifact's format, and `content` as that artifact. The returned code is the scaffold — modules, types, and operation signatures taken from the model. Write the behavior inside that scaffold. When a code file is already there, its content is kept: the render never replaces it. The file takes the scaffold's shape and keeps every line it held. A member the model no longer holds stays in the file, marked, and the render's result lists it under `migrate`, beside each member whose opening line the model writes another way. Report those differences and settle each one in the model or in the code, with the sources or the person. Do not delete existing code to make the file match the scaffold, because the file may hold behaviour the model never described.
7. Fill the practice **template** scaffold and save the artifact at the path these instructions name for its format.
7a. **A rewrite keeps the behaviour.** When this generate rewrites or reshapes code that already exists, first name the scenarios and tests that state what that code does today. Where none covers the behaviour about to be reshaped, write that test first and see it pass on the code as it is. After the change run those tests again. Code that follows the model or the rules and no longer does what it did is a defect, because nothing else in a generate says what the code had to keep doing.
7b. **Large job — several turns.** Decide the source from the **ask** and what this session already produced (a sketch, a model, a format to transform — not a locked default). If that source is a whole model, sketch, or similarly large artifact, implement **one slice** in this invoke, then stop. Report what this generate wrote and stop. Continue in later generate or iterate turns — even if the user asked for everything once. Filling the whole artifact in one generate is a defect (same class as dumping a map in one iterate round). A small implied source may finish in one turn. Do not treat a red full-tree **validate** as permission to finish the rest in this invoke; validate the slice you wrote.
8. Follow any extra build steps included in your instructions when present.
9. Run **validate** on what this turn wrote. If the job is one slice, a remaining gap in the rest of the source is the next turn, not this one. If the implied source was small enough for one turn and validate fails, fix the artifact and **validate** again until it passes.
