backlog-item

Module overview

space/kanban

Board shows every work session in a repository as a Ticket on a kanban, so a person can see at a glance what each session has done and what it needs next. Its Columns are the Backlog, three Stages (Discovery, Specification, Implementation), and Complete. A Stage splits into In progress and Done and carries a WIP limit, set with stage.set_wip_limit. board.show returns the whole board, board.folders lists the folders a person can choose as a workpath, and board.help(slug) returns a Help: the practice or fidelity that slug names, its stage, and its overview, guidance, and rules. A stage sends the fidelities it requires as the fidelities themselves, each with its formats and default format.

A Ticket is one session. ticket.create opens one. It is placed by its FidelityProgress: which of Generate, Validate, and Review are done on each fidelity its stage requires. A person moves it on with ticket.move_next, back with ticket.move_previous, straight into a stage's In progress or Done with ticket.move_to, and off the stages with ticket.close or ticket.archive. ticket.activate makes it the session the agent works in, after committing, pushing, or merging the ticket being left and creating the branch or worktree the person asks for; ticket.branch returns the ticket's own Branch, which says whether it exists and whether it is checked out, and ticket.open_worktree opens the ticket's own worktree. ticket.violations returns a Report of the rules broken on the ticket's stage. The Session Board app writes every action command itself, naming the ticket's session.json, and the Generate action renders an earlier fidelity into a new format before it generates.

fidelity-progress.report, fidelity-progress.files, and fidelity-progress.finish_review read one fidelity's validation report and files, and record that a person reviewed it.

A BacklogItem is an idea that is not a session yet. backlog-item.create writes one, and backlog-item.start opens it as a ticket in Discovery and moves the item's file into the ticket's session folder, where the idea stays until it becomes lasting context.

  • Purpose: See every session's progress through the delivery stages, and move sessions through them, from an agent's tools or from the Session Board app.
  • Seam (terms): Board, Column, Stage, Ticket, FidelityProgress, BacklogItem, Help, Report; the MCP operations board., stage., ticket., fidelity-progress., and backlog-item.*; @language_adapter(language="typescript") on Board, Stage, Ticket, FidelityProgress, and BacklogItem, so the Session Board app and the chat bar reach the same tools as typed objects
  • Dependencies (one-way): harness/agent_tools, harness/installation, harness/mcp, harness/guidance (PracticeGuidance, FidelityGuidance, Rule, PracticeCatalogue), harness/graph (the rule checks a report lists), harness/guidance/stages (the stage names), cdd_guidance/actions/validate (the saved graph reader, imported through sys.path as validate), space/session, space/repo, tools/file_manager (FileEntry). It sits in space because it tracks the work, beside the session and repo it reads. No Python module imports the board, so none of them may come to depend on it.

Constraint

Read a board from a repository; every column and ticket is read again from .sessions/ each time it is asked for. Move a ticket only through ticket.move_next, ticket.move_previous, ticket.move_to, ticket.close, and ticket.archive, so every move is a line in the session log or a folder move that the ticket reads back.

Store only what cannot be read from the work: a ticket's title, scope, parent, workpath, turned-off practices, and each practice root, in its session.json, and the WIP limits in .sessions/_board.json. Never store a ticket's progress or column; they come from the session log, so a move made by the agent and one made on the board give the same answer.

Progress counts only actions recorded in the session log. A fidelity's files existing is shown on the files list, but it does not mark Generate done. Validate and Review are allowed once any action on a fidelity is recorded or a file it declares is already there, as often as a person wants to check the same output again. The board and the chat bar read allowed_actions and add no rule of their own.

Never delete a backlog item's file: it is the only copy of the idea, so starting the item moves it instead.

Utility

repo

Module overview

space/repo

Repo is the local git clone of the project being worked on — its branches and its commits — so callers switch, commit, push, merge, and close work without running git themselves. Repo.current(project) is the clone holding the project a tool call names; the cdd server hands each repo tool its call's project, so one server answers chats on several projects and no repo tool takes a repository path.

Branch is a line of development on a Repo: it is checked out, switched to, saved (committed and pushed), moved into its own worktree, landed on the default branch, and closed. Worktrees (repo.worktrees) are the checkouts of the repository — the main clone and each linked worktree beside it — and a Worktree is one of them, where one branch is worked on while the main clone stays on another. Commit is a recorded snapshot whose message carries trailers such as Ticket:; git commit trailers are the record of why a change was made, so there is no second index of work to keep in step. Git (repo.git) runs the git command line in the clone, with one set of time limits and one error, RepoConnectError, for every operation. LatestRelease keeps the end-to-end results of the release that just landed and removes older ones.

The work sessions kept in the clone's .sessions folder are not the repository's concern: space/session owns them (Sessions).

The MCP tools repo.switch_branch, repo.close_branch, repo.switch_worktree, repo.close_worktree, and repo.push_commit act on Repo.current(project); each finds the branch it names (else the branch saved as open in .sessions/session.json) and calls one operation on it. The commands /switch-branch, /close-branch, /switch-worktree, /close-worktree, and /push call them.

  • Purpose: Give every caller one object graph for the clone, its branches and worktrees, and its commits, so version control is never reimplemented with raw git output.
  • Seam (terms): Repo, Branch, Worktrees, Worktree, Commit, Git, RepoConnectError, Repo.current, repo.switch_branch, repo.close_branch, repo.switch_worktree, repo.close_worktree, repo.push_commit
  • Dependencies (one-way): harness/agent_tools, harness/installation, harness/mcp, space/work_state (WorkState, which saves the open branch by its name and the open worktree by its folder; the repository turns them back into a Branch and a Worktree), tools/file_manager (FileManager, imported when first used).

Constraint

Callers pass the domain objects (Repo, Branch, Worktree, Commit), never git output as strings. A Repo acts only on the clone it was made for; to act on another clone, make a Repo for that clone, so a call can never change a clone it did not mean to. The repo tools take no repository path; they act on the clone of the project their call names. Run git only through repo.git, so every command gets the same time limits and the same error. Specs that need a repository make a real one in a temporary folder; there is no in-memory repository.

Utility

practice-session-output

Module overview

space/session

Session is one named piece of work in a project — a board ticket's work, or main, which works on the whole repository — so every action, log line, handoff, and validation report lands in the folder of the work it belongs to. A session lives in .sessions/{name}/: its session.json (title, scope, parent, workpath, and practice roots), its session.log, its handoffs, and its validation reports. A closed session moves to .sessions/_complete/{name}/. A session is read from its folder each time a caller asks for it, so a switch or a close made by another chat or by the hook server is seen at once; no session object is held between calls.

Sessions are the work sessions of one checkout and which of them is open. The open session is saved in one place, session in the checkout's .sessions/session.json (through WorkState). Sessions(project).current() and Sessions(project).switch(name, workpath) are the only operations that read or change which session is open; Sessions.saved reads it, named(name) and all() find the board's sessions, create(name, workpath, title=, scope=, parent=) makes a session for later without opening it, and close(session) makes main the open one again when that session was open. A ticket's session lives in the main checkout's .sessions, so a chat in the ticket's linked worktree logs into the folder the board reads.

The workpath is the folder a session works in; its practices write under it and its graph loads from it. An empty workpath is the whole repository. Session.root is that folder, worked out in one place: sketches, grill answers, partitions, each practice's folder, and the file manager all start from it.

PracticeSessionOutput is what one practice has in one session: whether it is on, the guideline it works with at its current fidelity and format, the folder it writes under, and its graph. session.practice("stories") returns it. Each fidelity of its guideline holds a FidelitySessionOutput: where that fidelity writes each format in the session, the files it declares there, and its reports folder. The folders a practice reads in every session of a repository are kept in its .context/practices.json (RememberedFolders).

SessionLog (session.log) is the session's session.log and session.err: one timestamped line per action, tool call, note, and loop marker, each ending with a pointer to the chat that caused it. A Loop is one context–generate–evaluate cycle marked in the log, so the lines of one cycle can be read back together with the chat that produced them. Each line points at the chat that caused it — the ChatPointer (harness/agent_tools) of the tool call the session was opened for (Session.chat), else the chat the environment names — so session.read_loop can put that chat's words back under the line. The rules a hook gave the agent wait in the session's folder until the next log line names them, because the hook server notes them and the cdd server writes that line. SessionFiles (session.session_files) are the files a session works with: the ones its practices declare, the ones in its folder, and any file of its repository it reads.

A handoff is a compact account of a session — what it achieved, what was learned, and where the next agent starts — so a fresh agent can continue the work without rereading the whole chat. Handoffs (session.handoffs) write each one as a new handoff-{timestamp}.md in the session's folder; Session.latest_handoff names the newest. The instructions session.handoff_session(next_focus, session) draft the handoff and call session.write_handoff.

A Context Decision Record (CDR) is a short, numbered markdown file that records a design choice a later reader would otherwise question: one that is hard to reverse, surprising without its context, and a real trade-off. DecisionRecords (Session.decision_records) are a session's records, .context/cdr/{NNNN}-{slug}.md under its workpath, each numbered one past the highest; CDR-FORMAT.md beside this module is their template. session.read_cdr_format, session.list_cdrs(session), and session.write_cdr(session, slug, paths) read the format, list the records, and write one; the instructions session.record_decisions_session(session) wrap an action's turn so records are offered as decisions are made.

CallSessions is how a tool call opens its sessions: sessions.py registers it with ToolCall when it is imported, so call.session is the session open in the call's project and call.session_named(session_file) the one a board command names, each opened for that call's chat, while the framework never imports this module.

ThrowawayProject is an empty project a spec works in, so the actions a spec runs write to their own session log instead of the log of whoever is working in the repository.

The MCP tools sessions.current and sessions.switch act on the project the call names. Every session.* tool acts on the session whose session.json its required session argument names (a path from the project): session.close, session.choose_workpath, session.files, session.folder_files, session.read_file, session.mark_loop, session.read_loop, session.append_log, session.write_handoff, session.read_cdr_format, session.list_cdrs, and session.write_cdr, and the instructions session.handoff_session and session.record_decisions_session; each finds its session and calls one operation on it or on its log, files, handoffs, or decision records. Per practice there are practice-session-output.enable, practice-session-output.choose_root, and practice-session-output.use_default_root; session-diagnostics.session_diagnostics probes the session log through the live MCP host. The commands /current-session, /switch-session, /close-session, /mark-loop, /read-loop, and /append-log call them, and the skills space-session-handoff-session and space-session-record-decisions-session run the two instructions.

  • Purpose: Keep the state of one piece of work — where it works, which practices it uses and where they write, the log of what was done, the handoff the next agent resumes from, and the reasons behind hard-to-reverse choices — so any chat or tool can pick the work up from its folder.

chat

Module overview

tools/chat

Chat is a Claude Code chat reached from outside it, so the session board can see which chats are connected and send one a command. A chat is connected while its cdd-board mod checks in every second; Chat.load(chat) is the chat with that id, and chat.list lists the connected ones with their name, whether a turn is running, and the folder they work in.

ChatCommand is a command a chat takes at its check-in: submit a prompt, fill the prompt box, or run a slash command. ChatMessage is a command as the board lists it — when it was sent and where it stands (waiting, taken, shown, done, or failed, with the reason it failed).

The MCP tools are chat.list, chat.send(kind, text), chat.messages, chat.remove, and chat.resend for the sender, and chat.check_in, chat.confirm, and chat.finish, which the cdd-board mod calls from inside the chat. The board's TypeScript reaches them through the language adapter the installer deploys.

  • Purpose: Let the board drive any connected chat — send it a command and follow that command until the chat has shown and finished it — without the chats and the board sharing a process.
  • Seam (terms): Chat, ChatCommand, ChatMessage, ChatNotConnectedError, chat.list, chat.send, chat.messages, chat.remove, chat.resend, chat.check_in, chat.confirm, chat.finish
  • Dependencies (one-way): harness/agent_tools, harness/installation, harness/mcp, harness/agent_tools (ChatPointer, which finds a chat's transcript by its id)

Constraint

Send only to a connected chat; sending to a chat whose mod has not checked in lately raises ChatNotConnectedError. Only the chat itself calls chat.check_in, chat.confirm, and chat.finish; a sender uses chat.send, chat.resend, and chat.remove. A fill waits while a turn runs, so do not expect it to show before the turn ends.

file-manager

Module overview

tools/file_manager

FileManager lists and reads the files under a session's roots — the folder each of its practices works in — so every application shows files the same way instead of each object growing a read operation of its own. A tool call loads it with FileManager.load(project=...), the file manager of the session open in the call's project; session.file_manager is the same object.

Folder is a listed folder and its entries, folders first; FolderEntry is one entry with its path and size. FileEntry is a declared file with its path from the project and whether it exists. FileText is a file's path and its text.

The MCP tools are file-manager.list(folder) and file-manager.read(path); the board's TypeScript reaches them through the language adapter the installer deploys.

  • Purpose: Give every caller one safe way to list and read a session's files, confined to the folders that session works in.
  • Seam (terms): FileManager, Folder, FolderEntry, FileEntry, FileText, PathOutsideRootsError, file-manager.list, file-manager.read
  • Dependencies (one-way): harness/agent_tools (FileManager.load opens the session of the call's project through ToolCall), harness/installation, harness/mcp. space/session, space/repo, and space/kanban import this module; it imports none of them.

Constraint

Name paths from the session's workpath. A path outside the session's roots raises PathOutsideRootsError, so a caller cannot read the rest of the disk through a session. read returns no text for a file that is gone, such as one deleted since a page listed it; check FileText.text rather than expecting an error.

  • Purpose: Keep meeting notes organized in Granola and turn the ones that matter into context files beside the work they inform.

Constraint

Create and move nothing in Granola until the user confirms the filing plan. Write each note verbatim to its own file; do not merge notes or summarize across them, so each context file can be read and cited alone.
