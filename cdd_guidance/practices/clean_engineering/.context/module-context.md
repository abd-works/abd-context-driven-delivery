# cdd_guidance/practices/clean_engineering
*CleanEngineering* structures a solution into independent modules with small public interfaces and one-way dependencies, then types the objects, then implements them with clean object-oriented code, keeping the same names in every step. Its fidelities are *modules* — each module's public seam and dependencies (`clean-engineering-modules`); *model* — typed classes, operations, and relationships (`clean-engineering-model`); and *code* — working production code behind those seams (`clean-engineering-code`). `clean-engineering.instructions` is the practice's guidance at its current fidelity. Other practices use Clean Engineering as the companion for their class and code work.

The class model is written as a sketch, markdown, JSON, draw.io, Python, TypeScript, Java, or JavaScript, and `render(format, content)` converts between them at the same fidelity; when the format is draw.io, the `generate_output` instructions hand diagram creation to *Drawio*.

- **Purpose:** Keep boundaries, types, and code consistent, so a change stays inside one module instead of spreading to every caller.
- **Seam (terms):** CleanEngineering, `clean-engineering.instructions`, `clean-engineering-modules`, `clean-engineering-model`, `clean-engineering-code`, `render`, `generate_output`
- **Dependencies (one-way):** `cdd_guidance/practices/clean_engineering/reading` (*GraphReading*, how the practice reads a working copy into the graph), `cdd_guidance/practices/clean_engineering/model` (the class model and its formats), `cdd_guidance/practices/clean_engineering/model/drawio` (*DrawIOCleanEngineeringModel*), `cdd_guidance/practices/source_code` (*CodeBody*, *CodeLanguage*, *SourceText*, *MeasuredBody*: the code of a file and of a body, read once for every language), `cdd_guidance/practices/sketch_document` (*SketchOutline*, which reads a class model written as a sketch), `harness/guidance` (*PracticeGuidance*), `harness/graph` (graph rules), `harness/agent_tools`, `harness/markdown`, `harness/annotations` (*Name*), `harness/whiteboard` (*Box*, where a class or module sits on a drawn diagram), `harness/drawio` (*DrawioFile*, *DrawioPage*, *CellStyle*, which read and write the class diagram), `harness/installation` (*ContextConfig*, the project's choice of code measures, and `data_of`).

Nothing in harness imports this practice back: *PracticeCatalogue* names it by reference, and the spec support that runs its rules on examples is its own `rule_examples.py` in its rules package.

## Constraint

Each `module-context.md` card opens with its language under `# {path}`, then Purpose, Seam (terms), Dependencies, and Constraint; typed class listings wait for the model fidelity. When a `module-context.md` is corrected, name the mistake as a rule in the modules fidelity in the same turn. Run lifecycle steps through the actions with this practice as guidance, not as methods on *CleanEngineering*.

## Packages

These folders have no card of their own: they are packages of this module, and their classes count in it.

### `clean_engineering/model`

*CleanEngineeringModel* is the object-oriented analysis and design (OOAD) model behind every Clean Engineering artifact: *Module*s holding *OoadClass*es, each with *Property*s, *Operation*s and their *Parameter*s, and *Relationship*s to other classes. One model is read from and written to every format — markdown, JSON, sketch, Python, TypeScript, Java, JavaScript, draw.io, and Claude Whiteboard — so a module map, a class diagram, and the code always say the same classes, the bases each class extends, and the stereotypes it carries. The practice names each format in `CleanEngineering(...).formats`; each format is one class, such as *MarkdownCleanEngineeringModel*, that parses and renders the same nodes. Text a format cannot read, such as Python that does not parse or a draw.io file that is not XML, raises *UnreadableSource* instead of reading as an empty model a sync would then apply. How the model reads a path is written in [ooad-model.md](ooad-model.md).

An operation's body is a *CodeBody* of `cdd_guidance/practices/source_code`, the module Clean Engineering, Stories, BDD, DDD, and the patterns share for reading code.

- **Purpose:** Keep one class model that every format and every practice reads, so converting between formats never changes the classes.
- **Terms other packages use:** CleanEngineeringModel, UnreadableSource, Module, OoadClass, Property, Operation, Parameter, Relationship
- **Uses:** `harness/graph` (the model's nodes are graph nodes), `cdd_guidance/practices/source_code` (*CodeBody*, *BracketStructure*, *SourceText*), and `cdd_guidance/practices/sketch_document` (*SketchOutline*, for the sketch format). Nothing here imports the practice: the practice imports this module and registers itself on *OoadNode*, and it hands the graph reading the format its model documents are written in (`model_document_format`). Each format's package (`model/markdown`, `model/drawio`, `model/whiteboard`, `model/python`, …) imports the base model and nothing in this folder imports a format, except specs. `model/drawio` and `model/whiteboard` both extend the channel-agnostic `model/diagram` (*DiagramClass*, *DiagramModule*, the modules view's *ModuleLayout*, the class view's *ClassView* and the card placement), so both draw one layout, and `model/whiteboard` draws on `harness/whiteboard`; a board is read back by a reader that owns the elements it reads (arrows and sections are never handed to a class model as bare data); the practice reaches *WhiteboardCleanEngineeringModel* by module and class name, so it adds no class named outside this module. Inside `model/drawio`, the page reader (`drawio/page`) is read by both the class model and the layout scanners, so the scanners depend on it one way. The graph rules live in the practice's `rules` package, which reads this model's measures; *ProductionCodeRule*, the base of every rule that judges one node at a time, lives there too. This module holds no rule. The graph reading and the facts it records for the rules are not here: they are the practice's `reading` package (`clean_engineering/reading`, with its own card), which imports this model and its formats, and nothing here imports it back. It is a package of the practice's module, so `deep-module` measures it with the practice, not on its own. JSON that does not parse raises *UnreadableSource*, as every other format does. A class, a module, a property, an operation, and a span of source each hold the parts that do one of their jobs, made once and reached through the owner (`oclass.source_facts`, `oclass.arrows`, `module.source_facts`, `prop.arrow`, `operation.source_facts`, `span.failures`, `span.collaborators`, `function.collaborators`), so no caller names a part's class.

**Constraint.**

Callers work with the base nodes and reach a format through the practice's `formats`; they never pick a format's internals or parse text themselves. Pass the previous file when rendering code from a model that came from markdown or a diagram, so the operation bodies already written are kept.

### `clean_engineering/measures`

*CheckedCodeMeasures* keeps the code measures of the files a read names, as the refresh a validate asks for does: each function, class and module read from them asks the tool its project chose for each measure in its language, and keeps the answer as a fact on its node, named in plain English (*CodeMeasure*, for the measures a tool supplies: `paths_through`, `readability_score`; `total_complexity`, `classes_depended_on`, `unshared_method_groups`; `modules_importing`, `abstractness`, `instability`). A measure a fact on the node already gives is read from that fact and no tool is asked: a function's lines (`line_count`) and parameters (its parameter nodes), a class's methods (`method_count`), a module's import loops (`module_import_loops`) and the modules it imports (`imported_modules`). A module is a folder that owns a module card, and only modules carry module measures: a folder without a card is a package, a part of the nearest module above it, so the module is measured over its own files and its packages', and its imports are those of all of them to other modules, a child module with a card of its own among them (*ModuleImports*, in `reading/folder_facts.py`). `GraphReading.metrics_of(node)` answers the measures a limit holds on a node, with value and limit, and after them the two measures of a module shown with no limit (`SHOWN_WITHOUT_LIMIT`: the modules it imports and the modules that import it), which the explorer tree shows under the node's `metrics`. *ChosenTools* is the project's table of measure by language, with the limit of each measure, read from `code_measures` in the `.context/config.json` of the session's project (for a graph no session holds, of the folder it reads, and never of a folder above it) and laid over the shipped table, which fills in Python, TypeScript and JavaScript. *MeasuringTool* is one tool behind one question, this measure of this node: *LizardTool* imports the outside tool when first asked, and *ReaderTool* reads what the graph already holds. The limit rules in `rules/code_measure_limits.py` read the facts and report a node past its limit in the same validation report as the other rules; they are rules of the code fidelity, so they judge a class only once one of its operations has a body (`ProductionCodeRule.code_fidelity_only`, from the fidelity the reader records on each class with `Node.read_at`). The parameters a function takes are held by `limit-operation-parameters` to the limit of `parameters_taken`. The numbers the other rules hold are named once in `rules/rule_numbers.py`, which the checks read and the practice's document takes by marker (`CleanEngineering.markdown_values`), with how each rule is decided, checked or judged (`requires_judge`).

- **Purpose:** Measure the size and complexity of code where a person already checks it, so a function, class or module past a limit shows beside the other rule findings.
- **Terms other packages use:** CheckedCodeMeasures, ChosenTools, CodeMeasure, MeasuringTool, MeasuredNode, MeasureNotTaken, NoToolChosen, MeasuringToolNotInstalled, ToolDoesNotTakeMeasure, `NOT_MEASURED`; and in `read_facts.py`, what the measures read of the nodes the reading builds, which the reading and the rules import from here: `DESCRIBED_FACT`, `IMPORTED_MODULES_FACT`, `IMPORTING_MODULES_FACT`, `MODULE_IMPORT_LOOPS_FACT`, *MeasuredReading*, `is_under`, `parameters_of`, `counted_parameters`
- **Uses:** `harness/installation` (*ContextConfig*, the project's config), `cdd_guidance/practices/source_code` (which files are test code, and each language's file endings). It imports nothing from `clean_engineering/reading`: it reads the facts the reading records by the names `read_facts.py` gives them, and the reading itself through *MeasuredReading*. The graph reading calls it while it reads, from `read_working_copy` through `keep_code_measures`; lizard is the optional `measures` dependency group of `pyproject.toml`.

**Constraint.**

Keep measures only through `GraphReading.keep_code_measures`, which the reader calls for the files a read names: a tool run on every load of the whole working copy would slow every read. A limit is an ordinary graph rule in `rules/code_measure_limits.py`, listed in `model/schema.yaml` like any other; add no second run, report or result type for measures, and change nothing in validate or `harness/graph` for them. A measure no tool could take, because none is chosen for the language (*NoToolChosen*) or the chosen tool is missing (*MeasuringToolNotInstalled*), is kept on the node as the reason and reported by the measure's rule; write `not measured` in the config to leave it out on purpose. Never skip a measure quietly, because a missing measure reads as code within its limit. Name a measure in plain English wherever a person reads it, with the tool's own name for it in brackets.

### `clean_engineering/model/drawio`

*Drawio* turns a Clean Engineering class model into a draw.io diagram — a modules view or a class view, chosen from what the model holds — and checks the diagram against the layout rules in `drawio.md`. `create_diagram(content, path)` writes the diagram; `render(content, path)` creates it, scans it, and, when definite layout failures remain, has the layout generator repaired by a sub-agent; `scan(paths)` reports layout rule violations on existing `.drawio` files. *CleanEngineering* is given a *Drawio* and uses it whenever its format is draw.io.

*DrawIOCleanEngineeringModel* is the draw.io format of the class model: it loads a diagram into the same modules and classes every other format reads, and saves them back. With `keep_positioning`, an updated diagram keeps the positions of the classes and the routes of the relationships already drawn, and lays out only what is new, so a person's arrangement survives regeneration. The diagram's own model is in [drawio-model.md](drawio-model.md).

- **Purpose:** Draw the class model as a readable draw.io diagram, and keep the diagram generator honest against its layout rules.
- **Terms other packages use:** Drawio, DrawIOCleanEngineeringModel, `create_diagram`, `render`, `scan`, `keep_positioning`
- **Uses:** `cdd_guidance/practices/clean_engineering/model` (the class model and its shared diagram layout), `harness/graph` (its scanners and rules are graph rules), `harness/installation`, `harness/agent_tools`, `harness/markdown`. The class model does not import it back.

**Constraint.**

Callers ask *Drawio* to create or scan a path; they never write mxCell attributes, waypoints, or HTML themselves. A layout failure is fixed in the layout generator, not by editing one diagram. Rules in `drawio.md` with no scanner, such as `module-spatial-cohesion`, are judged by validate as written rules.
