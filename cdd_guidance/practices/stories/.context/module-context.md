# cdd_guidance/practices/stories
*Stories* maps user interactions to system behaviours, then defines each behaviour through executable specifications. Its fidelities deepen one hierarchy: the *story map* (epics, sub-epics, and stories; `stories-story-map`), *scenarios* with concrete examples for each story (`stories-scenarios`), and *acceptance tests* that run those scenarios against production code (`stories-acceptance-tests`). `stories.instructions` is the practice's guidance at its current fidelity.

The same story model is written in many formats — sketch, markdown, JSON, draw.io, Miro, Claude Design, Python, TypeScript, and JavaScript — and `render(format, content)` turns a story map or its tests from one format into another without losing the hierarchy. The diagram formats — draw.io, Miro, and Claude Whiteboard (`whiteboard`, a `.whiteboard` board file sent to a Whiteboard artifact in Claude) — each extend the shared diagram story types (`model/diagram_story_map.py`) in a package of their own under `model/`; the whiteboard package draws its epics, sub-epics, stories and actors as `harness/whiteboard` elements. A story map rendered to a drawing and back keeps each story under the sub-epic its cell's id names, wherever the cell was left on the page. A scenarios file that names a story the map does not hold is read with its scenarios and reported by the rule `scenarios-name-a-story-on-the-map`, so its scenarios are never left out of the checks without a word.

A number a Stories rule holds is written once, on the story map model (`model/story_map.py`: `LAYER_BANDS`, the band of children each layer of a map holds, and `MOST_SCENARIOS`). The checks read it there, and the practice's document and the story map template carry a marker in its place (`{{child_band.sub_epic}}`, `{{story.most_scenarios}}`), which `Stories.markdown_values` fills as the guidance is read, so changing a band is one edit. Each checked rule's failing and repaired example is kept in `rules/rule_examples.py` (`EXAMPLE_PAIRS`: a rule's example folder, or a small story map in `MARKDOWN_PAIRS`), which the spec every practice shares runs (`cdd_guidance/practices/templates_and_rules_heavy_spec.py`).

- **Purpose:** Keep one Epic → Story → Scenario hierarchy that discovery, specification, and tests all read, so scope and behaviour stay traceable from the map to the code.
- **Seam (terms):** Stories, StoryTree (`model/story_tree.py`: the story map as the graph holds it, its step and epic node types, and a node's key, which UX and the Validate action ask), `stories.instructions`, `stories-story-map`, `stories-scenarios`, `stories-acceptance-tests`, `render`
- **Dependencies (one-way):** `harness/guidance` (*PracticeGuidance*), `harness/graph`, `harness/agent_tools`, `harness/markdown`, `harness/annotations` (*Name*), `cdd_guidance/practices/sketch_document` (*SketchOutline*, *DiscoveryDocument*), `cdd_guidance/practices/clean_engineering` (its class model, for code formats), `harness/whiteboard` (*Whiteboard*, for the whiteboard format), `harness/drawio` (*DrawioFile*, *DrawioPage*, *DrawioCell*, for the story map's draw.io format), `cdd_guidance/practices/source_code` (*CodeBody*, *CodeLanguage*, *WrittenBlock*, which read and write the code of a story test), `cdd_guidance/practices/ddd` (*Ddd*, read before Stories so a story can link to the domain it acts on), `harness/installation` (`CONTEXT_FOLDER`, and `data_field`, `identity` and `language_adapter`, which publish the story map's data to other languages), `harness/mcp` (`@mcp`, which publishes the story map's edits, such as `story-map.rename`, as MCP tools).

The UX practice depends on Stories: its screens show the stories, and it draws the Claude Design story canvas from the story model. Stories imports neither UX nor anything that imports it back.

## Constraint

Run lifecycle steps through the actions with this practice as guidance — `generate.generate(guidance=["stories-story-map"])` — not as methods on *Stories*. Write only stories the source describes or the user asks for. A story's scenarios cover its edge and error cases, and a sub-epic holds a story for each case big enough to be one (`edge-and-error-cases-have-scenarios`); the nine conditions in the scenarios Guidance of `stories.md` prompt which to write, and nothing about them is kept beside the scenarios. That rule is judged, with no graph check, because whether a scenario is a refusal is read from its meaning. Convert between formats with `render`, never by rewriting a format by hand, so every format keeps the same hierarchy.

## Packages

These folders have no card of their own: they are packages of this module, and their classes count in it.

### `stories/app`

- **Purpose:** the page a person edits a Stories file in, beside the chat: the story map as epics, sub-epics, stories and scenarios, edited in place. Moved here from its own repository (`C:/dev/story-ui`, 2026-11-12) to sit beside the Stories practice whose model it edits, as the Graph app sits in `harness/graph/app`.
- **Terms other packages use:** `StoryMapClient` (extends the generated `StoryMapClientGenerated`; holds its nodes, made once from each answer, as `epicsOnPage` and `incrementsOnPage`, the part a ticket's scope shows as `epicsShown`, and `addEpic`, `addIncrement` and `reorder`), the nodes of the map (`story-map-nodes.ts`: `StoryNodeOnPage`, with `EpicOnPage`, `StoryOnPage`, `ScenarioOnPage`, `StepOnPage` and `IncrementOnPage`, and `ExampleOnPage`), each knowing its kind and edited through its own tools, so each card of `StoryHierarchyView` calls its own node, `StoryMapApi` (the page's `CddApi`), `StoryMapFailures` (what failed on the page), `StoryMapWorkspaceView` and `StoryMapFailureView` (the page's error boundary); for a server, `storyMapRoutes` and `storyMapBuild` (`story-map-routes.ts`) and `STORY_MAP_PAGE` (`/story-map`, `story-map-page.ts`).
- **Domain:** none of its own. Every rule and every edit is the Python story model's (`cdd_guidance/practices/stories/model/story_model.py`: `StoryMap`, `Epic`, `Story`, `Scenario`, `Step`, `Example`, `Increment`, saved through `OpenedStoryMap`), reached through the generated adapter (`@cdd/practices/stories/model/*`), with the formats chosen for the fidelity through `FidelitySessionOutput` (`@cdd/space/session/practices/fidelity-session-output`), and the chat it was opened beside through `Chat` (`@cdd/harness/chat/chat`). No JSON or database story map: the file it was opened from is the store.
- **Served:** by the board's server on its port (8778), at `/story-map`, with `storyMapRoutes` (the story map's objects, the formats chosen, and the chat's) under `/api` (`STORY_MAP_API`, held by `StoryMapApi`, so the `story-map` package imports nothing from the app shell). `npm install` then `npm run build` writes `dist/`, which that server serves. `?file=<path from the project>` opens a Stories file; with none the page follows the story map of the session open in the project, read every two seconds. `?chat=<chat id>` (`CHAT_QUERY`, set by the chat bar's editor tile and by the board's editor widget for a ticket with a chat) names the chat whose file viewer shows a story's acceptance tests.
- **Constraints:** source only: `node_modules/` and `dist/` are ignored, so neither the runtime pin (a git checkout) nor an install carries them; the toolset walk skips `node_modules`. A failed call says what failed and how to fix it, and the page keeps the map as Python last sent it (`fail-loud-on-mcp`). Every failure on the page goes through `StoryMapFailures.fail(failure, context)`: a failed call, a read or edit that throws, a view that throws (`StoryMapFailureView`), and anything nothing caught (`main.tsx` listens for the window's `error` and `unhandledrejection`). It is shown on the page and sent to the chat that opened the page (its `?chat=` link) with `Chat.send('failure', {failure, context})`, which shows it on that chat's chat bar; each failure text goes to the chat once, so the read every two seconds meeting it again sends it once. A page no chat opened only shows it, and a failure to tell the chat is shown, never sent again. The views draw what the story model sends and nothing else: each node's description (the paragraph under its heading), edited through `edit_description`, a story's in its card and an epic's or sub-epic's in its lane once opened; a scenario's examples as the model's one table, each cell edited through its example's `edit_field` (the column that names it renames it) and a row removed through `remove`, written back into the scenario file with every other line as it was; each story's acceptance tests as links that open the file in the chat bar's file viewer of the chat the page was opened beside (`Chat.send` with `open_file`), never inside the Story UI, and, on a page no chat opened, as paths with a note saying where to read them; the increments, edited through `StoryMap.new_increment` and `Increment.add_story` / `remove_story` and kept in the thin slice beside the map; and, opened on a ticket, only the stories the ticket's session names (`StoryMap.scope`), with a Ticket scope toggle for the whole map. A map laid out by hand, such as `.context/story-map.md`, is edited too: it is read by itself and written back with every line an edit does not touch.
- **Tests:** `npm test` (type check and `story-map/story-map-client.spec.tsx`, jsdom); the story map tools are specified against a real cdd server in `cdd_guidance/practices/stories/model/story_map_edits_spec.py`.
