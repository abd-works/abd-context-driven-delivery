# cdd_guidance/practices/ux
*Ux* (user experience) defines how users reach the domain, from journey and information architecture to screen navigation. Its fidelities deepen one UX map: *information architecture* decides which screens exist and how users move between them (`ux-ia`); *mockup* locks screens as runnable greybox with typed controls and key interactions (`ux-mockup`); *front-end code* ships the product UI talking to a real backend (`ux-front-end-code`). `ux.instructions` is the practice's guidance at its current fidelity.

The UX map is written as draw.io, a Claude Whiteboard board, HTML, markdown, JSON, or Claude Design, and `render(format, content)` converts between them. *ClaudeDesignStoryMap* (`model/claude_design/story_canvas.py`) draws the Claude Design canvas a stakeholder plays: the story map, the story explorer, and the screens each story is shown on, read from the story model and the UX map. The mockup fidelity declares that canvas as an output in the `claude_design` format (each version's `design-canvas/{version}/project/canvas.json` in the UX root), so the Session Board and the chat bar offer it as the canvas format chip beside the html. The information architecture and the mockup each declare a `drawio` and a `whiteboard` output beside each other in the epic's `.context`, so the diagram chip chooses both. `ensure_javascript(practice, source_format, content)` gets the Stories or Clean Engineering JavaScript a mockup needs, rendering it through this session's own copy of that practice when it is missing. The front-end code fidelity writes views (`*View.tsx`, `*View.jsx`): it works in typescript by default, and `render` converts a view between typescript and javascript, dropping its type annotations one way and adding none the other. A view is no UX map, so *UxFormats* refuses a render between a view format and a format of the map as *ViewNotRendered*, and a view that declares what has no JavaScript without its type is refused as *ViewSyntaxNotConverted*.

- **Purpose:** Keep screens, navigation, and interactions in one hierarchy that the diagram, the mockup, and the front-end code all follow, in the domain's words.
- **Seam (terms):** Ux, UxFormats, ViewNotRendered, ViewSyntaxNotConverted, `ux.instructions`, `ux-ia`, `ux-mockup`, `ux-front-end-code`, `render`, `ensure_javascript`
- **Dependencies (one-way):** `cdd_guidance/practices/ux/model` (the UX map and its formats, loaded by format name), `cdd_guidance/practices/stories` (*Stories*, its story model, and *StoryTree*, which a story link asks for the node it names), `harness/guidance` (*PracticeGuidance*, *PracticeCatalogue*), `harness/graph` (its screen rules, and the graph *UxReading* reads UX map files into), `harness/agent_tools`, `harness/annotations` (*Name*), `harness/markdown` (*Format*), `harness/installation` (*JsonFile*, which keeps a drawio file's layout), `harness/drawio` (*DrawioFile* and its cells, for the UX map drawn in draw.io), `harness/whiteboard` (the board elements of the UX map drawn on a whiteboard), `harness/design_canvas` (*DesignCanvas*, *Artboard*, *CardLook*, for the story canvas of prototype screens), `cdd_guidance/practices/clean_engineering` and `cdd_guidance/practices/ddd` (*CleanEngineering*, *Ddd*, the practices *UxReading* reads after, so a screen links to the classes and aggregates they read). Stories imports nothing of UX.

## Constraint

Name screens and controls in the domain's words, not the layout's. Get another practice's JavaScript through `ensure_javascript`, never by writing it in a UX artifact. Run lifecycle steps through the actions with this practice as guidance, not as methods on *Ux*.

## Packages

These folders have no card of their own: they are packages of this module, and their classes count in it.

### `ux/model`

*UxMap* is the information architecture as one hierarchy: *Screen*s divided into *Region*s that hold *Control*s, the *Interaction*s a control offers, the *Transition*s between screens, the *ContentType*s and *NavComponent*s screens share, and the *UxContext* notes that apply to the whole map. *StoryDemoControl* is a control that runs story steps when used in a mockup. A screen and a control each serve stories, scenarios, and steps (`show_story`, `show_scenario`, `show_step`), each held as a *StoryLink*: its key and, when it was written as a markdown link, the file and heading it is written at. A diagram, a JSON file, and an HTML mockup are all the same *UxMap*, so every later fidelity reads the same screens. How the map reads a file is written in [ux-model.md](ux-model.md).

Each format is one class of the same map, in this module: *DrawioUxMap* (the default IA diagram, through the drawio-ux command line), *HtmlUxMap* (the mockup review page, product screens beside the story explorer, carrying the JSON model inside it), *JsonUxMap* (the full map as JSON), *MarkdownUxMap* (UX context notes), *WhiteboardUxMap* (a mockup's board: a section for each screen and region, a card for each control), and *ClaudeDesignUxMap*. Each `render`s a *UxMap* and `parse`s back what it rendered: JSON and HTML carry the whole map; draw.io carries screens with their layouts, regions with their areas, the controls each region shows with their types and, where a control's name is not its label, its name (a Story Demo control drawn as any other), transitions with their kind of navigation, the content types and nav components the screens share (a note for each on the Site Map), each screen's domain terms, and the stories, scenarios, and steps each screen and each control serves, and the whiteboard carries the same; markdown carries the scope and the context notes. A render over a file already there keeps what its source does not hold: the UX context keeps its scope and notes when the drawing is rendered to markdown, and the drawing stays as it is when the UX context is rendered to draw.io. The HTML page also carries the story explorer's tree (*ExplorerTree*: which epic and sub-epic each screen sits under, and its stories, scenarios, and steps), which the page's JavaScript only draws. HTML reads only a page it rendered, from the JSON it embeds. Claude Design writes a mockup as one prototype page per screen, each an HTML mockup page of that screen, and `canvas.json` placing a board for each; it reads the canvas back by joining each page's screen into one map, so it carries the whole map too. A render to it is saved into the canvas version being prepared, never into a published one (*RenderedCanvas*, in the Render action). *FrontEndView* (`view/front_end_view.py`) is one front-end view read from its text, which hands out its components (*Component*: its props, and the hooks and handlers it declares, each a *ComponentMember*), the props each takes, and its handlers; *TypeScriptView* and *JavaScriptView* (`view/view_formats.py`) are the two formats that read and write it, and each answers `reshape(rendered, existing)`, which the Render action calls to write a rendered view onto a view file already there: *ReshapedView* (`view/reshaped_view.py`) keeps every line of the file, adds a prop, hook or handler only the render holds empty, and marks one only the file holds as no longer in the model. A map rendered onto a UX context, a board, or a drawing already there keeps what only that file holds (`UxMap.keep_what_only`, `keep_served_by`). Every node sits on its map's graph, and a link from one screen to another (a transition, a tab's chrome, a destination) holds the *Screen* itself.

*UxReading* (`graph_reading.py`) is UX's part in the knowledge graph. It reads each UX map file under the practice's root (a drawing the drawio-ux command line wrote or one with a Site Map or Detailed IA page, `ux-map.json` or `ux.json`, a mockup's board, a mockup page that carries its map, `ux-context.md`) into a map of its own, whose nodes it places at the lines that name them. It records a transition's `from` and `to`, an interaction's `destination`, a nav component's `destinations`, and a screen's `chromeOf`; then, after Stories, Clean Engineering, and DDD have read, the `shows`, `showsScenarios`, and `showsSteps` edges from a screen and from a control to the stories, scenarios, and steps each serves (each with `shownOn` back), a link followed to the file and heading it names and never matched by its name alone, a screen's `domainTerms` edges to the one DDD class, else Clean Engineering class, each term names, and a Story Demo control's `storySteps` (each step with `runBy` back) and `boundField`. *ShownPlaces* (`shown_places.py`) traverses those edges both ways: a step's places are its own `shownOn` and `runBy` screens and controls, else its scenario's, else its story's, each control placed on the screen whose region holds it with the interactions it starts; a screen shows what it and its controls serve and run, with every scenario and step of those stories and scenarios. Render's `answer_board_comment` reads a comment on the design canvas through it. A UX map file that cannot be read as a map is kept, with the reason, in the practice root's `unread_files` fact.

- **Purpose:** Keep one UX map that every UX format and fidelity reads, so converting a diagram to a mockup never changes the screens.
- **Terms other packages use:** UxReading, UxMap, Screen, Region, Control, StoryDemoControl, Interaction, Transition, ContentType, NavComponent, UxContext, StoryLink, DrawioUxMap, WhiteboardUxMap, HtmlUxMap, JsonUxMap, MarkdownUxMap, ClaudeDesignUxMap, TypeScriptView, JavaScriptView, FrontEndView, ReshapedView, ExplorerTree
- **Uses:** `harness/graph` (the map's nodes are graph nodes), `harness/whiteboard` (the board a mockup is drawn on), `harness/markdown` (the headings a link's target names), `cdd_guidance/practices/clean_engineering` and `cdd_guidance/practices/ddd` (the classes and properties *UxReading* links a screen's domain terms and a control's bound field to; neither imports UX), `harness/annotations` (*Name*), `harness/design_canvas` (*DesignCanvas* and the artboard helpers the story canvas draws with), `cdd_guidance/practices/stories` (the story model the story canvas shows). Neither harness nor Stories imports this module.

**Constraint.**

Convert between formats through *Ux*'s `render` or a format class's `parse` and `render`; do not edit one format to match another by hand. A plain *Control* has no story steps; use *StoryDemoControl* for a control that runs them.

### `ux/story-demo`

*Story Demo* runs a mockup against its stories in the browser, so a person can watch a story play through the screens or drive the screens themselves. `StoryDemoPage.load(createStory, mode)` loads a story into the page in one of two modes: *Play*, where the explorer steps through the story's scenarios with `playNext`, and *Interactive*, where using a *StoryDemoControl* runs the story steps attached to it. The mockup's HTML marks which controls, lists, and inputs take part through `data-` attributes the generated mockup already writes.

`mountGeneratedMockup` plays a UX-generated page (`mount-generated-mockup.js`): *GeneratedMockup* owns what it paints, its *ProductScreens* (which screens show for a story, the current one, a region's selection), the explorer and product panels, and the values Interactive carries between stories; *ControlWiring* holds how the page's controls, list lines and links reach the stories; *Snapshot* reads what a scenario exposed by the dotted path a field names. The runner names no product's objects: the values it carries are those under the first name of every path the page's fields and lists are bound to.

*PlayDualRunner* collects a story's Given/When/Then steps and plays them one at a time in the browser, reporting a failed Then without stopping the page. `story-test-core` defines stories with `story`, `scenario`, and `collect` in a form that runs both in the browser and under Node's test runner (`story-test-node`), and `soft-assert` gives browser-safe Then assertions.

- **Purpose:** Show a mockup working through its stories, step by step or by hand, without a backend.
- **Terms other packages use:** StoryDemoPage, PlayDualRunner, StoryDemoControl, `mountGeneratedMockup`, `story-test-core`, `story-test-node`, `soft-assert`
- **Uses:** `cdd_guidance/practices/ux/model` (*StoryDemoControl*, which the HTML mockup is rendered from)

**Constraint.**

A plain *Control* has no story steps; only a *StoryDemoControl* runs them. A mockup's HTML imports `story-test-core` only, never the Node backend, so it runs in the browser. Keep the domain objects a story exposes across story switches in the page's session, and reset clears them.
