## Overview

The Claude Design channel renders the story map, its scenarios, and the UX screens as one Claude Design canvas: a story map you can play, and a story explorer that runs real screens on the stories' own fixtures. Stakeholders walk the product story by story while the stories, the domain, and the screens stay one graph. The canvas shows the stories on the screens that serve them, so the UX practice draws it from the Stories model.

**Where things live.** In the workspace: each session's canvas in the UX practice's root, `<ux root>/design-canvas/` (`CanvasVersions.in_practice_root(ux_root)`, the root session.json names for the UX practice, else the nearest folder under the session's root holding `ux.json` or `design-canvas/`, else `ux`; never the session's own `.sessions/<session>/` folder), with each version at `version-N/project/` (a version kept as a release at `<release name>/project/`) (artboards, `canvas.json`, `fixtures/`, `shots/`) and the UX map with its story → screen edges at `ux/ux.json`. In CDD: the generic canvas — `DesignCanvas` (pages, boards, `canvas.json`, writing to a folder), artboard and card helpers, and the project folder's files (*CanvasProject*) — is `harness/design_canvas/`; the abd look (`look.py`), the fixture bar (`fixture_screen.py`), and each story's prototype screen built on it (`story_screen.py`) are this practice's, beside this file; `story_canvas.py` beside this file lays out the story map and the explorer, and `ClaudeDesignUxMap` (`nodes.py`) lays out the Screens page; `screen_walk.py` walks a version's screens at their scenarios' steps before it is published, `project_story_canvas.py` runs the whole render of a project's canvas in one call, and `screen_artboard.py` and `canvas_explorer.py` read the artboards and the explorer back for the UX graph rules.

Render a project's canvas in one call with `ProjectStoryCanvas` (`project_story_canvas.py` beside this file), or the UX practice's `render_story_canvas` operation, which runs it with the session's roots and the fixtures builder of the stack pattern the session overlays: it reads the story map below the Stories root and `ux.json` in the UX root, builds the fixtures bundle, writes each `StoryScreen`, renders into the working version, and writes the walk, as the Steps below say. Underneath, the canvas itself is `ClaudeDesignStoryMap` (`cdd_guidance.practices.ux.model.claude_design.story_canvas`): `ClaudeDesignStoryMap(setup=StoryCanvasSetup(workspace=..., ux_map=ux_map)).render(story_map)` returns every canvas file as JSON (path → text). The story map comes from the latest story map drawio; the screens come from the UX map you pass, which you read first (for example `ux/ux.json` beside the canvas, through the UX practice's json format). The canvas keeps that map as a Claude Design map, which places each screen on its own page. Do not hand-edit the rendered files: change the generator, re-render, and republish.

## Versions

- **`update-the-existing-canvas`** — Before designing a canvas, look for one that already exists in context: `<ux root>/design-canvas/` (its `versions.json` and its version folders), `.dc.html` artboards and canvas links in the `.context/` of the modules the work touches (for example `harness/.context/ux/ChatBar.dc.html`), and canvas links named in their CDRs and context documents. When one exists, update it: start its next version from the latest (`CanvasVersions.working()`, a *CanvasVersion* whose `folder` you render into), change its artboards there, and keep its pages, boards, and names. When its `versions.json` holds `"keep_one": true`, `working()` answers the latest version itself, published or not: render into it and publish it again at the link it already has. Design a new canvas only when none exists, or when the person asks for a new one.
- **`never-overwrite-a-published-canvas`** — People edit a published canvas directly in Claude Design. A regeneration never publishes over it: `CanvasVersions.working()` (`harness/design_canvas/versions.py`) starts `version-N+1` as a copy of the latest version, the generator renders into it, and that version is published as a new canvas titled exactly `version.title`: the canvas's name, `ux-mockup` for the whole repository or `{scope}-ux-mockup` for an increment, feature, epic or module, then the version, such as `ux-mockup.version-7`, so a person can tell canvases apart and match each to its folder. `<ux root>/design-canvas/versions.json` records each version's link. A version is regenerated in place only while it is unpublished, when the user explicitly says to overwrite it, or when the project keeps one canvas: `"keep_one": true` at the top of `versions.json` (`CanvasVersions.keeps_one`), set when the person wants one canvas updated in place until they want versions again, and removed to go back to a new version on each render. With the setting on, the render writes into the published version and `publish_at` records the same link again; the walk still runs before each publish (`walk-before-publish`). Read the published canvas back before publishing over it: when people edited it in Claude Design since the last publish, merge their edits into the version's folder or ask the person, because CDD itself does not detect edits made on claude.ai; the only check left is the Artifact publish, which refuses when the canvas holds a newer version than the one the conversation last read or published.
- **`release-a-version`** — When a version is kept as a release, `CanvasVersion.release(name)`, asked of that version, renames its folder and its `versions.json` entry to the release's name (for example `<ux root>/design-canvas/design-system-setup/`), and the older versions are removed. Numbering then starts again at `version-1`, which `start_next()` copies from the latest release.
- **`each-version-carries-its-files`** — Screens link stylesheets, fonts and images as relative files inside the version (`../styles/…`, `../assets/…`), never as `/_blob/…` uploads: an upload lives in one canvas's store, so a new version's canvas cannot see the uploads of the one before.
- **`generators-add-to-the-prepared-version`** — Screen generators write into the folder of `CanvasVersions.unpublished()`, which refuses a published version unless the project keeps one canvas (`"keep_one": true`).

## Pages

- **`two-pages`** — `canvas.json` has two pages: **Story map** and **Screens**. The Story map page holds one artboard; the Screens page holds one board per prototype screen.
- **`screens-within-the-page-limit`** — Claude Design keeps at most 40 pages, and a board on a page it does not keep falls back onto the first page, on top of the story map. Each prototype screen gets a page of its own while they all fit; when they do not, the screens share one **Screens** page instead, in rows, each with its story panel beside it.
- **`one-map-artboard`** — The whole story map is one artboard (`Main.dc.html`) with one Play button. Do not split the map into an artboard per epic or story: many live artboards render hatched and slow.
- **`map-zooms`** — The map zooms with a trackpad pinch (ctrl + wheel) and its − / % / + buttons (`Artboard(..., zoomable=True)`). The % button shows the zoom and fits the whole map into its frame; pressed again once it fits, it goes back to actual size, so a reader sees every epic at once without pinching.
- **`thumbnails-need-screenshots`** — A story's thumbnail is its main screen's screenshot, the `image` the UX map records for that screen. A greenfield project has none until each prototype screen is captured, so its thumbnails read *No screenshot*; say so when you publish, rather than presenting the map as finished.

## Story map artboard

- **`map-mirrors-drawio`** — Lay the map out exactly as the story map drawio does: the same hierarchy, order, and scale. The latest drawio wins over older story code.
- **`epic-bars-span`** — An epic bar stretches across every sub-epic under it, drawn once. Sub-epic bars sit beneath, each spanning its stories. Never repeat an epic bar per sub-epic.
- **`abd-engineering-look`** — The map wears the abd engineering dark look (`LOOK` in `nodes.py`): `#0B0B0B` background, `#111113` cards, orange `#E5531A` for epic text, sub-epic fills, and the story card's inset rule; monospace labels. No white backgrounds or white buttons anywhere on the map or the explorer panel.
- **`one-thumbnail-per-story`** — Under each story, show one thumbnail: the story's main screen. Do not show the next story's screen, a thumbnail per transition, or a blank capture. No captions, no breadcrumbs.
- **`only-thumbnails-link`** — Story cards are not clickable. A thumbnail opens the story explorer deep-linked at that story, scenario, and step (`/screens/explorer.dc.html#story=…&scenario=…&step=…`).

## Story explorer

- **`screen-left-hierarchy-right`** — The explorer fills the frame (its board expands to fill): the live screen on the left, on the explorer's dark background, and the story hierarchy as a full-height panel on the right. The screen draws at its own size (`screen-at-its-own-size`), centred in the left pane, and the pane scrolls when the screen is taller than it. Only the right panel wears the abd look; its styles are scoped (`sm-` prefixes) so they never reach the product screens, which keep their own stylesheets.
- **`collapsible-tree`** — The hierarchy is a collapsible tree — epic → sub-epics → story → scenario → step — nested exactly as the story map nests it: an epic that holds its stories directly lists them under itself, and sub-epics nest as deep as the map has them, each drawn once, so the tree reads like the map and never repeats an epic as its own sub-epic. Each level opens and closes on its own, with a small indent, plus *Collapse all*, *Reset*, *Play next*, and a button that hides the panel.
- **`back-to-story-map`** — The panel starts with a **← Story map** link back to `Main.dc.html`.
- **`outline-rows`** — An outline scenario (`Name: ${example}`) lists its example rows, read from the fixtures bundle's expanded scenarios; picking a row loads that row on the screen.
- **`selection-in-view`** — The selected row scrolls into view whenever the selection changes, including when a screen's button moves the explorer.
- **`group-steps-without-screens`** — A step with no screen of its own joins the next step that has one, so every row the reader picks shows a screen.
- **`screen-cascade`** — A step shows the screen it is `shownOn`; without one, its scenario's screen; without that, its story's screen. When no screen applies, show the step's screenshot, else *No screen for this step yet*.
- **`explorer-drives-the-screen`** — The explorer dc-imports each prototype screen with `story`, `scenario`, `step` (the selected step group's text), `stepIndex` (that group's position in the scenario, from 0), `stepKind` (`when` when the group holds a When step, else the phase of its last step), and `go` props. The screen loads the selected scenario's fixture itself and shows the state for that step group, and `go(story)` moves the explorer to that story when a button on the screen leads there — the reader stays in the explorer. `go(story, scenario, step)` moves it to a step: in the scenario on show, the next step group after the one on show with a line that is, or starts with, `step`, else the first such group. So an action the reader takes on a When moves the explorer on to its own Then, a scenario with a second When and Then moves on to the second outcome, and the screen and the step on show stay together.
- **`one-group-per-action`** — The explorer lists a scenario as one step group per action: what leads to the first action, then each outcome with what leads to the next action, then the last outcome. CDD derives this from the scenarios: for each screen that shows a story or scenario and names none of its steps in the UX map, the screen shows the step before each Then that opens a run of Thens, and each scenario's last step. A scenario with two actions has three groups, and the screen keeps a state for each, so the outcome between the two actions is on screen, not skipped. Leave a screen's steps out of the UX map so CDD derives them; name a step on a screen only to group a scenario differently, and the steps a screen names then decide its groups, because the person chose them.
- **`selected-step-stands-out`** — The step group on show is drawn on a strong orange band with a thick orange bar, brighter than the scenario's box, so the reader sees at a glance which step the screen is showing. Step text reads as plain words: the `**`, `++`, links and backticks the scenario files write around terms are dropped.

## Prototype screens

A prototype screen is a real screen on a `.dc.html` artboard — the product's markup and stylesheets, not a sketch — that draws what the scenario's Givens stored. Build each story's screen as a `StoryScreen` (`story_screen.py` beside this file), which puts the markup on the shared fixture bar, hands it every domain object the scenario bound, each under its own name (`fromFixture` keeps them all with the repositories the Givens filled; the markup reads `{{ cart.… }}` or `{{ credentials.… }}`, all of them at once as `{{ bound }}`, the repositories as `{{ repositories }}`, and the explorer's `{{ go }}`), so a screen whose scenario binds credentials and no cart still draws the scenario's own objects, keeps a position for each step group, and moves the explorer to the next Then when a button or link is pressed before the scenario's last outcome. The screen's markup has one of four sources, each a small class with a head and a body:

- **`written-from-scratch`** — The main path: write the screen's markup and stylesheets for the project (`WrittenMarkup(head, body)`), in the product's own look and components when the project has them.
- **`taken-from-an-existing-app`** — When the project can reach a running or checked-out app that already draws the screen, take that page (`AppPageMarkup(page, stylesheet_folder)`): its body without the app's scripts, its inline styles, and its linked stylesheets, which `files` (a `ScreenFiles`, `screen_files.py` beside this file) copies into the version (`stylesheets` names them, as linked from `stylesheet_folder`). Replace the page's sample values with reads of the bound objects.
- **`ported-from-another-canvas`** — An option when a Claude Design prototype of the product already exists: copy its component beside the screens and draw it through `dc-import` (`PortedCanvasMarkup(component, head, attributes, size, files)`), which passes each bound object it takes (`inputs`, by name) and each position setting as attributes. `files` names the component's file and each file or folder it loads, by the path its copy takes in the version's project folder, and the links to drop, such as the prototype's vendor React and feedback scripts (`ScreenFiles(component, needs, dropped)`); the render copies them into the version, writes the component as `screens/<component>.dc.html`, and repoints its links to the copies. Use it when the person hands over such a prototype; it is not the default.
- **`mounted-production-view`** — When the product already has a production view for the screen, mount that view instead of copying its markup, so the canvas shows production as it is (`MountedViewMarkup(view, bundle)`, `mounted_view.py` beside this file). `MountedViewBundle(project_root, entry, folder, namespace)` bundles the project's view entry with esbuild into the version's `project/ds/<folder>/` when the render copies the screen's files, and stops with `MountedViewsNotBuilt` when it cannot. The entry is the project's seam with the canvas: it exports each screen by name, as a component that takes `bound`, `repositories` and `position` and makes the view's clients from them (a `CartClient` made from the bound `Cart`); `canvasRoutes`, by `METHOD /path`, which answer the view's requests by running the domain operation on those objects in the browser, never from a table written for the canvas; and `canvasNavigation`, the story each page a view leaves to belongs to, so `window.location` moves the explorer through `go` and the artboard stays where it is. The bundle runs views compiled for React 19 on the canvas's React 18 through a JSX shim, and scopes the product's stylesheet to the screen's frame (`.canvas-screen`): its selectors, its `:root` tokens, its width media queries as container queries, `vw` as `cqw`, and its fixed elements, so nothing reaches the explorer's panel. A mounted view is one element in the editor: people edit its fixtures and positions, not its text; a redesign starts from one of the other sources.
- **`screen-at-its-own-size`** — Draw every screen at the size of the prototype it shows, a phone's 390×844 unless the screen says otherwise (`StoryScreen(width, height)`), so the canvas shows the screen exactly as the prototype does. The markup sits in a frame that wide and at least that tall (`.canvas-screen`, a size container named `canvas-screen`); the screen's board on its own page takes that size, and the explorer places the screen at that width, centred. The browser window around the canvas is always wide, so a stylesheet's width media queries would draw the desktop layout; they are asked of the frame instead, as container queries. A mounted view's stylesheet gets this from its scoping; for a screen taken from an app or ported from another canvas, the render turns the width and height `@media` rules of each stylesheet it copies, and of the component's `<style>` blocks, into `@container canvas-screen` rules and `vw` into `cqw`, keeping every selector and every other media query as written, because a ported design system's tokens answer to `:root` and to the theme the component sets on the page (`ContainerCss`, `screen_files.py`). A height query asks the frame's width container, which answers only width, so write a screen's breakpoints in widths.
- **`positions-per-step-group`** — `positions` gives each scenario one position per step group the explorer lists (`stepIndex` 0, 1, …); past the last group the screen keeps the last. An outline's example row (`<outline>: <row>`) takes the outline's positions, and a scenario with none takes `story_position`. When a ported prototype keeps its states in a file (each slug's settings, with `scenarios` listing each scenario's states), `PrototypeStates(file, data_settings)` (`prototype_states.py` beside this file) reads the story's and each scenario's positions from it without the settings that hold data, and `story_screens(ux_map_file, screen)` makes a screen for each UX-map screen it keeps a state for from one screen the project configures.
- **`prototype-drives-scenarios`** — When the prototype and a scenario disagree, the prototype drives the scenario, then the domain's language: change the scenario's steps to what the screen does, in the domain's terms, rather than bending the screen to the steps.

`StoryScreen` builds on the fixture bar, whose rules every prototype screen follows:

- **`fixture-bar`** — Build the screen as a `FixtureScreen` (with its `ScenarioSource`), which puts the fixture bar at the screen's root and the bar's shared methods into its `DCLogic` class; return `Object.assign(this.barVals(), {...})` from `renderVals`. Declare `story`, `scenario`, `step`, and `go` in `data-props`; the bar does, and reloads the fixture when the explorer moves to another scenario or step.
- **`no-auto-load-standalone`** — Opened on its own, a screen does not load a fixture: its list starts on *Load a scenario…*, so a reader can walk it by hand or pick a scenario to load. Inside the explorer the explorer's scenario loads automatically; picking another scenario there loads it and moves the explorer's tree to it.
- **`from-fixture`** — The screen implements `fromFixture(repositories, scenario, examples, step, bindings)`, returning the state the scenario shows at `step`, the step group the explorer selects. Read it from the repositories the Givens filled, from what the scenario's steps bound by name (`bindings`, such as a visitor's cart the product never stores, bound with `setStoryBinding('cart', cart)`), and from the example fixtures — never hard-code data the stories already hold.
- **`actions-run-before-a-then`** — The bar loads a scenario's fixture through as many of its Whens as the step group on show follows: none before the first action, all of them at the last outcome (`load(story, scenario, actions)`, `actions` from the explorer's `stepIndex`). So a Then shows the state the real domain operation left, not a hand-made copy of the outcome.
- **`type-what-the-customer-enters`** — On a step group where the Customer acts (`stepKind` is `when`), the screen types the values its fields hold back in, one character at a time and one field after another, ending on exactly the values the scenario gives. A reader then sees what the Customer does on that step, instead of a form that is already filled. The typing changes only what each field shows, never the screen's state or the domain, so the step's values stay the ones the fixture loaded; with reduced motion turned on, the values show at once. The fixture bar's shared methods do this (`replayEntries`), so every screen gets it without project code.
- **`position-is-not-data`** — When the product screen takes settings that place it (which page, whether a sheet or dialog is open), a screen may keep those per step group. Every value the steps name — names, plans, prices, numbers, codes — comes from the fixture through the domain objects, never from a setting.
- **`real-domain-logic`** — Buttons call the bundled domain objects (validate, verify, resend, select) and show their real messages; refusals come from the domain, not from copies in the screen.
- **`one-scenario-list`** — The bar holds one list, not a picker beside a paste box: every scenario of the story (an outline's example rows among them), then dev mode's seed paste for the screen's path. Picking a scenario does both jobs at once — it loads the scenario's fixture and types the values it enters (`fromFixture(...).entered` when the screen returns it, else its state) — so picking an invalid row shows the domain's refusal. Picking the dev seed types the seed paste through the screen's `paste(field)`, which maps each field (by the label it shows) into state.
- **`edit-from-the-explorer`** — Inside the explorer the bar ends with **Edit**, a link to the screen's own artboard. Each screen sits alone on its own canvas page as a plain frame (not a full-window page), so Edit moves Play to it and leaving Play (‹) lands on that page in the editor. A link cannot switch pages or open the editor itself; editing inside the explorer would change the explorer, which draws the screen through `dc-import`.
- **`story-panel-beside-the-screen`** — Each screen's page also holds a separate, read-only **Stories** board to the right of the screen: the whole hierarchy with the screen's own stories opened to their scenarios and steps, and every other epic, sub-epic and story collapsed and greyed out. Nothing in it links or edits; it only shows where the screen sits in the story map.
- **`follow-to-next-story`** — Links to the next screen call `follow(event, nextStory)`: inside the explorer it moves to that story and loads its fixture; standalone the link opens the next screen, which has its own picker.

Three stop-rules keep a canvas from being published with screens that do not follow their scenarios' steps:

- **`real-screens-not-screenshots`** — Build each screen from real markup: written for the project, taken from an existing app's page, or ported from a prototype's own source (for a Claude Design prototype, its `.dc.html` files and the scripts they load). Never put a screenshot in a screen's place; when the person wants a screen copied and only screenshots are at hand, ask for the app or the prototype, or write the markup from scratch. A screenshot shows one state, so it cannot follow a scenario, and the `screen-is-a-prototype` rule fails it.
- **`stop-when-fixtures-fail`** — When the fixtures bundle (`project/fixtures/canvas-fixtures.js`) or the domain bundle the screens run on cannot be built, say what failed and stop until it builds. Never fall back silently to states written by hand into the screens: those show whatever the agent typed, not what the stories hold, and the reader cannot tell. Write per-scenario states by hand only when the person agrees, and then give every scenario its own (`every-scenario-has-a-state`).
- **`walk-before-publish`** — Before a version is published, walk its screens: `StoryCanvasWalk(version).walk(story_map)` (`screen_walk.py` beside this file) renders each screen the explorer plays at every step group the explorer lists for its scenarios, with the `stepIndex` the explorer hands it, and reports for each step the values it names (quoted text, dollar amounts, codes written in capitals, phone numbers) that the screen shows or leaves out. Save the report in the version's folder (`report.write(version.folder / "walk.md")`) and make each screen show what it leaves out. `version.publish_at(url, report)` refuses while a value is missing (*UnshownStepValues*); pass `accepted_misses` only for values the prototype cannot show, such as a name it keeps fixed, and only once the person agrees. `versions.json` keeps the accepted ones beside the link, so the gap stays in view.

The fixtures bundle — `CanvasFixtures` with `load(story, scenario)`, `scenarios(story)`, `examples`, `pasteFor(path)` — comes from the active pattern (`patterns/lern_domain_driven/practices/stories/model/claude_design/`).

## Steps

1. Look for an existing canvas in context (`update-the-existing-canvas`). When one exists, every step below updates it rather than starting a new canvas.
2. Link the stories to the screens in the UX map (`ux.json` in the UX root, with its `shownOn` edges); leave a screen's steps out so CDD derives its step groups (`one-group-per-action`).
3. Build each story's screen as a `StoryScreen` from its markup source — written from scratch, taken from an existing app, or ported from another canvas (`real-screens-not-screenshots`).
4. Render the canvas in one call: `ProjectStoryCanvas(project_root, ux_root, stories_root, fixtures).render({slug: screen, ...})`, with `fixtures` from the stack pattern (for the LERN pattern, `LernDomainDriven().canvas_fixtures(project_root)`), or the UX practice's `render_story_canvas` operation when the screens are already in the working version. It reads the story map below the Stories root with each story's scenario file and the UX map; builds the fixtures bundle into the working version's `project/fixtures/canvas-fixtures.js` (`CanvasVersions.working()`), checking the pattern's story runtime first; copies the files each screen's markup source names (`files`) into the version; writes each screen to `project/screens/<slug>.dc.html` and names it as that screen's `prototype` in `ux.json`; renders the story map and the explorer with each story's and scenario's `path:line` in its scenario file, for the explorer's open request; and walks the screens into `walk.md` (`walk-before-publish`). When the fixtures cannot be built it stops with `FixturesNotBuilt`, rendering nothing: say what failed and stop until it builds (`stop-when-fixtures-fail`). Name the scope with `scope=` when the canvas covers an increment, feature, epic or module rather than the whole repository. Print what it returns with `rendered.print_summary()`, which writes a character the console cannot hold, such as a minus sign a step quotes, as its escape.
5. Validate the UX map with the graph, so `screen-is-a-prototype`, `screen-follows-scenario`, `every-scenario-has-a-state`, and `scenario-listed-once` check the screens, and fix what they find.
6. Fix each screen that leaves out a value its steps name (`rendered.walk.misses`, listed in `walk.md`), and render again until nothing is missing but what the person accepts.
7. Publish the version as a new canvas titled exactly `version.title` and keep its link with `version.publish_at(url, report, accepted_misses=[...])`; build further screens into the next version the same way.
