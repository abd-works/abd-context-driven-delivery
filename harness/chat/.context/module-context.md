# harness/chat
*Chat* is a Claude Code chat reached from outside it, so the session board can see which chats are connected and send one a command. A chat is connected while its cdd-board mod checks in every second; `Chat.load(chat)` is the chat with that id. *Chats* is the roster of them all: `chats.list` lists the connected ones with their name, whether a turn is running, and the folder they work in, and `chats.open` opens a new one.

*ChatCommand* is a command a chat takes at its check-in: submit a prompt, fill the prompt box, run a slash command, or open a file (a path from the project) in its chat bar's file viewer, as the Story UI editor opened beside the chat does for a story's acceptance test. *ChatMessage* is a command as the board lists it — when it was sent and where it stands (waiting, taken, shown, done, or failed, with the reason it failed).

`chats.open(folder, prompt)` opens a new chat in the Claude app on a folder with its prompt filled in. A new chat is one object, *NewChat* (`chats.new_chat(folder, prompt)`): its folder, its prompt, and the chat it is opened from (`opened_from`, the chat whose call made the chats, `Chats.load(call)`), which answers its `claude://code/new` link (`link`, the prompt with what keeps the new chat on its folder and, when a titled chat asked, what has it join that chat's sidebar section) and opens it (`open()`, through the *ChatOpener* the chats hold, which hands the link to the system). A page in the app's Browser pane cannot hand the app that link, so the board opens a ticket's chat through it (`Ticket.new_chat_link`), and `repos.open` opens a new repository's chat through it (*RepositoryChat*). A run that names a file in `CDD_OPENED_CHATS` gets *RecordedChatOpener* (`ChatOpener.from_environment()`), which keeps each link in that file instead of opening the app, so no spec opens a chat on this machine.

The MCP tools are `chats.list` and `chats.open` on the roster, `chat.send(kind, text)`, `chat.messages`, `chat.remove`, and `chat.resend` for the sender, and `chat.check_in`, `chat.confirm`, and `chat.finish`, which the cdd-board mod calls from inside the chat. The board's TypeScript reaches them through the language adapter the installer deploys. Each chat holds its *ChatMailbox* (`chat.mailbox`), the folders its messages wait, are taken, shown, done, or failed in. In Python, `chat.mailbox.queue(kind, text)` sends as `send` does and answers with the *ChatMessage* it waits in, and `chat.mailbox.message(id)` finds a sent message in whatever state it is, so a sender such as a session's file comments can follow its message to done.

- **Purpose:** Let the board drive any connected chat — send it a command and follow that command until the chat has shown and finished it — without the chats and the board sharing a process.
- **Seam (terms):** Chats (`Chats.load(call)`: `list`, `open`, `new_chat`), NewChat (`link`, `open`, `opened_from`), ChatOpener (`open(link)`, `from_environment`), RecordedChatOpener, Chat, ChatMailbox (`chat.mailbox`: `queue`, `message`), ChatCommand, ChatMessage, ChatNotConnectedError, `chats.list`, `chats.open`, `chat.send`, `chat.messages`, `chat.remove`, `chat.resend`, `chat.check_in`, `chat.confirm`, `chat.finish`
- **Dependencies (one-way):** `harness/agent_tools` (the toolset annotations, and *ChatPointer*, which finds a chat's transcript by its id; the chat finds it once and keeps its path in `chat.json`, so reading its title again does not search the Claude projects folder), `harness/installation`, `harness/mcp`. It imports nothing from space, tools, or cdd_guidance, so it sits in harness above harness/mcp.

## Constraint

Send only to a connected chat; sending to a chat whose mod has not checked in lately raises *ChatNotConnectedError*. Only the chat itself calls `chat.check_in`, `chat.confirm`, and `chat.finish`; a sender uses `chat.send`, `chat.resend`, and `chat.remove`. A fill waits while a turn runs, so do not expect it to show before the turn ends.
