# harness/diagnostics
This module reports whether CDD is running and answering: the server health report says which of its long-running parts are up right now, and the probes check that what an install published answers through the live host.

*ServerHealth* tells a person whether the parts of CDD that run beside the MCP server are up — every registered *App* and the hook server — so the server health band in the chat can show them without anyone opening a terminal. A caller asks with the `server-health.report` MCP operation, or through its TypeScript language adapter (`@cdd/harness/diagnostics/server-health`).
*App* is one CDD web app a person opens beside the chat: the CDD Kanban, the Graph app, or the Story UI editor. Its status (*AppStatus*: not installed, not running, running) is read from its folder and its ports every time it is asked, and `app.open` readies it: it installs it while it is not installed (npm install, then the page build), launches it while it is not running (`npm start` in its folder, through *BackgroundStart*), and answers it with its url, or refuses with *AppNotStarted*, which names the app, the step, the output that says why, and the command that fixes it. *App* keeps the one registry of apps (`register`, `registered`, `App.load(label)`, which refuses a label no module registered with *AppNotRegistered*). Its TypeScript language adapter is `@cdd/harness/diagnostics/app`. It lives here, not in harness/installation, because `app.open` is an MCP operation and harness/installation imports no harness/mcp.
*AgentToolsProbe* checks the space, harness, and tools operations one install published, through the running MCP host; a person runs it as `agent-tools-diagnostics.agent_tools_diagnostics` (`/agent-tools-diagnostics`) and reads the result under `agent_tools` in `diagnostics.json`.
*GuidanceProbe* checks an install's practice and fidelity instructions and calls each guidance action with probe arguments; a person runs it as `guidance-diagnostics.guidance_diagnostics` (`/guidance-diagnostics`) and reads the result under `guidance` in `diagnostics.json`.
Both diagnostics toolsets extend *CallDiagnostics*, which holds the one call a toolset is made for and the install of the project that call names, made once. The toolset an install publishes is made with no call; it answers each call through `for_call`, and asked to probe without a call it raises *DiagnosticsNeedACall* rather than probe the folder the server runs in. The guidance probe calls the actions of *ActionCatalogue* that the install deployed and leaves `improvement.repair` and `improvement.verify_fix` alone, reporting them skipped, since they act on real work; it reads each practice's folder from the practice. Probe arguments and skips are kept here by each operation's published MCP name (decision `cdr/0001`).

- **Purpose:** Show whether CDD is running: which of its servers and apps are up, for the chat's server health band, and whether what an install published answers through the live host, so a broken publication shows up in a report rather than in a failing chat.
- **Seam (terms):** ServerHealth, App, AppStatus, AppNotStarted, AppNotRegistered; the MCP operations `server-health.report`, `app.open`, `agent-tools-diagnostics.agent_tools_diagnostics`, and `guidance-diagnostics.guidance_diagnostics`; each probe reports a section whose colour is red when any probe in it failed, so the reply and `diagnostics.json` agree.
- **Dependencies (one-way):** harness/agent_tools (*ToolCall*, which carries the call's project and the MCP host answering it), harness/installation (`@language_adapter`, `@data_field`, and *Installer*, made once for the call's project and held by the diagnostics made for that call; the probe reads what the install published and writes its section through it), harness/mcp, harness/hooks (*HookDaemon*, which answers whether this checkout's hook server is running), harness/process (*BackgroundStart*, which launches an app's server), harness/guidance, and harness/graph (`GRAPH_APP_PORTS`, the graph app's ports, read from the one file the app's servers read). Every app registers itself with *App* from the ports file its servers read: `app.py` makes and registers the Graph app, since harness/graph sits below this module, and space/kanban registers the CDD Kanban and the Story UI editor, since nothing here imports space. The report lists each app with its url, where a chat reaches it whether or not it answers yet, so the chat-ui names no port of any app's. A probe of a guidance action calls it in the main session of a temp project, which `ToolCall.session_in` opens. Nothing in the framework imports this module, and it imports nothing above the framework.

## Constraint

The server health report answers only while the MCP server is up, so it says nothing about the server itself; the band in harness/chat-ui/pane works out that the server is lost, or that tools are missing, from how its own calls fail. The band calls the report after every cdd call and every prompt, so the operation stays out of the session log (`@noSessionLog`).

Run a probe through the MCP host answering the diagnostics call (`call.mcp_host`); a probe that builds its own host checks code the chats do not run. A tool that does not answer within the probe's time limit is reported red and left running, so one hung tool never hangs the report. Keep the probes here, above the modules they check, so a module never imports its own checker.
