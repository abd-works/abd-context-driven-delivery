# harness/diagnostics
This module reports whether CDD is running and answering: the server health report says which of its long-running parts are up right now, and the probes check that what an install published answers through the live host.

*ServerHealth* tells a person whether the parts of CDD that run beside the MCP server are up — every registered *App* and the latest heavy and e2e test runs — so the server health band in the chat can show them without anyone opening a terminal. A caller asks with the `server-health.report` MCP operation, or through its TypeScript language adapter (`@cdd/harness/diagnostics/server-health`).
*CddVersion* tells a chat which CDD version it runs and how that stands against the latest release on origin (its newest `v*` tag), so the chat bar's version badge shows it green (current), yellow (a minor version behind) or red (a major version behind) and offers the update. A caller asks with the `cdd-version.check` MCP operation, which fetches origin's tags first, or through its TypeScript language adapter (`@cdd/harness/diagnostics/cdd-version`); the version is `major.minor` of the `version` in the served checkout's `pyproject.toml` (*Release*), and how the two stand is a *VersionStanding*. When origin cannot be reached it reads the newest release tag as last fetched. Commits on main after a release do not make a chat behind, and the badge's update (`/install-latest`) merges that release, not the tip of main. `cdd-version.set_next` (`/version`) writes the next version into the `pyproject.toml` of the project the call names, the version given or the next minor, and refuses text that is not a version with *VersionNotValid*; nothing raises the version by itself.
`cdd-version.release` (`/release`) releases the version `/version` set, never on red (*CddRelease*): `/version` sets the number, `/release` only packages it and changes no file. It refuses with *ReleaseAlreadyTagged* when that version already has its tag, and with *ReleaseOnRed* unless the latest e2e and heavy runs passed on HEAD; previewed, it answers the version and its release notes (*ReleaseNotes*: the commits and the tickets moved to `.sessions/_complete` since the previous `v*` tag, or since the last change to `pyproject.toml` before the first tag); published, it pushes HEAD, tags it `v<version>`, pushes the tag, and runs `gh release create` with the GitHub command line in the project's folder, answering the release's url. The person is asked before publishing.
*TestCadence* runs the slow tiers on main on a cadence, heavy every hour and e2e every day (*TestTier*), one at a time. Nothing keeps time: every `server-health.report` calls `start_due`, which starts the overdue tier in a background process (`python -m harness.diagnostics.test_runs <tier> <checkout> <record folder> --started <when the cadence recorded the run>`, *TestRunner*, the boundary to `scripts/test.ps1`) for the repository's own folder while it has main checked out (`main_checkout`); that process goes on with the run the cadence recorded, so the two are one run. A tier does not run in the checkout's own folder, which goes on changing: it runs in a detached git worktree at the commit the run records (*RunWorktree*, under `test-run-worktrees/` in the cdd home, removed when the run ends), which borrows the checkout's `node_modules` folders by link, copies the language adapters its install wrote (`.claude/language-adapters`, copied so that nothing reaches the person's own installed folder), and brings the scheduled e2e run's captures back to the checkout. A run by hand therefore tests HEAD as committed, not uncommitted edits. Each run (*TestRun*) names its checkout, its commit, and the process that runs it by its id together with when that process started, since the system gives an ended process's id to a later one; a run is live only while that process runs, and killing it ends its `test.ps1` and the specs under it (a *StarterBoundJob* of `harness/process`). A run started while another is live, on any checkout, waits and says each time what it waits for. The runs are kept in `test-runs.json` in the cdd home (*TestRunRecord*, one per checkout: the latest run of each tier with the run before it, so a failure after a pass is a new failure, and a run on a ticket's worktree leaves main's result alone). The file is put in place whole, so a reader never meets half a record, and a file that holds something else is refused with *TestRunRecordUnreadable*, which names the file and what it holds, and is never written over. The report lists the latest of each tier under `test_runs`, the health band shows them, and the chat raises a toast once for each new failure.

*DesktopWalkQuestion* (`desktop_walk_question.py`) is what the cadence asks the person when it starts an e2e run on its timer in a checkout that holds desktop story tests (`*_story.desktop.md`): whether to run the desktop walk now, which takes their screen and keyboard. The e2e run starts at once whatever the answer. `server-health.report` holds the open question as `desktop_walk_question`, the chat bar draws it as a dialog, and `server-health.answer_desktop_walk(run_id, is_yes)` takes the first answer any chat gives and tells that chat whether to run the question's command, `/desktop-walk`. On no, or no answer within ten minutes, nothing is walked, and the e2e run's summary says the walk was not run and why. A run a person starts by hand asks nothing.
*App* is one CDD web app a person opens beside the chat: the CDD Kanban, the Graph app, or the Story UI editor. Its status (*AppStatus*: not installed, not running, running) is read from its folder and its ports every time it is asked, and `app.open` readies it: it installs it while it is not installed (npm install, then the page build) and answers it with its url and its *AppServer* (the *NodeScript* its server runs: its folder and its command, and the ports it tries, which on the dev lane sit `ServerLanes.DEV_APP_PORT_OFFSET` above its ports file's, the command then naming the first with `--port`), or refuses with *AppNotStarted*, which names the app, the output that says why, and the command that fixes it. `app.install` installs an app again whatever its status, as the board's Update does for the CDD Kanban, so an open page loads the new build. The chat that opens an app starts its server, so the server stops when that chat ends, as /board's did; two apps one server serves (the board's server serves the CDD Kanban and the Story UI editor) share one *AppServer*. An app is made from its *AppPackage* (its folder, `package.json`, the folders outside it its build reads, and npm) and its *AppPage* (the *AppServer* that serves it and its path there): `App(label, AppPackage(folder, imports), AppPage(server, path))`. *Apps* is the one registry of apps, `APPS` (`app.register()`, `APPS.registered`, `App.load(label)`, which refuses a label no module registered with *AppNotRegistered*). Its TypeScript language adapter is `@cdd/harness/diagnostics/app`. It lives here, not in harness/installation, because `app.open` is an MCP operation and harness/installation imports no harness/mcp.
*AgentToolsProbe* checks the space, harness, and tools operations one install published, through the running MCP host; a person runs it as `agent-tools-diagnostics.agent_tools_diagnostics` (`/agent-tools-diagnostics`) and reads the result under `agent_tools` in `diagnostics.json`.
*GuidanceProbe* checks an install's practice and fidelity instructions and calls each guidance action with probe arguments; a person runs it as `guidance-diagnostics.guidance_diagnostics` (`/guidance-diagnostics`) and reads the result under `guidance` in `diagnostics.json`.
Both diagnostics toolsets extend *CallDiagnostics*, which holds the one call a toolset is made for and the install of the project that call names, made once. The toolset an install publishes is made with no call; it answers each call through `for_call`, and asked to probe without a call it raises *DiagnosticsNeedACall* rather than probe the folder the server runs in. The guidance probe calls the actions of `ACTION_CATALOGUE` that the install deployed and leaves `improvement.repair` and `improvement.verify_fix` alone, reporting them skipped, since they act on real work. Its *ProbeArguments* makes one set of practices for the probe (a *PracticeSet*), which answers the practice or fidelity a slug names, so the probe reads an instruction from the guidance the set found and each practice's folder from the practice. A probed answer is the operation's text or its JSON data (*ProbedAnswer*). Probe arguments and skips are kept here by each operation's published MCP name (decision `cdr/0001`).

- **Purpose:** Show whether CDD is running: which of its servers and apps are up, for the chat's server health band, and whether what an install published answers through the live host, so a broken publication shows up in a report rather than in a failing chat.
- **Seam (terms):** ServerHealth, CddVersion, VersionStanding, VersionNotValid, CddRelease, ReleaseNotes, ReleaseOnRed, ReleaseAlreadyTagged, TestCadence, DesktopWalkQuestion, TestTier, TestRun, TestRunRecord, TestRunRecordUnreadable, TestRunner, RunWorktree, App, AppPackage, AppPage, AppServer, NodeScript, Apps (`APPS`), AppStatus, AppNotStarted, AppNotRegistered; the MCP operations `server-health.report`, `cdd-version.check`, `cdd-version.set_next` (`/version`), `cdd-version.release` (`/release`), `app.open`, `app.install`, `agent-tools-diagnostics.agent_tools_diagnostics`, and `guidance-diagnostics.guidance_diagnostics`; each probe reports a section whose colour is red when any probe in it failed, so the reply and `diagnostics.json` agree.
- **Dependencies (one-way):** harness/agent_tools (*ToolCall*, which carries the call's project and the MCP host answering it), harness/installation (`@language_adapter`, `@data_field`, and *Installer*, made once for the call's project and held by the diagnostics made for that call; the probe reads what the install published and writes its section through it), harness/mcp, harness/guidance, harness/graph (`GRAPH_APP_PORTS`, the graph app's ports, read from the one file the app's servers read), harness/process (*BackgroundStart*, *PythonInterpreter*, and *RunningProcess*, which start and watch a test run; *ExclusivePort* and *ProcessNotStopped*, which find and stop an app's server), harness/git (*Git* and *RepoConnectError*, which read the checkout's version tags and push a release), and harness/e2e_review (*ScheduledReview*, which the test cadence starts on the screens of the daily e2e run, and *E2eReview*, whose latest run the health report shows). Every app registers itself with *App* from the ports file its servers read: `app.py` makes and registers the Graph app, since harness/graph sits below this module, and space/kanban registers the CDD Kanban and the Story UI editor, since nothing here imports space. The report lists each app with its url, where a chat reaches it whether or not it answers yet, so the chat-ui names no port of any app's. A probe of a guidance action calls it in the main session of a temp project, which `SESSION_OPENING.saved_in` opens. Nothing in the framework imports this module, and it imports nothing above the framework.

## Constraint

The server health report answers only while the MCP server is up, so it says nothing about the server itself; the band in harness/chat-ui/pane works out that the server is lost, or that tools are missing, from how its own calls fail. The band calls the report after every cdd call and every prompt, so the operation stays out of the session log (`@noSessionLog`).

Run a probe through the MCP host answering the diagnostics call (`call.request.mcp_host`); a probe that builds its own host checks code the chats do not run. A tool that does not answer within the probe's time limit is reported red and left running, so one hung tool never hangs the report. A probe reports red any failure the program declares, such as a refusal a module defines or an OSError, and lets a built-in programming error such as a TypeError raise (`raised_by_a_bug`), so a bug is never read as a probe's ordinary finding. Keep the probes here, above the modules they check, so a module never imports its own checker.
