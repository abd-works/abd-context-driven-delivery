# harness/e2e_review
*E2eReview* reviews end-to-end screens step by step. An agent walks a sub-epic by hand (`walk`) or runs its browser story tests (`run`), and either way gets an *E2eRun*: one run folder, `<project>/.sessions/<release>/e2e-test-results/<epic>/<sub-epic>/<run>/`, whose `results.json` holds one entry per step, whose `screens/` holds each step's screenshot, and whose `review.json` holds the verdicts, and whose `changed.json` holds its summary. The one model of a run is TypeScript's, in `report/run.ts`: *SubEpicRuns* (a sub-epic's runs, its baseline, `accept`) and *Run* (its steps, review, previous run, `pairsAgainst`, `changedAgainst`, `judge`, `recordVerdict`, `addWalkedStep`, `summary`); `review.ts` is only its command line (pairs, verdict, judge, walk-step, accept, summary) and `report.ts` only renders a *Run*. Every command that changes a run keeps its summary beside it, and *E2eRun* reads that summary once, so the server health report never starts Node; a `changed.json` written before the summary holds only the changed steps' keys and is read as those. `changed_pairs` lists the steps whose screen changed against the accepted run, the sub-epic's baseline (`baseline_of`); `record_verdict` records a review verdict (intended, regression caught, missed by the tests, noise) with its reason on one changed step, `judge_step` the judge's verdict on a step a test ran, and `record_walked_step` a step of a walk by hand; and `accept` makes a reviewed run the next baseline, which only the person does.

*ScheduledReview* is what the daily e2e run does once its tests end: for each sub-epic it ran it writes the report pages (`E2eReview.write_report`), lists the changed pairs, and starts a background agent that may only read the screenshots and record verdicts. *E2eRunReview* is one run across every sub-epic it ran, the line the server health report shows. *ReportTool* is the boundary to `harness/e2e_review/report/`, the TypeScript that compares screenshots pixel by pixel, applies the verdict rules, and writes the report pages; Python runs it through Node and never repeats its rules.

- **Purpose:** Let a person and an agent see what each end-to-end step's screen looks like, judge every screen that changed, and accept a run as the baseline the next one is compared with, so a change no test asserts on is still seen.
- **Seam (terms):** E2eReview (`walk`, `run`, `changed_pairs`, `record_verdict`, `judge_step`, `record_walked_step`, `accept`, `latest`, `baseline_of`, `write_report`), E2eRun, E2eRunReview, ScheduledReview (`RELEASE`, `start`), ReportTool, E2eReviewRefused, `RUN_STAMP_FORMAT`; the MCP operations `e2e-review.walk`, `e2e-review.run`, `e2e-review.changed_pairs`, `e2e-review.record_verdict`, `e2e-review.judge_step`, `e2e-review.record_walked_step`, and `e2e-review.accept`
- **Dependencies (one-way):** harness/agent_tools (the toolset annotations), harness/installation (`@data_field`), harness/mcp (`@mcp`, `@long_call`, and *ClaudePlugins*, which finds the Claude Code command line the review agent starts with), and harness/process (*BackgroundStart*, which starts the browser story tests).

Two modules depend on it the other way: the test cadence of harness/release starts a *ScheduledReview* after the daily e2e run, and the server health report of harness/diagnostics shows the latest *E2eRunReview*.

## Constraint

Keep the pixel check, the verdict rules, and the report pages in `report/`, and reach them only through *ReportTool*, so one program decides what counts as a changed screen and which verdicts a step may take. Only the person accepts a baseline: `accept` takes their name, and the scheduled review's agent is started without it. The module names `story_tests/` and the board's Playwright project (`space/kanban/app`) as the places the browser story tests run from, so a project that keeps them elsewhere cannot use `run` as it stands.
