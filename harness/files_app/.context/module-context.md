# harness/files_app

The *Files app* shows a session's files beside the chat and takes a person's comments on them back to that chat: the file viewer as an app of its own, on its own server and port (`app/ports.json`, 8783), which reads only the files its link names and never the board. It is the one place a session's files are viewed; the chat bar's files button, its session name, and an `open_file` another page sends a chat all open it. Stories and scenarios: the main map's (E) Review Generated Work In File Viewer (`.context/story-map.md`, `story_tests/review-generated-work-in-file-viewer/`); acceptance tests: `space/session/review-files-in-files-app.story.*.py`, `app/files/*.spec.ts`. Model: `.context/files-app-model.md`.

**Opening it.** Python registers it once as an *App* (`files_app.py`, `FILES_APP`, harness/apps); a chat readies it with `app.open('Files')` and starts its server while it is not running. A link names what to show and who opened it:

| Query | Means |
|---|---|
| `files=<ticket>&fidelity=<slug,slug>` | the files of those fidelities of the ticket; the chat bar's files button names every fidelity of the shown stage, every practice's |
| `session-folder=<ticket>` | every file in `.sessions/<ticket>` |
| `file=<path>` | the file to open first, a `.drawio` file in the draw.io editor beside the file list |
| `chat=<id>` | the chat that opened the page, which its comments and practice changes are sent to |
| `project=<folder>` | the project every call names (`X-CDD-Project`) |

**What it calls.** Its server (`app/files-server.ts`) answers only this machine's own page and serves the generated routes of `session.*`, `file-comments.*`, `fidelity-progress.*`, `practice-session-output.*`, `failure.describe`, and one chat route, `chat.send`, through the cdd server; so the Files app does what those operations do and holds no rule of its own. The page reads the session's practices with `session.show`, and a practice toggle calls `practice-session-output.enable` then sends the chat a `refresh`, which its chat bar answers by reading the board again. A comment is added, edited, sent and cleared with the `file-comments.*` tools; the open file is read with `session.file` (text, comments, folds, violations), again every two seconds while a comment on it is sent. A `.drawio` file shows the draw.io editor (`tools/drawio_viewer`, port 8791) in the file view beside the file list, through the server's draw.io page, which starts the viewer when nothing answers its port; its ↗ link opens the same page in a tab of its own where the browser opens one (the app's browser pane opens none). A right-click on a file or folder offers to show it in the system's file browser (Explorer, Finder, or the desktop's file manager), which the server starts on this machine through `/reveal` (`app/file-explorer.ts`). A call that names a project folder that is not there, such as a ticket's worktree closed since the page opened, is refused with *ProjectFolderMissingError*, which names the folder.

**Its graph view.** The file bar's Graph button shows the session's graph instead of the files: the practice trees holding only the nodes read from the files the bar lists (`session.graph_trees`, read again whenever the bar lists other files, so the stage, practice, format and Changed filters narrow both alike), each opened a level at a time (`session.graph_branch`). Each row is drawn as the Graph app draws it, with its kind's mark (`@graph-app/labels/kind-mark`), and while the graph reads, the page shows the cdd server's progress with the Graph app's `LoadProgressView` (`/cdd/progress`). Selecting a node opens its file at its lines, or, for a node no file's lines hold such as a folder, each listed file below it (`session.graph_node_ranges`), as the file is now when it changed since the graph read it. A node shown under a relationship group, such as an operation another invokes, opens alone in its own file, never the file of the node the group sits under; with Ctrl, Cmd or Shift it joins the nodes selected, and each other file they sit in opens below the first, the page scrolling to the first node's lines. Once the trees are read, the page reads every member the graph holds (`session.graph_members`) so the source view opens a call in place across files. An open file then opens only the folds holding a selected node and closes the rest (`files/files-graph.ts` *FilesGraph*, `files-graph-view.tsx`, the source view's `openAround`), and each open file collapses to its name on its own, or all at once (`files/open-files.ts` *OpenFiles*). The graph is the session's own, read from exactly the files the bar lists (`Session.graph_trees`, `Graph.load_files`), so the bar's filters are the graph's one file filter; the page keeps no copy of it beyond what the session answered. Above the trees sits the graph view's node filter, the Graph app's own (`NodeFilterLists`, `nodeFilter` and `chosen` from `@graph-app/filter`): node types, connectors, rules and the Violations switch, offered by `session.graph_filter_choices` (Python's *Filter*). It is a different filter from the file list and applies with it: `session.graph_trees` and `session.graph_branch` take it as `node_filter`, which only narrows the nodes of the files listed and never widens the list, and a change of either the list or the node filter reads the graph again with both (`FilesGraph.filterTo`).

**Failures and Fix.** Every failure the page meets stays in the failure band under its head until a person dismisses it, with the context it failed in and a Fix button (`files/failure-fixes.ts` *FailureFixes*, `files/failure-band-view.tsx`): a file that did not open, the files that did not list, a graph that did not read, and the links of the open file that lead to a file or heading that is not there (`session.file` callouts' `missing`), said as one failure of that file. Fix asks `failure.describe` for the failure with its kind, lists the most common causes Python answers for that kind, and sends the chat that opened the page the fix command it answers (`chat.send` as a `command`), so the chat fixes it with those causes to check first; a page no chat opened shows the command to copy, and a chat that did not take it shows why, with Fix offered again. The page names only the kind of each failure it meets; the causes and the command are Python's (`tools/error_display`).

**Rendered or source.** A markdown, HTML, SVG or JSON file opens rendered, with Rendered and Source toggles leading the file's bar; every other file opens in the source view alone (`files/file-view.tsx` *FileView*, `files/file-rendering.ts`). Markdown is rendered by `marked` with each line kept on a line of its own, as a scenario's steps are written (`files/markdown-page.ts`): its front matter shows small above the page, text in angle brackets that is no lower-case HTML tag, such as a class model's `<<Aggregate Root>>` and `Collection<Cart>`, stays text, `++Book++` is underlined, and an indented tree, such as a BDD realization's states and their fenced call graphs, keeps its levels. Markdown and SVG are cleaned by `DOMPurify`, the versions Monaco already loads, so no script the file holds runs; an HTML page shows in a frame whose sandbox runs none of its scripts; JSON is laid out two spaces to a level, or shown as its text with the reason it is not valid. A link in a rendered page is followed: a web page opens in a tab of its own, and a link to another file opens that file at the section the link names (`page.graph.goToFile`); in the source view a press on a link with Ctrl or Cmd held does the same, as Go to file on an open callout does. A file opened at lines asked for, such as a node selected in the graph view, opens in the source view, which alone marks lines, comments and broken rules.

**Folding and its keys.** The source view folds as Monaco folds the file's language, classes, functions and blocks, and markdown by its headings, with or without Rules; the session's folds (`session.file` folds) are read for the graph's places. Its shortcuts are Cursor's own fold keys, VS Code's with the chord leader Cursor moved off Ctrl+K to Ctrl+M (Ctrl+M Ctrl+0 fold all, Ctrl+M Ctrl+J unfold all, Ctrl+M Ctrl+[ and ] fold or unfold the region and those inside it, Ctrl+M Ctrl+L toggle the fold, Ctrl+M Ctrl+1 to 7 fold that level, Ctrl+Shift+[ and ] fold or unfold the region), each of which the project's `.context/files-app-keybindings.json` replaces command by command, written as VS Code's and Cursor's keybindings.json writes them: `[{ "key": "ctrl+m ctrl+m", "command": "editor.toggleFold" }]`. It sits in `.context` beside the project's other settings (`config.json`) and is read once as the page opens with `session.read_file` (`files/files-fold-keys.ts` *FilesFoldKeys*); a file not there keeps Cursor's keys, and a file that is not a list of keys and Monaco's fold commands, or names a key Monaco has none for, keeps them too and the page says so in a toast.

**Callouts.** What opens in place under a line is a callout, in the rendered view and the source view alike: what a markdown link names, the section of its heading or the whole file when it names none, in a markdown file or in a story test's steps and `# Map:` and `# Model:` lines, and for a link to a file or heading not there a callout that says what is missing (`session.file` callouts), a call or class the code reaches among the graph's members once the graph view read them, and in a story test the functions, operations and examples each step invokes and observes, on the step's first line (`session.file` steps, read with Rules or Cross-file, from the session's graph). A story test opens no call or class of its own, and no file opens one a comment, a docstring or a string names. While closed a callout's line carries a mark and a label naming it; open, its lines alone show under the line, shaded once, without the graph's `/* call: */` marks, and a call inside it opens one shade deeper. On a rendered page the mark ends the line, and what opens is drawn as its kind: a markdown section as a page, code as its lines, each with the marks of its own callouts, a section those its own file holds (`session.file` of that file) and code the calls the graph's members reach, so from the story map a person opens a story's scenario in place, then what a step observes or invokes, then an operation it calls (`files/rendered-callouts.ts` *RenderedCallouts*). Which callouts show follows the file view's filters, and the session decides it: the page sends the files it lists and the graph view's node filter with each read of a file (`session.file` `paths` and `node_filter`, `files/file-callouts.ts` *FileCallouts*), and Python's *FileViewFilter* answers only the callouts they show, by the graph's own *Filter*: a callout into a file of a stage, practice or format turned off is left out, a file no fidelity declares always shows, and what a step invokes or observes is left out while the node filter leaves out that connector or the node type it reaches. The page draws what comes back and reads its open files again when a filter changes, after the graph when the graph view is reading it; it keeps no rule of its own.

**Diagnose and Align.** Under the page's head, Diagnose asks the session for every gap between its formats (`format-alignment.diagnose_alignment`) and lists each in the session's words; Align has it render the files a render brings in step (`format-alignment.align_formats`) and lists each file rendered, each failure met, and the gaps still there (`files/format-alignment.ts` *FormatAlignment*, `format-alignment-view.tsx`). A gap a render does not close and each failure carry Fix, which puts it on the failure band, whose own Fix sends it to the chat. Which gaps there are, which a render closes, and which file it reads from are the session's answers.

**Seam (terms):** the page's link and its query (`files`, `fidelity`, `session-folder`, `file`, `chat`, `project`); the server's routes under its API root (the generated `session.*`, `file-comments.*`, `fidelity-progress.*`, `practice-session-output.*`, `failure.describe` and `chat.send` routes, the draw.io page, and `/reveal`); the *App* `FILES_APP` that `app.open('Files')` readies.

**Depends on:** the generated TypeScript adapters (`.claude/language-adapters/typescript`), the graph explorer's source view (`harness/graph/app/source`), harness/apps (*App*, *AppPackage*, *AppPage*, *AppServer*), and the cdd server. Nothing imports it.

## Constraint

Open the Files app only through `app.open('Files')` and a link that names its files, and reach a session only through the server's generated routes; the page keeps no rule or copy of the session of its own. A link names its files; one with neither `files` nor `session-folder` shows that it names none. A practice change reaches the chat bar only while the chat checks in with the board, as comments do. A field added to a session operation's data reaches the page only after the language adapters are written again (an install, or `installer.write_language_adapters()`) and the app is built again.

**What a link names.** The page shows what its link names (`files/files-link.ts` *FilesLink*): the files of a ticket's fidelities (`?files=<ticket>&fidelity=<slug,slug>`), every file of its session folder (`?session-folder=<ticket>`), or every file of the folder its session works in (`?workpath-folder=<ticket>`), read through the session.json `&session=` names (else `.sessions/<ticket>/session.json`). `&file=<path>` opens that file first and `&line=<n>` shows that line of it, unfolded and scrolled into view (`FilesPage.linesShownIn`), until the person opens another file or selects a node in the graph view. The chat bar and the CDD Kanban board open it this way; the board has no file viewer of its own (2026-11-21).
