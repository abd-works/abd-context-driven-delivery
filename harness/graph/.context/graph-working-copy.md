# Graph working copy

The explorer graph is built from source on disk, not from a separate query database.

`Graph.load_working_copy(folder, practices, database?, overlays?)` stores the repo root on `graph._folder`, creates one `PracticeGraph` per practice key, and calls `fill_working_copy` in `harness/graph/working_copy.py`. The graph names no practice. Each practice registers a `GraphPractice` from its own `graph_practice.py` (`cdd_guidance/practices/{practice}/graph_practice.py`), and each pattern a `GraphOverlay` from its `graph_overlay.py`; `GraphPractices` imports that module the first time the graph asks for the practice or pattern. `fill_working_copy` reads every requested practice in the order their `reads_after` needs (DDD reads Clean Engineering's classes, so Clean Engineering goes first), then lets each one `link` its nodes to other practices' nodes, then reads each applied overlay, then runs every practice's rules.

A practice reader adds the objects its parser built to its practice graph with `PracticeGraph.add(node, node_id, file, start, end)`: the `OoadClass`, `Operation` (private ones and module functions too, so rules measure them directly), `Parameter`, `Property`, `Module`, BDD spec node, DDD building block, or Epic/Story/Scenario/Step is the node itself. A node with no parsed object behind it, such as a story's example or a LERN tier file, is made with `PracticeGraph.add_named`. Edges are recorded with `PracticeGraph.link(kind, parent, child, display)`. Rules read measurements through `node.get_fact`, which reads the node's own attributes named in its class's `graph_facts`, so every measurement has one copy and rules check exactly the object the explorer shows. `graph.json` stores those facts with the node, so a graph reloaded without parsing holds plain `Node`s that answer `get_fact` from `data`. A parsed node's `data` keeps only what the reader alone knows, such as a class's folder, or the class a property belongs to when the reader found it by its getter or field.

A step's keyword, text, and phase come from its `Step`; an operation's class (`owner`) comes from its `Operation`. The Clean Engineering root holds every member its model documents describe as its `model_members` fact, which `graph.json` saves in the practice's `root_facts`. A bounded context's node is a DDD `BoundedContext`, which reads its name from its folder's `.context/bounded-context.md`; an aggregate's node is a DDD `Aggregate`.

`attach_rules` runs the checks each `GraphPractice` gives (its own rules, the rules of a node's file language, and each active overlay's rules for it) and records each finding on its node as a `Violation`: the rule, the practice, the node, what the node is, the file and lines, the message, and the severity. `graph.json` saves each violation in its practice's `rules`, and the Validate action's reader and the board read the same `Violation` back. Each practice's `rebuild_tree()` builds the tree the app serializes.

The Vite app in `harness/graph/app` follows the CDD web domain access pattern. Its server holds one `CddConnection` and mounts the generated `graphRoutes`, so every call reaches the graph its project's cdd runtime holds: each project the server works on has a graph of its own, so one chat's loads and filters never show up in another's. The page's `GraphClient` extends the generated `GraphClientGenerated` and calls `loadWorkingCopy` with every practice name mapped to the chosen folder root. It adds only the folder dialogs, which `choose_folder.py` opens on the server's machine.

Every graph operation answers an object that marks its data with `@data_field`: the graph's own `PracticeGraph` and `Filter`, the `Inventory` of practices, a node's `GraphRulesCollection` and each `GraphRule` in it with its `Violation`s, or an object from `harness/graph/explorer.py`: a node's place in the explorer tree, a node's source, or a node a filter matches, each of which holds the node it describes and reads its data from it.

`EDGE_ORDER` in `graph.py` says where each edge kind's group sits under a node in the explorer tree. The loader, the model objects, and the schema edges all read it through `edge_order`, and `graph.json` saves the number on each edge. Every `schema.yaml` and overlay `rules.yaml` is read by one `Schema` class in `harness/guidance/schema.py`, so the schema edges, the rule lists, and the fidelity map see the same types and fields. The source view's folds and the inlining of called operations are built in TypeScript (`app/source/call-expansion.ts`); Python sends only the source text with each call marked. A load reports each practice, file, and rule through `report_progress`, and the page reads those steps from `/cdd/progress` while it waits. Every call finishes within ten minutes.
