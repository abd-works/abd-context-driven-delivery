# harness/guidance
*Guidance* is a body of practice an agent can follow: an overview, guidance, rules, templates, and the **instructions** that join them, read from markdown kept beside the class. A guidance class is an *AgentToolSet*, so the same words are installed as a skill, an MCP prompt, and rules files.
*PracticeGuidance* is one field of practice, such as Stories or Clean Engineering, that deepens through named stages. Each stage is a *FidelityGuidance* (Stories' `story_map`, then `scenarios`, then `acceptance_tests`), and the practice knows its current fidelity (`work_at(fidelity)`), whose format is the practice's format: a fidelity holds the format it last used, keeping it in the session its practice works in, so the next action on it works in it without being told, the examples beside it, the Clean Engineering companion of each fidelity, and how to `render` an artifact into another format. A practice also says what the knowledge graph reads from it: the node types the graph treats as classes, members, or source-ordered, the practice it reads after or extends, how it reads a working copy into its graph (`read_working_copy()`) and links to other practices (`link_to_other_practices()`), and the graph rules it checks (`graph_checks`, `language_checks`, and `checks()` with the graph's overlays; `rules_in` reads a rules package). A practice holds the graph that holds it (`graph`) and the practice it extends (`extended`), one of the same set of practices, so neither is looked up by name.
*Rule* is one named rule a practice holds (`one-way-deps`), with the text an agent checks work against. *RulesCollection* is a practice's or fidelity's rules together with where they apply: always, or to files matching a glob. A practice's rules are injected into the chat when a file they apply to is edited.
*PracticeCatalogue* is the one list of practices CDD ships, in the order the approach walks them (Stories, DDD, UX, Clean Engineering, BDD), so the board, the graph, and the catalog read the same practices. The framework names no practice: `cdd_guidance/practices` registers their classes (`register`) when it is imported, as every process that loads the repository's toolsets imports it, and a process where nothing registered them raises *PracticesNotRegistered*. `create_all()` makes a new set of them, each holding the practice it extends and the Clean Engineering practice whose fidelities accompany its own from the same set (`hold_set`), which is how a session makes its practices, so a fidelity's companion works in the session's own Clean Engineering; `toolset_ref` gives the toolset an action lists for a practice's or fidelity's slug.
A fidelity lists the actions that work on it (`fidelity.actions.generate(format="drawio")`): guidance names no action class, so harness/guidance_actions registers how an action runs on a fidelity with `ActionCatalogue.run_actions_with` when it is imported, as space/session registers its sessions with *ToolCall*. A fidelity holds its *ApproachStage*, its template file, and answers whether it declares a path (`declares`), so the catalog and the board ask it rather than looking a stage up by name or matching outputs again.
*ActionCatalogue* is the one list of actions CDD ships: `cdd_guidance/actions` registers each action folder's toolset (`register`) when it is imported, and each operation a toolset publishes as a skill is one *Action* (generate, repair, verify_fix); an operation annotated `@noDeploy` is called from Python only and is not an action. The catalog, the session log, and the prompt notifier read it, and a new action folder joins it by being there.
*Schema* reads one practice's `model/schema.yaml` (or a pattern overlay's `rules.yaml`) into its types, fields, and rule slugs, so the graph and the fidelity map see the same types.
The *stages* of the approach — `discovery`, `specification`, `implementation` (`harness.guidance.stages`, *ApproachStages*) — are the stage each fidelity names as **Stage:**, with each stage's scope and the actions a person runs on a fidelity in it; the graph, the catalog, and the Session Board read them here.
`load_document(content, paths)` is the document a call names, read from the files at paths so the call carries no body; a practice renders it and the actions read it.

- **Purpose:** Let a practice be one class plus its markdown, with fidelities, rules, templates, and examples an agent can follow and a validator can check against.
- **Seam (terms):** Guidance, GuidanceCollection, PracticeGuidance, FidelityGuidance, Rule, RulesCollection, PracticeCatalogue, UnknownPractice, PracticesNotRegistered, ActionCatalogue, Action, Schema, SketchLens, `load_document`, `rules_in`; `STAGES`, *ApproachStage*, *StageScope*, `DISCOVERY`, `SPECIFICATION`, `IMPLEMENTATION`; each practice's and fidelity's instructions published as MCP prompts under its slug (`stories`, `stories-story-map`). Each of these is a noun a practice author writes or a reader of guidance holds, so the module is wider than 40% public by design; its internals (*RenderRequest*, *AppliesTo*, *SchemaType*, *ApproachStages*, *DeclaredFile*, *FidelityActions*) stay private.
- **Dependencies (one-way):** harness/agent_tools, harness/annotations (*Name*), harness/markdown, harness/installation, harness/mcp, harness/hooks (rules are injected on a hook, and their read-only notice is the hook result's toast, which the hook server hands to the notifier), and nothing in cdd_guidance: the practices and the actions register their classes with *PracticeCatalogue* and *ActionCatalogue* when their packages are imported, and a fidelity's Clean Engineering companion is the one its practice's set holds. A rule injection notes its rules in the session *ToolCall* opens for the hook's project; nothing here imports space or tools.

## Constraint

Subclass *PracticeGuidance* for a new practice and keep its words in `{practice}.md` beside the class (Overview, Guidance, shared rules, a section per fidelity with its Rules), so the installer, the catalog, and the validator all read the same text. Reach another practice's fidelity through the practice's `fidelities`, and a fidelity's Clean Engineering companion through `PracticeGuidance.clean_engineering_companion`, rather than joining companion text in a subclass. Convert artifacts with `PracticeGuidance.render`, and put each format's adapter under `{practice}/model/{format}/`, so one practice has one object model behind every format. In a session, work with the session's own practice, the one its graph holds, and give an action's fidelity and format to that practice's fidelity (`work_at`, `format`), which keeps them; outside a session, a caller that changes a practice's current fidelity or format makes its own instance with `PracticeCatalogue.create(key)`, because the catalogue's shared instance is read by every other caller. Declare a practice's graph reading on its class and keep the readers in its `model/graph_reading.py`, so the graph never imports a practice.
