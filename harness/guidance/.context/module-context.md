# harness/guidance
*Guidance* is a body of practice an agent can follow: an overview, guidance, rules, templates, and the **instructions** that join them, read from markdown kept beside the class. A guidance class is an *AgentToolSet*, so the same words are installed as a skill, an MCP prompt, and rules files.
*PracticeGuidance* is one field of practice, such as Stories or Clean Engineering, that deepens through named stages. Each stage is a *FidelityGuidance* (Stories' `story_map`, then `scenarios`, then `acceptance_tests`), and the practice knows the fidelity it was made at (`fidelities.current`, set once by its constructor), whose format is the practice's format: a fidelity holds the format it last used, keeping it in the session its practice works in, so the next action on it works in it without being told, the examples beside it, the Clean Engineering companion of each fidelity, and how to `render` an artifact into another format. A practice holds three parts, each made once when it is made. Its formats (*PracticeFormats*, `practice.formats`) make each adapter once, pick the format that reads a file (`for_file`, `reading_with`, `suffixes`), and turn a *RenderRequest* into output; a practice whose formats convert in a way of their own names its own kind (`formats_type`). Its part in the knowledge graph (*PracticeReading*, `practice.reading`) says the node types the graph treats as classes, members, or source-ordered, the practices it reads after, how it reads a working copy into its graph and links to those practices (`read_working_copy()`), and the graph rules it checks (`graph_checks`, and `checks()` with the graph's overlays; `rules_in` reads a rules package); the graph hands it the graph and the practice's nodes there (`held_in`), so code holding a practice asks `practice.reading.in_graph` for its nodes. Its *Schema* (`practice.schema`) is read once from `model/schema.yaml`. A practice holds the practice it extends (`extended`), one of the same set of practices, so it is never looked up by name. A practice's `editor` is the app that edits its files beside the chat (an *App* of harness/diagnostics, held but never imported here): the module that makes the app sets it on the practice's class, as space/kanban sets the Story UI editor on Stories (`Stories.editor = STORY_UI_APP`), and every other practice has none.
*PracticeSupplement* is guidance that adds to other practices at the fidelities it names, such as TDD on Clean Engineering `code`, Stories `acceptance_tests`, BDD `development`, and DDD `tactics`. It is a *PracticeGuidance* kept with the practices, but it has no stage and no fidelities of its own on the board. Its front matter names what it `supplements`, and `always_apply` puts it on in every session. A practice holds the supplements of its set that name it (`practice.working_set.supplements`). A supplemented fidelity's `instructions` and `checked_rule_collections` end with each supplement's text and rules for it. The graph adds each supplement's graph rules to the practice's own (its *GraphOverlay*, as a pattern's), whatever overlays the session chose. `cdd_guidance/practices` registers supplements apart from the practices (`PRACTICE_CATALOGUE.register_supplements`), so the board never lists one as a practice. A supplement's working set (*SupplementWorkingSet*) also reads the fidelities its front matter names into the set's own, once it is handed the set.
*Rule* is one named rule a practice holds (`one-way-deps`), with the text an agent checks work against. *RulesCollection* is a practice's or fidelity's rules together with where they apply: always, or to files matching a glob. A practice's rules are injected into the chat when a file they apply to is edited.
*PracticeCatalogue* is the one list of practices CDD ships, in the order the approach walks them (Stories, DDD, UX, Clean Engineering, BDD), so the board, the graph, and the catalog read the same practices. The framework names no practice: `cdd_guidance/practices` registers their classes with the process's one catalogue, `PRACTICE_CATALOGUE` (`register`), when it is imported, as every process that loads the repository's toolsets imports it, and a process where nothing registered them raises *PracticesNotRegistered*. The catalogue keeps its classes in a *ClassRegistry* (harness/annotations), the one registry the practices, the actions, and the patterns each register with; each practice goes by its name, its folder's name (`names`, `practice_classes`). `create_all()` makes a new set of them, a *PracticeSet*, each holding the practice it extends and the Clean Engineering practice whose fidelities accompany its own from the same set, which is how a session makes its practices, so a fidelity's companion is the session's own Clean Engineering fidelity; `create(name)` makes one practice with the practices of its set it works with. A practice holds the practices of its set it works with in its *WorkingSet* (`practice.working_set`: `extended`, `companion`, `supplements`), which the catalogue hands the set (`hold`). A practice answers to the slugs a person types (`answers_to`, and `fidelities.called` for a fidelity's bare name), and a set answers which of its practices or fidelities a slug names (`answering`, `practice_answering`, `named`, `slugs`), so a guidance action and a diagnostics probe read a slug once into their own set's objects. Why the catalogues are instances the process holds once is recorded in `cdr/0005-the-catalogues-are-instances-of-one-registry.md`, which replaces `cdr/0001`.
A fidelity lists the actions that work on it (`fidelity.actions.generate(format="drawio")`): guidance names no action class, so harness/guidance_actions registers how an action runs on a fidelity with `ACTION_CATALOGUE.run_actions_with` when it is imported, as space/session registers its sessions with `SESSION_OPENING`; a fidelity's actions are made with the catalogue (*FidelityActions*), and each *Action* runs through the catalogue that made it. A fidelity holds its *ApproachStage*, its template file, and answers whether it declares a path (`declares`), so the catalog and the board ask it rather than looking a stage up by name or matching outputs again.
*ActionCatalogue* is the one list of actions CDD ships, held once per process as `ACTION_CATALOGUE`: `cdd_guidance/actions` registers each action folder's toolset (`register`) when it is imported, and each operation a toolset publishes as a skill is one *Action* (generate, repair, verify_fix); an operation annotated `@noDeploy` is called from Python only and is not an action. The catalog, the session log, and the prompt notifier read it, and a new action folder joins it by being there.
*Schema* reads one practice's `model/schema.yaml` (or a pattern overlay's `rules.yaml`) into its types, fields, and rule slugs, so the graph and the fidelity map see the same types.
The *stages* of the approach — `discovery`, `specification`, `implementation` (`harness.guidance.stages`, *ApproachStages*) — are the stage each fidelity names as **Stage:**, with each stage's scope and the actions a person runs on a fidelity in it; the graph, the catalog, and the CDD Kanban read them here. A stage reads its actions from the action catalogue: each action's operation is annotated `@on_stage(rank, *traits)` (*OnStage*, with the traits `STEP`, `TAKES_FORMATS`, `CHECKS`) with where it sits (partition, then the steps generate and validate, then iterate, sketch, render, and document), so no list of action names is kept beside the catalogue.
The session a practice works in is space/session's, which harness never imports, so `worked_session.py` names what guidance asks of it as protocols (*WorkedSession*, *PracticeOutput*, *FidelityOutput*), as the action catalogue names the fidelity an action runs on; and `practice_formats.py` names a format's adapter and the model it reads (*FormatAdapter*, *ObjectModel*) and what a render converts (`RenderContent`). A file no format reads (*NoFormatReads*) and text with no format named for it (*SourceFormatNotSet*) are broken calls, refused by name.
`load_document(content, paths)` is the document a call names, read from the files at paths so the call carries no body; a practice renders it and the actions read it.

- **Purpose:** Let a practice be one class plus its markdown, with fidelities, rules, templates, and examples an agent can follow and a validator can check against.
- **Seam (terms):** Guidance, GuidanceCollection, PracticeGuidance, WorkingSet, PracticeSupplement, UnknownSupplementedFidelity, PracticeFormats, PracticeReading, FidelityGuidance, Rule, RulesCollection, PracticeCatalogue (`PRACTICE_CATALOGUE`), PracticeSet, UnknownPractice, PracticesNotRegistered, ActionCatalogue (`ACTION_CATALOGUE`), Action, `@on_stage` (`STEP`, `TAKES_FORMATS`, `CHECKS`), Schema, SketchLens, `load_document`, `rules_in`; `STAGES`, *ApproachStage*, *StageScope* (`covering`), `DISCOVERY`, `SPECIFICATION`, `IMPLEMENTATION`; each practice's and fidelity's instructions published as MCP prompts under its slug (`stories`, `stories-story-map`). Each of these is a noun a practice author writes or a reader of guidance holds, so the module is wider than 40% public by design; *DeclaredFile* is public too, because a session's output makes one for a declared path under its current root (`cdr/0002-a-declared-file-is-a-value-of-the-current-root.md`). *SketchLens* and *DeclaredFile* live in guidance.py beside the practice and fidelity that hold them. Its internals (*AppliesTo*, *RuleInjection*, *SchemaType*, *ApproachStages*, *FidelityActions*, and the protocols of `worked_session.py`) stay private.
- **Dependencies (one-way):** harness/agent_tools, harness/annotations (*Name*), harness/markdown, harness/installation, harness/mcp, harness/hooks (rules are injected on a hook, and their read-only notice is the hook result's toast, which the hook server hands to the notifier), and nothing in cdd_guidance: the practices and the actions register their classes with *PracticeCatalogue* and *ActionCatalogue* when their packages are imported, and a fidelity's Clean Engineering companion is the one its practice's set holds. A rule injection notes its rules in the session *ToolCall* opens for the hook's project; nothing here imports space or tools.

## Constraint

Subclass *PracticeGuidance* for a new practice and keep its words in `{practice}.md` beside the class (Overview, Guidance, shared rules, a section per fidelity with its Rules), so the installer, the catalog, and the validator all read the same text. Reach another practice's fidelity through the practice's `fidelities`, and a fidelity's Clean Engineering companion through `FidelityGuidance.clean_engineering`, rather than joining companion text in a subclass. Convert artifacts with `PracticeGuidance.render` at the fidelity the practice was made at, or with `FidelityGuidance.render` and `render_files` at the fidelity a call works at, both through the practice's formats, and put each format's adapter under `{practice}/model/{format}/`, so one practice has one object model behind every format. In a session, work with the session's own practice, the one its graph holds, which every call in the session shares: an action holds the fidelity it works at and never moves the practice's current fidelity, and a format it names is kept by that fidelity in the session. Outside a session, a caller that works at a fidelity or format of its own makes its own instance with `PRACTICE_CATALOGUE.create(name)`; the catalogue holds classes only, so every reader makes and holds its own practices. Name a practice's kind of graph reading on its class (`reading_type`) and keep that *PracticeReading* subclass in its `model/graph_reading.py`, so the graph never imports a practice.
