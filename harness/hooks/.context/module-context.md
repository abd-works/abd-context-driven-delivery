# harness/hooks
*Hook* lets a toolset member run when the IDE fires a named event, such as `sessionStart`, `preToolUse`, or `afterAgentResponse`: the author types `@hook("preToolUse")` on the member, the member receives the event's payload (*HookPayload*, which also gives the tool call it reports as `call`, made once so every handler opens the same session), and it returns the fields the IDE reads (`permission`, `continue`, `user_message`, `agent_message`, `additional_context`), or a *HookResult*. Every hook on the same event runs, and the IDE gets one merged answer. `@hook("event", disabled=True)` turns one member off; `@Hooks(disabled=True)` above `@agent_toolset` turns off every hook on that class, and `@Hooks(deploy=False)` keeps them out of install; both are read through `Hooks.from_toolset_class(type(toolset))`, whose `disabled` and `deploy` say so.
*HookInstallation* is how `/install` publishes hooks: it records each hooked member in the IDE folder's `hook-handlers.json`, points every event it uses at the hook server in `hooks.json`, and answers which events and operations an install registered (`registered_events`, `registered_operations`). It is the hook channel's *RegisteredChannel* (its `destination` is `Hook`, and the event a member runs on is `Hook.name_given(tool.callable)`), and it holds no server (`server` is none), so an install stands up and starts nothing for it: the hook command starts the checkout's *HookDaemon* on the first event, and replaces one that loaded older hook code. It lives in `hook_installation.py`, which registers it with `SERVER_CHANNELS.register` (harness/installation) when it is imported; the package's `__init__` imports it, so any process that uses hooks can install them, and the Installer runs it without importing this module. An IDE whose layout runs no hooks gets none. A `hooks.json` that is not JSON is refused with *HooksFileUnreadable* and left as it is, so the person's own hooks are never written over. `@hook` and `@mcp` on the same member are two separate publications.
*HookDaemon* is the long-running hook server of one checkout (`HookDaemon(repo)`), a *ServerDaemon* (harness/process), whichever IDE's hook command reaches it: it keeps its address, log, and start lock in the checkout's `.hook-server/` folder, which belongs to no IDE; `running()` answers the *RunningServer* answering on its port as this checkout's (`is_running()` whether one does), and `ensure()` starts it, or replaces one that loaded older hook code, and answers it; its `address` (*HookDaemonAddress*) is where a hook command sends the event. A starting daemon that finds its port held by this checkout's daemon on older code, including one the older layout started (its address in `.cursor/hook-server.json`), stops it and takes the port; anything else on the port raises *HookPortTaken*. `stop()` stops the checkout's daemon; closing a worktree calls it (space/repo), so no daemon outlives its checkout. `hook_daemon.py` is also the hook command every install registers. The installed hook command ensures it runs and forwards the event to its address. It holds its checkout's *RepositoryToolsets*; when it starts it imports every toolset class the repository defines and serves the toolsets the `hook-handlers.json` of every hook-running IDE folder lists (`HookServer.from_repository`, *InstalledHookHandlers*, whose `refs` are each toolset's *ToolsetReference*, made into the *HandlerCatalog*); a toolset whose `@Hooks(deploy=False)` keeps it out of install never runs, so the registrations those modules make, such as how a call opens its session, hold in the hook process as they do in the MCP host.
*HookServer* runs inside the daemon and answers every event. Each event's *HookPayload* answers its own `session`, a *HookSession* (harness/agent_tools' *CallSession* with the rules it keeps for each chat, `chat_injections`, and `log_hook_dispatch(text)`, the dispatch log each handler's result is written to): the session saved as open in the `.sessions/session.json` of the event's project, else of the checkout whose hook server received it (main when none is), read once per event through the event's *ToolCall* (`payload.call.session`), which opens it with the opener space/session registers (`SESSION_OPENING.open_with`), so every hook of the event works in one session and a switch or a close made through MCP reaches the next event at once. The hook server writes its dispatch log under that session's `logs/` folder, and the session's *ChatInjections* (space/session) keep the rules a hook gave each chat and replay them on that chat's next prompt. A project that registers no sessions still gets its events answered, with nothing logged.
A hook's result can carry a `toast`, a short notice the person sees beside the chat; it is not sent to the IDE. The hook server hands each merged toast to the notifier registered with the process's one *HookToasts* (`HOOK_TOASTS.show_with`) (tools/prompt_notify registers when it is loaded), so a hook names its toast and never the notifier. `@Toast` (*Toast*, a *Destination* with no channel) on an operation or instructions asks that notifier to toast the operation when an agent calls it; the notifier reads the annotation (`Toast.annotates`). `rules_toast(source, labels)` writes the toast for injected rules, and `TOAST_ARROW` separates a toast's source from the rest, so the notifier can join the toasts of one burst.

- **Purpose:** Let a toolset member answer IDE events, and keep one hook server per checkout that runs every hooked member and merges their answers.
- **Seam (terms):** Hook, Toast, Hooks (`Hooks.from_toolset_class(cls)`: its `disabled` and `deploy`), `events_served(event)`, HookPayload, HookResult (its *HookMessages*), HookInstallation, HooksFileUnreadable, HookDaemon (a *ServerDaemon*, which raises harness/process's *ServerDidNotStart*), HookDaemonAddress, HookPortTaken, HookServer (`from_repository`, `from_handlers`), HookToasts (`HOOK_TOASTS.show_with`), `rules_toast`, `TOAST_ARROW`; the annotations `@hook("event")` and `@Hooks(disabled=True)`

## Constraint

Name the event exactly as the IDE does; it must be one of `Hook.EVENTS`, and an unknown name fails when the class is decorated, so a misspelled hook never installs silently. A disabled hook returns nothing, even when another operation calls it directly. Do not start the hook server by hand: the installed hook command and `HookDaemon.ensure()` start it, and a second start waits on the first through its start lock. The files depend one way: `hooks.py` (annotations and files) ← `hook_server.py` ← `hook_daemon.py` (daemon and hook command) ← `hook_installation.py`. Importing the package registers *HookInstallation* with the Installer; the hook command puts the checkout on the import path when it runs as a script.
