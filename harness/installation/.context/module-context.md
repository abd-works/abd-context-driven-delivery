# harness/installation
*Installer* publishes every annotated toolset member in one repository into an IDE's folder (`.claude`, `.cursor`, `.github`, Kilo), so an author never writes a skill, command, rules file, MCP entry, or hook entry by hand. A person runs it as `/install`, or `python scripts/install.py --ide Claude`, and `/clean` removes what it wrote. It is made for the repository it installs (`Installer(ide, path, repo=...)`, or `Installer.load(project=...)` for the project a call names), never for the checkout its own code sits in, because one server installs many projects. It loads the repository's toolset classes with *RepositoryToolsets* and writes each member through the installations of one run (*InstallChannels*, made once per run): a *FileInstallation* for each file channel, the *LanguageAdapterInstallation*, and one installation of every server channel registered with it. Then it stands each server up to check it loads and starts it, so a finished install answers at once.
A server channel is a *ServerInstallation*: its files point the IDE at a server process, so beside writing them it stands the server up, starts it (`ensure_running`), reports it (`status`), and names what it published. harness/mcp (*McpInstallation*, the cdd server) and harness/hooks (*HookInstallation*, the hook server) each register theirs with `Installer.installs_through(kind)` when they are imported, the same way space/session registers with `ToolCall.open_sessions_with`, so this module never imports them and a new server channel is one more registration. A server channel can also name toolsets every install publishes, such as the hooks that start the cdd server. An install in a process where no server channel registered stops with *ServersNotRegistered*; `scripts/install.py` imports both.
The install record (`record`) is the list of files the last install wrote; a record that cannot be read stops the install and the clean with *InstallRecordUnreadable* rather than being written over, so no installed file is forgotten. `diagnostics` is the install's `diagnostics.json` (*InstallDiagnostics*): `write_section(section, results)` adds one section coloured by its worst result, which is how the diagnostics probes report. An install that fails names the toolset and its cause (*ToolsetInstallFailed*).
*RepositoryToolsets* finds every toolset class in one repository by reading its source, and puts the folders that load them on the import path; the Installer, the hook server, and the MCP host each read the repository this way, so all three publish the same toolsets. `collect()` answers each toolset's `module:Class` reference without importing anything, which is how a toolset is named where it crosses a process boundary (`hook-handlers.json`, the cdd server's `--toolsets`); `classes()` imports each module and answers the classes, keeping each one that cannot be loaded in `unloadable` (*ToolsetUnloadable*) so every reader decides whether to stop or serve the rest. Importing every module this way also makes the registrations those modules make hold, as the hook server needs.
A member's destination is chosen with an annotation on it: `@skill`, `@command("name")`, `@rules` (defined here), `@mcp` (harness/mcp), or `@hook("event")` (harness/hooks); each is a *Destination* from harness/annotations. A member with no destination annotation stays in-process. `@noDeploy` keeps a member out of every destination, and `@noCatalog` keeps it out of the generated catalog without changing what is installed.
*ContextConfig* is a project's `.context/config.json` (`CONTEXT_FOLDER` names the `.context` folder once): the guidelines that apply to file patterns, which the hook server reads to decide whether a pattern's hooks run, and the folder each practice writes in, which a session reads.
*Installation* writes one destination's files, made with the install's *IdeLayout*, so every channel of one install reads one layout. *IdeLayout* is one IDE's folder layout (where its skills, commands, prompts, rules, and user-level MCP config go, and the rule file's extension), so a new IDE is one more layout rather than an `ide ==` test in every writer.
`@language_adapter(language="typescript")` on a toolset class publishes its `@mcp` operations as typed TypeScript, so an application outside Python calls the same tools as typed objects; `shares_file_views=True` marks the toolset whose client the shared file views read files through (the file manager's). `@identity(...)` on a class names the data fields that name one of its objects, the ones a tool loads it by. `@data_field` under `@property` annotates a property as part of the object's data, and `@data_field(reference=True)` sends the object it holds by its identity alone, so data can name an object that is sent in full elsewhere; `@edits("field")` names the field an operation changes when its argument is called something else, and *SourceFile* annotates a field that holds a path in the session's workspace. `data_of(value)` is the one way an object becomes JSON data, for every MCP answer and every language adapter type alike.

- **Purpose:** Install one repository into one IDE folder through every channel, from one walk of the repository, and start the servers that install points at; give every channel the annotations, the data, and the writer it publishes a member with.
- **Seam (terms):** Installer (`install`, `install_self`, `clean`, `ensure_runtimes`, `diagnose_install`, `toolsets`, `record`, `diagnostics.write_section`, `Installer.installs_through`), InstallChannels (`of(kind)`), ToolsetInstallFailed, ServersNotRegistered, InstallRecordUnreadable, RepositoryToolsets (`collect`, `classes`, `unloadable`), ToolsetUnloadable, ContextConfig, MalformedContextConfigError, `CONTEXT_FOLDER`, Installation, ServerInstallation, FileInstallation, IdeLayout, LanguageAdapterInstallation, SourceFile; the annotations `@skill`, `@command`, `@rules`, `@noDeploy`, `@noCatalog`, `@language_adapter`, `@identity`, `@data_field`, `@edits`; `data_of(value)`; `/install`, `/clean`; `python scripts/install.py`
- **Dependencies (one-way):** harness/agent_tools, harness/annotations, harness/markdown, harness/name. harness/hooks and harness/mcp import this module and register their server installations with the Installer; it imports neither. harness/diagnostics imports it.

## Constraint

Change installed files only by changing the annotated source and installing again; `.claude/`, `.cursor/`, `.github/`, `.mcp.json`, and the `cdd` entry in `~/.claude.json` are overwritten on every install. Name the repository on every *Installer* you make. Install into an IDE folder that exists: when the install record names a folder that is gone, the install goes to `{repo}/.cursor`. Put the destination annotation on the member, never in a list on the toolset, so moving a member moves its publication with it. Read the repository's toolsets and import path through *RepositoryToolsets*, so every reader skips the same folders; code that only needs those does not make an Installer. Import this package as `harness.installation`, and leave `harness/` off `PYTHONPATH`, so `import mcp` loads the MCP SDK.
