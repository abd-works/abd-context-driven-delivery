# harness/installation
*Installer* publishes every annotated toolset member in one repository into an IDE's folder (`.claude`, `.cursor`, `.github`, Kilo), so an author never writes a skill, command, rules file, MCP entry, or hook entry by hand. A person runs it as `/install`, or `python scripts/install.py --ide Claude`, and `/clean` removes what it wrote. It is made for the repository it installs (`Installer.create(ide, path, repo=...)`, or `Installer.load(project=...)` for the project a call names), never for the checkout its own code sits in, because one server installs many projects; the factory makes its collaborators and hands them to it: the IDE folder it installs into (*InstallTarget*: the IDE's *IdeLayout*, the folder, and the install's `diagnostics.json` kept there), the checkout's *LastInstall*, and the repository's *RepositoryToolsets*; the installer makes the install record of that folder itself. An IDE name is matched whatever its case, and one that is no IDE CDD installs into is refused with *UnknownIde*; a path that is empty or a file is refused with *NotAnInstallFolder*, and the folder is kept as its whole path. `scripts/install.py` answers either refusal with exit 2, and a `--from-chat` that names no folder with exit 3. Each install is one *InstallRun* (`InstallRun(installer, toolsets, replace)`, kept as the installer's `last_run`): it loads the repository's toolsets by their *ToolsetReference* (`repository_toolsets()`, read through *RepositoryToolsets*) and writes each member through the installations of the run (*InstallChannels*, made once per run; `publish`): a *SkillInstallation*, *CommandInstallation*, and *RulesInstallation* for the file channels (`files`, `rules`; each a *FileInstallation* that says where its file goes, `relative_path`, and what it holds, `front_matter` and `body`), the *LanguageAdapters* (`language_adapters`), and one installation of every channel registered with it (`registered`). `for_tool(tool)` is every installation a tool is written through, and `published` is what each registered channel published, by its channel. Then the run stands each channel's server up to check it loads and starts it (`stand_up`, `ensure_running`), so a finished install answers at once; the hook channel has no server for it to start, since the hook command starts the hook server on the first event.
Every installation writes through one *InstallPlace*: the IDE folder (*InstallTarget*), the install record (`install_record`), and the repository being installed (`repository`), with `layout`, `path`, `repo`, and `is_temporary` read from them; `wrote(path)` keeps a written file in the record, and `relative_folder(install_folder)` is a toolset's install folder from the repository; where a tool's files go and what they are named is the toolset's to say (`AgentToolSet.installed_as`, an *InstalledName*), so an installation names no practice or fidelity. `InstallPlace.into(target, repository)` makes a place that keeps its own record, for a writer outside an install run, such as the catalog working out where a skill goes. An *Installation* is a place that writes one channel's files, and names that channel as its `destination`, the *DestinationKind* of harness/annotations; the language adapters are a place but no channel, since they are written from whole toolsets rather than from a tool's destinations.
A *RegisteredChannel* is an installation a module registers with the Installer beside the file channels: it says which tools it takes (`accepts`), what it published (`published`), what it writes once every tool is recorded (`write_once_recorded`, such as the IDE's MCP entry), and one line for each fact the install report gives about it (`status`). A channel whose files point the IDE at a server holds that server (`server`, a *ChannelServer*): the install stands it up in its own process over what was installed (`stand_up`, answering a *StandUp*: the tools it serves and the tools it skipped, with a `notice` naming those), then starts it (`ensure_running`); a server whose process the install runs in (`runs_this_process`) is not started again. harness/mcp (*McpInstallation*, whose server is the cdd server) and harness/hooks (*HookInstallation*, which holds no server, because its hook command starts the hook server itself) each register theirs with `SERVER_CHANNELS.register(kind)` (*ServerChannels*, the process's one list of registered channels) when they are imported, the same way space/session registers with `SESSION_OPENING.open_with`, so this module never imports them and a new channel is one more registration. The Installer makes each registered channel with its factory, `kind.create(target, record, repository)`, so a channel whose server needs collaborators, as the cdd server's *ServedCheckout*, is handed them; `kind.into(target, repository)` makes one with its own record. A registered channel can also name toolsets every install publishes (`toolsets`), such as the hooks that start the cdd server. An install in a process where no channel registered stops with *ServersNotRegistered*; `scripts/install.py` imports both.
The install record (`record`, *InstallRecord*) is `.install-state.json` in the IDE folder: the IDE, the folder's whole path, and the files the last install into that folder wrote. Each folder keeps its own, so an install into another folder, or for another IDE, leaves this one's files known to its clean. The record is saved as each file is written, so an install that stops halfway still lists what it wrote. A record that cannot be read stops the install and the clean with *InstallRecordUnreadable* rather than being written over, so no installed file is forgotten. *LastInstall* (`last_install`) is the one file beside the installer that names the IDE and folder the checkout last installed into, where an install that names neither goes; it lists no files, and an install into a temporary folder is not remembered. A CDD before this kept the last install's files in that one file, and the first install or clean hands them to the folder's record (`hand_over_to`). One install or clean runs in an IDE folder at a time: the installer's *InstallLock* (`lock`, the file `.install-lock`, a *LockFile* of harness/process held for the process that installs) makes a second say what it waits for and how long, wait for the first, and refuses it with *InstallAlreadyRunning* when the first outlasts the wait. Taking the lock is one step of the operating system, which gives it back when its process ends, so a stopped install leaves the file but no held folder. harness/mcp holds one on the cdd home while it publishes the mods. `install_self` (`scripts/install.py --self`) adds the Installer's own commands to the last install and removes none of it; `write_language_adapters()` writes the TypeScript language adapters alone. `diagnostics` is the install's `diagnostics.json` (*InstallDiagnostics*): `write_section(section, results)` adds one section coloured by its worst result, which is how the diagnostics probes report. Each run ends by diagnosing what it deployed: *Deployed* is what the folder holds on each channel (`Deployed.of_folder(target, toolsets, published)`, `items(channel)`, `CHANNELS`), *DeployedChanges* is what changed since the last install (`changes_since(last)`: `added`, `removed`, and the `colour` of how much changed), and *InstallDiagnosis* holds both with the status each registered channel reports (`colour`, `is_red`, `report`). The Installer makes it (`diagnosis_of(channels, published)`), `InstallDiagnostics.record(diagnosis)` appends it to the history, `last_deployed()` reads the last install's back, and a red one is printed with how to diagnose it (`red_report`). An install that fails names the toolset and its cause (*ToolsetInstallFailed*).
*RepositoryToolsets* finds every toolset class in one repository by reading its source, and puts the folders that load them on the import path; the Installer, the hook server, and the MCP host each read the repository this way, so all three publish the same toolsets. Its `IMPORT_FOLDERS` is the one list of a checkout's import folders: the cdd server's environment (*CddHome*) and the catalog generator take `pythonpath()` from it, and *ToolsetReference* searches the import path it sets. `references()` answers a *ToolsetReference* to each toolset without importing anything, finding a class by the names an author types for the annotation kinds that make a member installable (`annotation_kinds.installing_names`, so a new kind is found as soon as its publisher is imported); a reference is written as its `module:Class` text only where it crosses a process boundary (`hook-handlers.json`, the cdd server's `--toolsets`). `classes()` imports each module and answers the classes, keeping each one that cannot be loaded in `unloadable` (*ToolsetUnloadable*) so every reader decides whether to stop or serve the rest. Importing every module this way also makes the registrations those modules make hold, as the hook server needs. The checkout this code was imported from, the code a hook server or a probe runs, is `RUNNING_CHECKOUT`, the one place that works it out from where the framework sits; a reader makes `RepositoryToolsets(RUNNING_CHECKOUT)`. The repository also names the folders its guidance is kept in (`GUIDANCE_FOLDER`, `agents_folder`, `standing_rules_folder`, `references_folder`); the Installer and each *Installation* (`repository`) ask it rather than spell `cdd_guidance` themselves.
A member's destination is chosen with an annotation on it: `@skill`, `@command("name")`, `@rules` (defined here; `@skill` and `@command` are *NamedDestination*s, whose annotation may name what it installs), `@mcp` (harness/mcp), or `@hook("event")` (harness/hooks); each is a *Destination* from harness/annotations. A member with no destination annotation stays in-process. `@noDeploy` (harness/annotations) keeps a member out of every destination, and `@noCatalog` (harness/annotations) keeps it out of the generated catalog without changing what is installed. `data_of` takes any value an answer sends (*SentValue*: a plain value, a path, an enum, a mapping or sequence of them, or an object of a class that describes its data), and a *DataClass* is generic in the class it describes, so its `data` and `reference` take an instance of that class.
*ContextConfig* is a project's `.context/config.json` (`CONTEXT_FOLDER` names the `.context` folder once): the guidelines that apply to file patterns, which the hook server reads to decide whether a pattern's hooks run, and the folder each practice writes in, which a session reads. It lives here, below harness/hooks, because the hook server is its lowest reader and no module below the hooks owns a project's `.context/` folder; this module is the one that reads and writes a project's CDD configuration files. *JsonFile* is one file holding a JSON object, read and written whole by its owner: `.context/config.json`, an install's `diagnostics.json` and `.install-state.json`, and the hook files each hold one, and each owner names its own kind of *JsonFileUnreadable*, so a file a person wrote is never saved over (decision record 0001). A change that reads the file and writes it back holds it for that change (`with file.held():`), through a *LockFile* (harness/process) beside the file, one per hold, so a change another thread or process makes to the same file waits its turn and none is lost; a wait that outlasts the hold's time limit raises *JsonFileBusy*, a *LockFileHeld*. *AppPorts* reads an app's `ports.json` through it once (`of(server)`), the one file the app's own servers read: the graph app (`GRAPH_APP_PORTS`) and the session board (`BOARD_APP_PORTS`) each make one, so a port is written once, and the *App* each registers (harness/diagnostics) takes its server's ports from it.
*Installation* writes one destination's files through the install's *InstallPlace*, so every channel of one install reads one layout and keeps one record. `is_temporary(folder)` is the one test of an install into the system's temporary folder, as a spec's is; such an install keeps its MCP entry in the folder (`InstallPlace.is_temporary`) and is not remembered as the checkout's last install. *IdeLayout* is one IDE's folder layout (where its skills, commands, prompts, rules, and user-level MCP config go, and the rule file's extension), so a new IDE is one more layout rather than an `ide ==` test in every writer. `installed_guidance_kind(path)` (each layout's `guidance_kind_of`) says whether a path lies in a folder an install writes skills, rules, or agents into, in any IDE's folder, for the hooks that log or toast a file.
`@language_adapter(language="typescript")` on a toolset class publishes its `@mcp` operations as typed TypeScript, so an application outside Python calls the same tools as typed objects; `shares_file_views=True` marks the toolset whose client the shared file views read files through (the file manager's). `@identity(...)` on a class names the data fields that name one of its objects, the ones a tool loads it by. `@data_field` under `@property` annotates a property as part of the object's data, and `@data_field(reference=True)` sends the object it holds by its identity alone, so data can name an object that is sent in full elsewhere; `@data_fields` on a dataclass makes every field it declares its data, typed as declared, for a record such as a board element whose fields are what it is, and a property it annotates `@data_field` joins them; a string of a kind of its own, such as an element id, is typed a string; `@edits("field")` names the field an operation changes when its argument is called something else, and *SourceFile* annotates a field that holds a path in the session's workspace. `@language_adapter`, `@identity`, `@edits`, `@data_field`, `@data_fields` and *SourceFile* are *Annotation* kinds, registered with the others, and live with *DataClass* and `data_of` in `data_class.py`; `destination.py` keeps the *InstallPlace* and *Installation* bases, *RegisteredChannel* with its *ChannelServer* and *StandUp*, and the tools a server skipped. `data_of(value)` is the one way an object becomes JSON data, for every MCP answer and every language adapter type alike; each class holds its *DataClass* (`DataClass.of`), read once. Beside the generated classes, the shared TypeScript names the project a page shows: `projectOfPage` reads its `?project=` link and `PROJECT_HEADER` carries it on every call (`cdd-shared.ts`), and an app server keeps one cdd connection per project the calls name (`ProjectConnections`, `cdd-connection.ts`), so each call works in the session open in that project; the CDD Kanban and the Graph app both serve every repository this way.

- **Purpose:** Install one repository into one IDE folder through every channel, from one walk of the repository, and start the servers that install points at; give every channel the annotations, the data, and the writer it publishes a member with.
- **Seam (terms):** Installer (`install`, `clean`, `diagnose_install`, `install_self`, `write_language_adapters`, `repository_toolsets`, `diagnosis_of`, `red_report`, `last_run`, `toolsets`, `record`, `diagnostics.write_section`), InstallRun (`run`, `publish`, `stand_up`, `ensure_running`, `channels`, `diagnosis`), ServerChannels (`SERVER_CHANNELS.register`), InstallChannels (`registered`, `files`, `rules`, `language_adapters`, `servers`, `published`, `deployed`, `toolsets`, `of(kind)`, `for_tool(tool)`), Deployed, DeployedChanges, InstallDiagnosis, InstallDiagnostics (`record`, `last_deployed`, `write_section`, `installed_items`), ToolsetInstallFailed, ServersNotRegistered, InstallRecord, InstallRecordUnreadable, LastInstall, InstallLock, InstallAlreadyRunning, UnknownIde, NotAnInstallFolder, RepositoryToolsets (`references`, `classes`, `unloadable`, `pythonpath`, `ensure_import_path`, `IMPORT_FOLDERS`, `GUIDANCE_FOLDER`, `agents_folder`, `standing_rules_folder`, `references_folder`), `RUNNING_CHECKOUT`, ToolsetUnloadable, ContextConfig, MalformedContextConfigError, JsonFile (`held()`), JsonFileUnreadable, JsonFileBusy, AppPorts, `CONTEXT_FOLDER`, InstallPlace (`into`, `wrote`, `folder_for`), Installation (`destination`), RegisteredChannel (`create`, `into`, `accepts`, `published`, `write_once_recorded`, `status`, `server`), ChannelServer (`stand_up`, `ensure_running`, `runs_this_process`), StandUp, FileInstallation, SkillInstallation, CommandInstallation, RulesInstallation (`write_standing_rule`), IdeLayout, InstallTarget, LanguageAdapters, SourceFile, DataClass, `is_temporary`; the annotations `@skill`, `@command`, `@rules`, `@language_adapter`, `@identity`, `@data_field`, `@data_fields`, `@edits`; `data_of(value)`; `/install`, `/clean`; `python scripts/install.py`
- **Dependencies (one-way):** harness/agent_tools, harness/annotations, harness/markdown, harness/process (*LockFile*, which *InstallLock* and `JsonFile.held` are). harness/hooks and harness/mcp import this module and register their channels with the Installer; it imports neither. harness/diagnostics imports it.

## Constraint

Change installed files only by changing the annotated source and installing again; `.claude/`, `.cursor/`, `.github/`, `.mcp.json`, and the `cdd` entry in `~/.claude.json` are overwritten on every install. Name the repository on every *Installer* you make. Install into an IDE folder that exists: when *LastInstall* names a folder that is gone, the install goes to `{repo}/.cursor`. Put the destination annotation on the member, never in a list on the toolset, so moving a member moves its publication with it. Read the repository's toolsets and import path through *RepositoryToolsets*, so every reader skips the same folders; code that only needs those does not make an Installer. Import this package as `harness.installation`, and leave `harness/` off `PYTHONPATH`, so `import mcp` loads the MCP SDK.
