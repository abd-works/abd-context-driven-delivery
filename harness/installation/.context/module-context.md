# harness/installation
*Installer* publishes every annotated toolset member in one repository into an IDE's folder (`.claude`, `.cursor`, `.github`, Kilo), so an author never writes a skill, command, rules file, MCP entry, or hook entry by hand. A person runs it as `/install`, or `python scripts/install.py --ide Claude`, and `/clean` removes what it wrote. It is made for the repository it installs (`Installer(ide, path, repo=...)`, or `Installer.load(project=...)` for the project a call names), never for the checkout its own code sits in, because one server installs many projects. It loads the repository's toolset classes with *RepositoryToolsets* and writes each member through the installations of one run (*InstallChannels*, made once per run): a *FileInstallation* for each file channel, the *LanguageAdapterInstallation*, and one installation of every server channel registered with it. Then it stands each server up to check it loads and starts it, so a finished install answers at once.
A server channel is a *ServerInstallation*: its files point the IDE at a server process, so beside writing them it stands the server up, starts it (`ensure_running`), reports it (`status`), and names what it published. harness/mcp (*McpInstallation*, the cdd server) and harness/hooks (*HookInstallation*, the hook server) each register theirs with `Installer.installs_through(kind)` when they are imported, the same way space/session registers with `ToolCall.open_sessions_with`, so this module never imports them and a new server channel is one more registration. A server channel can also name toolsets every install publishes, such as the hooks that start the cdd server. An install in a process where no server channel registered stops with *ServersNotRegistered*; `scripts/install.py` imports both.
The install record (`record`) is the list of files the last install wrote; a record that cannot be read stops the install and the clean with *InstallRecordUnreadable* rather than being written over, so no installed file is forgotten. `diagnostics` is the install's `diagnostics.json` (*InstallDiagnostics*): `write_section(section, results)` adds one section coloured by its worst result, which is how the diagnostics probes report; it also diagnoses an install from the *InstallChannels* of its run (`deployed`, `diagnosed`, `record_run`), which hold what the run deployed. An install that fails names the toolset and its cause (*ToolsetInstallFailed*).
*RepositoryToolsets* finds every toolset class in one repository by reading its source, and puts the folders that load them on the import path; the Installer, the hook server, and the MCP host each read the repository this way, so all three publish the same toolsets. Its `IMPORT_FOLDERS` is the one list of a checkout's import folders: the cdd server's environment (*CddHome*) and the catalog generator take `pythonpath()` from it, and *ToolsetReference* searches the import path it sets. `references()` answers a *ToolsetReference* to each toolset without importing anything, finding a class by the names an author types for the annotation kinds that make a member installable (`annotation_kinds.installing_names`, so a new kind is found as soon as its publisher is imported); a reference is written as its `module:Class` text only where it crosses a process boundary (`hook-handlers.json`, the cdd server's `--toolsets`). `classes()` imports each module and answers the classes, keeping each one that cannot be loaded in `unloadable` (*ToolsetUnloadable*) so every reader decides whether to stop or serve the rest. Importing every module this way also makes the registrations those modules make hold, as the hook server needs. The repository also names the folders its guidance is kept in (`GUIDANCE_FOLDER`, `agents_folder`, `standing_rules_folder`, `references_folder`); the Installer and each *Installation* (`repository`) ask it rather than spell `cdd_guidance` themselves.
A member's destination is chosen with an annotation on it: `@skill`, `@command("name")`, `@rules` (defined here), `@mcp` (harness/mcp), or `@hook("event")` (harness/hooks); each is a *Destination* from harness/annotations. A member with no destination annotation stays in-process. `@noDeploy` keeps a member out of every destination, and `@noCatalog` keeps it out of the generated catalog without changing what is installed.
*ContextConfig* is a project's `.context/config.json` (`CONTEXT_FOLDER` names the `.context` folder once): the guidelines that apply to file patterns, which the hook server reads to decide whether a pattern's hooks run, and the folder each practice writes in, which a session reads. It lives here, below harness/hooks, because the hook server is its lowest reader and no module below the hooks owns a project's `.context/` folder; this module is the one that reads and writes a project's CDD configuration files. *JsonFile* is one file holding a JSON object, read and written whole by its owner: `.context/config.json`, an install's `diagnostics.json` and `.install-state.json`, and the hook files each hold one, and each owner names its own kind of *JsonFileUnreadable*, so a file a person wrote is never saved over (decision record 0001). *AppPorts* reads an app's `ports.json` through it once (`of(server)`), the one file the app's own servers read: the graph app (`GRAPH_APP_PORTS`) and the session board (`BOARD_APP_PORTS`) each make one, so a port is written once, and the *App* each registers (harness/diagnostics) takes its server's ports from it.
*Installation* writes one destination's files, made with the install's *IdeLayout*, so every channel of one install reads one layout. `is_temporary(folder)` is the one test of an install into the system's temporary folder, as a spec's is; such an install keeps its record and its MCP entry in the folder (`Installation.is_temporary`). *IdeLayout* is one IDE's folder layout (where its skills, commands, prompts, rules, and user-level MCP config go, and the rule file's extension), so a new IDE is one more layout rather than an `ide ==` test in every writer. `IdeLayout.installed_guidance_kind(path)` says whether a path lies in a folder an install writes skills, rules, or agents into, in any IDE's folder, for the hooks that log or toast a file.
`@language_adapter(language="typescript")` on a toolset class publishes its `@mcp` operations as typed TypeScript, so an application outside Python calls the same tools as typed objects; `shares_file_views=True` marks the toolset whose client the shared file views read files through (the file manager's). `@identity(...)` on a class names the data fields that name one of its objects, the ones a tool loads it by. `@data_field` under `@property` annotates a property as part of the object's data, and `@data_field(reference=True)` sends the object it holds by its identity alone, so data can name an object that is sent in full elsewhere; `@edits("field")` names the field an operation changes when its argument is called something else, and *SourceFile* annotates a field that holds a path in the session's workspace. `@language_adapter`, `@identity`, `@edits`, `@data_field` and *SourceFile* are *Annotation* kinds, registered with the others, and live with *DataClass* and `data_of` in `data_class.py`; `destination.py` keeps the omission annotations, the *Installation* bases, and the tools a server skipped. `data_of(value)` is the one way an object becomes JSON data, for every MCP answer and every language adapter type alike; each class holds its *DataClass* (`DataClass.of`), read once. Beside the generated classes, the shared TypeScript names the project a page shows: `projectOfPage` reads its `?project=` link and `PROJECT_HEADER` carries it on every call (`cdd-shared.ts`), and an app server keeps one cdd connection per project the calls name (`ProjectConnections`, `cdd-connection.ts`), so each call works in the session open in that project; the CDD Kanban and the Graph app both serve every repository this way.

- **Purpose:** Install one repository into one IDE folder through every channel, from one walk of the repository, and start the servers that install points at; give every channel the annotations, the data, and the writer it publishes a member with.
- **Seam (terms):** Installer (`install`, `install_self`, `clean`, `ensure_runtimes`, `diagnose_install`, `toolsets`, `record`, `diagnostics.write_section`, `Installer.installs_through`), InstallChannels (`of(kind)`, `toolsets`), ToolsetInstallFailed, ServersNotRegistered, InstallRecordUnreadable, RepositoryToolsets (`references`, `classes`, `unloadable`, `pythonpath`, `ensure_import_path`, `IMPORT_FOLDERS`, `GUIDANCE_FOLDER`, `agents_folder`, `standing_rules_folder`, `references_folder`), ToolsetUnloadable, ContextConfig, MalformedContextConfigError, JsonFile, JsonFileUnreadable, AppPorts, `CONTEXT_FOLDER`, Installation, ServerInstallation, FileInstallation, IdeLayout, LanguageAdapterInstallation, SourceFile, DataClass, `is_temporary`; the annotations `@skill`, `@command`, `@rules`, `@noDeploy`, `@noCatalog`, `@language_adapter`, `@identity`, `@data_field`, `@edits`; `data_of(value)`; `/install`, `/clean`; `python scripts/install.py`
- **Dependencies (one-way):** harness/agent_tools, harness/annotations, harness/markdown. harness/hooks and harness/mcp import this module and register their server installations with the Installer; it imports neither. harness/diagnostics imports it.

## Constraint

Change installed files only by changing the annotated source and installing again; `.claude/`, `.cursor/`, `.github/`, `.mcp.json`, and the `cdd` entry in `~/.claude.json` are overwritten on every install. Name the repository on every *Installer* you make. Install into an IDE folder that exists: when the install record names a folder that is gone, the install goes to `{repo}/.cursor`. Put the destination annotation on the member, never in a list on the toolset, so moving a member moves its publication with it. Read the repository's toolsets and import path through *RepositoryToolsets*, so every reader skips the same folders; code that only needs those does not make an Installer. Import this package as `harness.installation`, and leave `harness/` off `PYTHONPATH`, so `import mcp` loads the MCP SDK.
