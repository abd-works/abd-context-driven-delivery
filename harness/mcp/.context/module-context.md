# harness/mcp
*Mcp* publishes an operation to every chat as a tool of the one `cdd` MCP server: the author types `@mcp` on an `@agent_tool` operation, and an `@agent_instructions` member is published as a prompt whose call answers with its instructions. The tool's name is the toolset's kebab name and the member's name (`ticket.move_next`). `@long_call` on an operation that may take minutes (a graph build, a git push, a diagnostics run) gives it the long time limit, so the operation says how long it takes rather than a list of names in the server. Both annotations live in `harness.mcp.mcp_annotations`, which loads no MCP SDK, so a toolset that only annotates its operations stays quick to import; the server module imports it, so importing the server defines the `@mcp` channel install reads.
*McpHost* is that server: one process on this machine that every chat in every project talks to over HTTP at `127.0.0.1:47800/mcp`. Each request names its chat's project in the `X-CDD-Project` header, and *McpHost* keeps one *McpServer* — that project's enrolled toolsets — per project, so state a toolset keeps between calls never crosses between chats. A call without that header fails with *ProjectNotNamed*, and a tool no toolset publishes with *ToolNotEnrolled*. A tool that raises answers the chat as an error (`isError`), naming the error, never as an ordinary result. `cdd.ping` and `cdd.restart` are always published; `cdd.restart` reloads the server's Python in place for every chat. Each request becomes one *ToolCall* that carries the host answering it, so code running inside a call reaches the host through `call.mcp_host`.
*McpInstallation* writes the IDE's `cdd` entry, so a chat knows the server's address and how to name its project, and records which operations the server publishes. It is the MCP channel's *ServerInstallation*: it holds the *McpDaemon* of its *CddHome*, starts the server (`ensure_running`, which for Claude Code also installs the cdd and board plugins through *ClaudePlugins*), reports it, and names *CddServerHooks*, the hooks that start the server when a chat starts, as a toolset every install publishes; this module registers it with `Installer.installs_through` when it is imported. *McpDaemon* finds, starts, and stops the server process for one *CddHome* (`ensure_from(checkout)`, `pin_from`, `serve_checkout`), and its `ping()` answers the *RunningServer* it finds, which holds that server's process, so an install or a chat's connect step can start it when none answers. *CddHome* is the server's install folder, `~/.cdd/`: which checkout the server runs and the pinned copy of it, so installing from one worktree does not repoint every open chat; a `runtime.json` it cannot read raises *RuntimeRecordUnreadable* rather than being pinned over. It publishes the board mod with `install.json`, the command the mod's Run install runs (`install_command`: the served checkout's `scripts/install.py --from-chat` on the server's Python), so the mod never reads `runtime.json` itself.

- **Purpose:** Let any chat, in any project, call the operations authors annotate `@mcp`, through one long-running server that keeps each project's toolsets apart.
- **Seam (terms):** Mcp, McpHost (`McpHost.from_repo(repo)`, `McpHost.from_refs(refs, ...)`, `dispatch(name, arguments, project)`, `checkout_server`), McpServer, McpInstallation, McpDaemon, RunningServer, CddHome, CddServerHooks, ClaudePlugins, ProjectNotNamed, ToolNotEnrolled, RuntimeRecordUnreadable, ThrottledReporter; the annotations `@mcp` and `@long_call`; the MCP operations `cdd.ping` and `cdd.restart`; `python -m harness.mcp`
- **Dependencies (one-way):** harness/agent_tools (*ToolCall*: each request becomes `ToolCall.sent(arguments, project, tool=..., mcp_host=...)`, which carries the project and the chat the request came from to the tool and to the session it logs in), harness/annotations (*Destination*, *Annotation*), harness/installation (*ServerInstallation*, *Installer*, which this module registers *McpInstallation* with, *IdeLayout*, *RepositoryToolsets*, `data_of`), harness/hooks (`@hook`, on *CddServerHooks*), harness/process (*BackgroundStart*, *PythonInterpreter*, *StoppableProcess*, and *Git*, which copies a checkout into the pinned runtime). It imports nothing above the framework.

## Constraint

Publish an operation by putting `@mcp` on it; nothing else is enrolled, so a member without the annotation stays in-process. Run the server only as `python -m harness.mcp` from the checkout it serves, or let `McpDaemon` start it; a second start exits because the first one holds the port. Change which code serves every chat only with `python scripts/install.py` from the main checkout (a plain install pins its commit when the server is pinned to an older one), `--pin-runtime`, or `--serve-from-checkout`, never by starting another server. A tool reads its project and the session open there from its *ToolCall*, never from what the process worked on last. Code that runs outside a call, such as a script or a spec, names its project on `McpHost.dispatch(name, arguments, project)`. Leave `harness/` off `PYTHONPATH`, so `import mcp` loads the MCP SDK and not this package.

A tool runs on a worker thread, which cannot be stopped. The host makes each chat's call with `answers_a_chat` set (`ToolCall.answers_a_chat`), and work that call starts that would hold the interpreter for minutes, such as a graph build, runs in a worker process instead: every chat shares the server's one interpreter. A call made in process (`McpHost.dispatch`) answers no chat. A tool's progress reaches its chat at most four times a second (*ThrottledReporter*), and `cdd.ping` answers on the event loop itself. A call still running at its time limit (10 seconds; ten minutes for an operation annotated `@long_call`) keeps running: its caller is told it is still running, an identical call (same tool, project, arguments, and chat) waits for that run instead of starting another, and the result is kept for ten minutes for the next identical call to collect. A run that fails after its caller stopped waiting is logged. On Windows the server keeps accepting connections when a caller hangs up before it is accepted (`WinError 64`); any other accept failure stops the server, so the next connect starts a fresh one.
