# harness/mcp
*Mcp* publishes an operation to every chat as a tool of the one `cdd` MCP server: the author types `@mcp` on an `@agent_tool` operation, and an `@agent_instructions` member is published as a prompt whose call answers with its instructions. The tool's name is the toolset's kebab name and the member's name (`ticket.move_next`). `@long_call` on an operation that may take minutes (a graph build, a git push, a diagnostics run) gives it the long time limit, so the operation says how long it takes rather than a list of names in the server. Both annotations live in `harness.mcp.mcp_annotations`, which loads no MCP SDK, so a toolset that only annotates its operations stays quick to import; the server module imports it, so importing the server defines the `@mcp` channel install reads. The server module itself loads the SDK only when *McpHost* first speaks MCP to a chat, so making a server, enrolling its tools, and dispatching a call in-process (a probe, a script, a spec) never pay the seconds the SDK takes to import.
*McpHost* is that server: one process on this machine that every chat in every project talks to over HTTP at `127.0.0.1:47800/mcp`. The host makes one *ChatRequest* for each request a chat sends, from its headers and the port the caller's end of its connection uses: `process` is the Claude Code process the request comes from, `chat` the chat (*ChatPointer*), `project_for(tool)` the project a call works on, and `tool_request(tool, host)` the *ToolRequest* the call answers. The host makes each *ChatRequest* from its module as it is now, so after `cdd.restart` a request names chats and calls with the classes the re-imported tools know. Each call names its project from the Claude Code chat it comes from: the folder Claude Code records for the process holding the request's connection (or the one `X-CDD-Chat-Process` names), read on every call, else the `X-CDD-Project` header, which a client that is not a Claude Code chat sends, such as Cursor or an app server. *McpHost* keeps one *ProjectToolsets* — that project's enrolled toolsets — per project, so state a toolset keeps between calls never crosses between chats. A host serving chats is made with the two lanes and its cdd home (`McpHost(checkout_toolsets, lanes, home)`, which `python -m harness.mcp` passes through `from_repo`), so it hands a call whose project runs on the other lane to that lane; a host made in process for a probe or a spec has neither. A request is never refused for naming no project: the Claude Code plugin declares the server's address alone, because a headers helper has about ten seconds while a chat starts and one that ran past them cut its chat off from cdd. A call whose project neither names fails with *ProjectNotNamed*, and a tool no toolset publishes with *ToolNotEnrolled*. A tool that raises answers the chat as an error (`isError`), naming the error, never as an ordinary result. `cdd.ping` and `cdd.restart` are always published; `cdd.restart` reloads the server's Python in place for every chat. Each request becomes one *ToolCall* that carries the host answering it, so code running inside a call reaches the host through `call.request.mcp_host`.
*McpInstallation* records which operations the server publishes and writes the IDE's `cdd` entry through its *CddEntry* (`installation.cdd_entry`: its `path`, `write()`, and `point_chats_at_served_lane()`, which a full install and every `--pin-runtime`, `--update`, or `--serve-from-checkout` run: on the dev lane it writes the worktree's `.mcp.json` `cdd` entry naming the dev lane's server, on the stable lane it drops that entry), so a chat knows the server's address and how to name its project. It is the MCP channel's *RegisteredChannel* (its `destination` is `Mcp`): it is made with the install's *InstallTarget* and *InstallRecord* and the *ServedCheckout* the server is installed from (`McpInstallation(target, record, served)`; `installation.served`, whose stable lane's *McpDaemon* is `installation.daemon`), by `McpInstallation.create(target, record, repository)`, the factory the Installer makes every registered channel with. It records each `@mcp` operation, writes the IDE's `cdd` entry once every tool is recorded (`write_once_recorded`), and reports whether the server runs (`status`). Its server is *McpChannelServer* (`installation.server`), the cdd server as an install handles it: `stand_up()` loads every toolset of the served checkout in the install's process to check it loads and answers a *StandUp*, `ensure_running()` starts the server when none answers (and for Claude Code installs the `cdd` plugin and, through `install_mods()`, every mod the served code declares, each through *ClaudePlugins*' `install(plugin)`, which answers a *PluginInstall*: installed, watched, or missing, reported as `{plugin name}: {state}`; a plugin Claude Code watches through `CLAUDE_CODE_PLUGIN_DIRS` needs no install, and one installed from a checkout's own marketplace, `abd-works`, is replaced), and `runs_this_process` is true when the install runs inside the cdd server, which then stands up and starts nothing. The installation names *CddServerHooks*, the hooks that start the server when a chat starts (each hook loads them with `CddServerHooks.load()`, which hands them the running checkout's *ServedCheckout*), as a toolset every install publishes; this module registers it with `SERVER_CHANNELS.register` (harness/installation) when it is imported. *McpAddress* is where the server answers and the headers a request names its chat with (`url`, `ping_answer`), and hands a call to the other lane's server (`send_lane_call(call, seconds)`, which takes any call that writes itself as JSON, a *SentCall* such as *ToolCall* with its `as_sent()`, and answers a *LaneReply*: the answer, or the failure by its kind and message); it is kept to the standard library so the connect script finds a running server without loading the framework. The receiving server reads the call back with `ToolCall.from_sent(sent, host)`. *McpDaemon* finds, starts, and stops the server process for one *CddHome* (`McpDaemon(home, address)`), a *ServerDaemon* (harness/process), and its *ServedCheckout* switches the server onto one checkout's code (`ensure`, `pin`, `update`, `serve_on_disk`, `keep_pinned_current`) and copies the language adapters an install wrote into the pinned runtime (`take_language_adapters(written, ide_folder)`), since git never copies them there and the apps the server launches import the CDD domain through them; its `running()` answers the *RunningServer* it finds, which holds that server's process, so an install or a chat's connect step can start it when none answers. Its *ServingProcess* (`McpDaemon.this_process`) is the server as the process that runs it: it claims the port, publishes the address tools look for, withdraws it when it ends, and ends with the process `CDD_SERVER_OWNER` names. *CddHome* is the server's install folder, `~/.cdd/`: which checkout the server runs and the pinned copy of it, so installing from one worktree does not repoint every open chat, and the server's own files; a `runtime.json` it cannot read raises *RuntimeRecordUnreadable* rather than being pinned over. The Claude Code marketplace it publishes is its own object, *ClaudeMarketplace* (`home.marketplace`, its `claude-plugins` folder). The marketplace publishes the `cdd` plugin (`publish_cdd_plugin(server)`, `cdd_plugin`), which declares the server's address and a chat-start hook that runs `connect.py --start` to start a server that is not running, versioned by a hash of both so Claude Code takes a changed one. It publishes the mods of the code the server runs (`publish_mods(code)`, and `publish_mods_for_chats(is_dev_lane_running)` when a server restarts, which also publishes the dev lane's mods into the stable lane's marketplace that chats install from). A mod declares itself with a `cdd-mod.json` file beside its `.claude-plugin` folder, naming its plugin, the files of the checkout it carries besides its own, and the file its Run install command is written to; *PublishedMods* finds those declarations in the code being published, each a *PublishedMod*, so this module names no folder of harness/chat-ui or tools/, and a pinned server publishes the mods its own code declares. *PublishedPlugin* is one plugin of the marketplace by its name and the one owner of its `{name}/.claude-plugin/plugin.json`: its `manifest`, `version`, `description`, `installed_name` (`{name}@cdd-home`), and `publish_from(mod)`, which copies the mod and versions it by a hash of its files so Claude Code takes a changed one. A mod that runs an install gets that command written into its folder (`ClaudeMarketplace.INSTALL_COMMAND`, `install.json`; `install_command`: the served checkout's `scripts/install.py --from-chat` on the server's Python), so the mod never reads `runtime.json` itself. One install at a time publishes into the marketplace: it holds harness/installation's *InstallLock* while it copies the mods, so an install from the main checkout and one from a ticket's worktree at the same moment both finish.

- **Purpose:** Let any chat, in any project, call the operations authors annotate `@mcp`, through one long-running server that keeps each project's toolsets apart.
- **Seam (terms):** Mcp, McpHost (`McpHost.from_repo(repo, lanes, home)`, `McpHost.from_refs(refs, ...)`, `dispatch(name, arguments, project)`, `checkout_toolsets`), ProjectToolsets (`start(toolsets)`, each a *ToolsetReference*), ChatRequest, McpInstallation, McpChannelServer, CddEntry, McpDaemon, ServedCheckout, McpAddress, CddHome, ClaudeMarketplace, PublishedPlugin, PublishedMods, CddServerHooks, ClaudePlugins, PluginInstall, ProjectNotNamed, ProjectIsClaudeSettings, ToolNotEnrolled, RuntimeRecordUnreadable, ThrottledReporter; the annotations `@mcp` and `@long_call`; the MCP operations `cdd.ping` and `cdd.restart`; `python -m harness.mcp`
- **Dependencies (one-way):** harness/agent_tools (*ToolCall*: each request becomes `ToolCall.sent(arguments, project, request)`, where the request is the *ToolRequest* its *ChatRequest* makes, `ToolRequest(chat, tool, host, answers_a_chat=True)`, which carries the project and the chat the request came from to the tool and to the session it logs in), harness/annotations (*Destination*, *Annotation*), harness/installation (*RegisteredChannel*, *ChannelServer*, *StandUp*, *Installer*, which this module registers *McpInstallation* with, *IdeLayout*, *RepositoryToolsets*, *InstallLock*, `data_of`), harness/hooks (`@hook`, on *CddServerHooks*), harness/process (*ServerDaemon*, *RunningServer*, *PythonInterpreter*, *RunningProcess*, *ExclusivePort*, *ClaudeChatProcess*), harness/git (*Git*, which copies a checkout into the pinned runtime). It imports nothing above the framework.

## Constraint

Publish an operation by putting `@mcp` on it; nothing else is enrolled, so a member without the annotation stays in-process. Run the server only as `python -m harness.mcp` from the checkout it serves, or let `McpDaemon` start it; a second start exits because the first one holds the port. Change which code serves every chat only with `python scripts/install.py` from the main checkout (a plain install pins its commit when the server is pinned to an older one), `--pin-runtime`, `--serve-from-checkout`, `--restart-everything` (stop every app's server and the hook server, restart the cdd server at once, install in full, ping), or `--from-latest` (fetch tags and merge the latest release, the newest `v*` tag, then `--restart-everything`), never by starting another server. `McpDaemon.stop` also stops a server that holds the port without answering, found by the port it listens on. A tool reads its project and the session open there from its *ToolCall*, never from what the process worked on last. Code that runs outside a call, such as a script or a spec, names its project on `McpHost.dispatch(name, arguments, project)`. Leave `harness/` off `PYTHONPATH`, so `import mcp` loads the MCP SDK and not this package.

A tool runs on a worker thread, which cannot be stopped. The host makes each chat's call with `answers_a_chat` set (`call.request.answers_a_chat`), and work that call starts that would hold the interpreter for minutes, such as a graph build or the drawing of a class diagram, runs in a worker process instead (*WorkerProcess*, harness/agent_tools): every chat shares the server's one interpreter. A call made in process (`McpHost.dispatch`) answers no chat. A tool's progress reaches its chat at most four times a second (*ThrottledReporter*), and `cdd.ping` answers on the event loop itself. A call still running at its time limit (10 seconds; ten minutes for an operation annotated `@long_call`) keeps running: its caller is told it is still running, in a sentence an agent reads and, beside it, as data (`structuredContent` `{"still_running": {"tool", "seconds"}}`), which is how a client such as a language adapter recognises the answer, since the sentence may be reworded; an identical call (same tool, project, arguments, and chat) waits for that run instead of starting another, and the result is kept for ten minutes for the next identical call to collect. A run that fails after its caller stopped waiting is logged. On Windows the server keeps accepting connections when a caller hangs up before it is accepted (`WinError 64`); any other accept failure stops the server, so the next connect starts a fresh one.
