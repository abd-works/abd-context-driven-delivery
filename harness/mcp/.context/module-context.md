# harness/mcp
*Mcp* publishes an operation to every chat as a tool of the one `cdd` MCP server: the author types `@mcp` on an `@agent_tool` operation, and an `@agent_instructions` member is published as a prompt whose call answers with its instructions. The tool's name is the toolset's kebab name and the member's name (`ticket.move_next`).
*McpHost* is that server: one process on this machine that every chat in every project talks to over HTTP at `127.0.0.1:47800/mcp`. Each request names its chat's project in the `X-CDD-Project` header, and *McpHost* keeps one set of toolsets per project, so state a toolset keeps between calls never crosses between chats. A call without that header fails with *ProjectNotNamed*. `cdd.ping` and `cdd.restart` are always published; `cdd.restart` reloads the server's Python in place for every chat. Code running inside a call finds the *McpHost* serving it with `serving_mcp_host()`.
*McpInstallation* writes the IDE's `cdd` entry, so a chat knows the server's address and how to name its project, and records which operations the server publishes. *McpDaemon* finds, starts, and stops the server process, so an install or a chat's connect step can start it when none answers. *CddHome* is the server's install folder, `~/.cdd/`: which checkout the server runs and the pinned copy of it, so installing from one worktree does not repoint every open chat.

- **Purpose:** Let any chat, in any project, call the operations authors mark `@mcp`, through one long-running server that keeps each project's toolsets apart.
- **Seam (terms):** Mcp, McpHost, McpInstallation, McpDaemon, CddHome, ProjectNotNamed; the mark `@mcp`; `serving_mcp_host()`; the MCP operations `cdd.ping` and `cdd.restart`; `python -m harness.mcp`
- **Dependencies (one-way):** harness/agent_tools, harness/marks (*Destination*), harness/installation (*Installation*, *RepositoryToolsets*, `data_of`), harness/process (the daemon starts and stops its process the way the hook server does), space/session (*ChatPointer*, the chat a call came from), space/work_state (each call still runs inside `working_on(project)` for space code that reads its project from there rather than from its call). Of these, only space/session imports this module back, so the two space imports are what keep it in a cycle (`.sessions/_backlog/break-module-dependency-cycles.md`).

## Constraint

Publish an operation by putting `@mcp` on it; nothing else is enrolled, so a member without the mark stays in-process. Run the server only as `python -m harness.mcp` from the checkout it serves, or let `McpDaemon` start it; a second start exits because the first one holds the port. Change which code serves every chat only with `python scripts/install.py --pin-runtime` or `--serve-from-checkout`, never by starting another server. Each call's runtime hands its tools the call's project as a *ToolCall* (`AgentTool.invoke(arguments, project=...)`), so a tool reads its project and the session open there from its call, never from what the process worked on last. Code that runs outside a call, such as a script or a spec, names its project on `McpHost.dispatch(name, arguments, project)` or `AgentTool.invoke(..., project=...)`. Leave `harness/` off `PYTHONPATH`, so `import mcp` loads the MCP SDK and not this package.

A tool runs on a worker thread, which cannot be stopped. A call still running at its time limit (10 seconds; longer for graph builds and repository commands) keeps running: its caller is told it is still running, an identical call (same tool, project, and arguments) waits for that run instead of starting another, and the result is kept for ten minutes for the next identical call to collect. On Windows the server keeps accepting connections when a caller hangs up before it is accepted (`WinError 64`); any other accept failure stops the server, so the next connect starts a fresh one.
