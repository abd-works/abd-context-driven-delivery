# harness/process
*BackgroundStart* starts a server that keeps running after the chat that started it, with no console window on Windows (`BackgroundStart(log).run(command, cwd, env)`, or its `creationflags` and `startupinfo` for a caller that starts the process itself); where the starter's Windows job refuses to let its children leave, as a chat's does, *Wmi* creates it through `Win32_Process.Create`, outside every job, running `outside_job_launcher.py`, which appends its output to the log. *PythonInterpreter* is the Python to start: `windowless` for a background server, `console` for a hook command whose JSON the IDE reads from stdout.
*RunningProcess* is a process on this computer by its id, asked whether it is still running (`alive`) and which ports it listens on (`listening_ports`), and stopped (`stop(wait_seconds)`), which waits for the process to exit or raises *ProcessNotStopped*; an id of 0 and this process's own id are never signalled. *LockFile*, *ServerDaemon*, and `scripts/instances.py` name processes this way. `started_at` is when the process started, as the operating system keeps it: the system gives an ended process's id to a later one, so a file that names a process keeps its id together with this time, as a test run's record does.
*StarterBoundJob* (`starter_bound_job.py`) holds the processes a starter starts to the starter's own life: each process it takes in (`take_in(process)`), and every process those start, is ended by Windows when the starter ends, however it ends, so no child goes on working in a folder the next starter believes is free. Windows refusing the job raises *JobNotMade*; outside Windows it holds nothing. The test runner (harness/release) puts a tier's `test.ps1` in one.
*ExclusivePort* is the one port a long-running server may hold, claimed by an exclusive bind (`claim()`); `holder()` names the *RunningProcess* holding it, so a server that finds its port taken can tell what took it. Which process listens on which port is read from Windows' TCP table, or `ss` elsewhere, by a helper private to the module that *ExclusivePort* and *RunningProcess* ask.
*LockFile* (`lock_file.py`) is a file the operating system locks for the one holder that claimed it, naming that holder's process at its start (`holder`): `claim()` waits up to its wait while another holder has it, then raises *LockFileHeld*, and `try_claim()` answers at once whether it took it; one holder may claim again, and the file is free once its first claim is given back; `held()` holds it for one piece of work. The operating system gives the lock back when its holder's process ends, however it ends, so a killed holder leaves the file but never a held lock. harness/installation's *InstallLock* and the lock beside a *JsonFile* are lock files, and so are a server's start lock and harness/release's claim on the record of test runs: every place that claims a file between processes uses this one class. Each holder makes its own *LockFile*, so two threads exclude each other as two processes do.
*ServerDaemon* (`server_daemon.py`) is the one model of a long-running server: a server that keeps running past the command that started it, on the one port it may hold (*ExclusivePort*), with its output in a *CappedLogFile*. `running()` asks it who it is and answers a *RunningServer* (its process, the folder it serves, the stamp of the code it loaded, the projects its chats worked on) or none; `ensure()` starts it when none answers, one start at a time through a start lock beside its log, and waits until it answers or raises *ServerDidNotStart* with the log's last lines; `stop()` stops the process that answers, else the one holding the port, since a server that holds its port without answering keeps every new one from claiming it; `restart()` stops and ensures. harness/hooks' *HookDaemon* and harness/mcp's *McpDaemon* are server daemons; each says how it is asked (`running`), run (`_command`, `_folder`, `_environment`), and named, and keeps what differs on purpose: the hook daemon's takeover of its port from older code, the cdd server's quiet second start.
*CappedLogFile* (`capped_log_file.py`) is a log file kept under a size (*LOG_SIZE_LIMIT_BYTES*, 4 MB): once it reaches it, `roll_when_full()` moves its lines to the previous file beside it (`server.log.1`), replacing an older one, so a log and its previous file never take much more than twice the size. The cdd server's and the hook daemon's output logs roll when they start, and a session's `session.log`, `session.err`, and hook logs before each line they write; a file another process holds open is left until the next write or start that finds it free, since Windows will not move it. Without it, logs written on every tool call or by a server that runs for weeks grew until they filled the disk.
*AnswerReads* (`answer_reads.py`, `ANSWER_READS`) counts the answers this process gives, so a value read from a file, such as a session's `session.json`, is read once for an answer however often that answer asks for it; *ServedAnswers* is the answers given from one checkout's sessions, none until a call finds those sessions, and *HeldForAnswer* holds one value for the answer it was read in. *LogTimestamp* (`log_timestamp.py`) is the one way every log the framework keeps stamps its times, a moment in UTC to the second, which a session's log, its hook logs, the board's last-activity times, the prompt log, the toasts, the violation history, and an accepted violation all use; `REPORT_DATE_FORMAT` beside it is the stamp a validation report's or a handoff's file name ends with.
The process classes live in one module, `process.py`, since each is a few lines about one process on this computer.
*ClaudeChatProcess* (`claude_chat_process.py`) is the Claude Code process a chat runs in, and the folder its session works in now, read from the session file Claude Code keeps for it; `from_ancestors()` finds it above the connect script, `from_header` and `from_connection` above a request to the cdd server. It uses only the standard library and harness/git's *Checkout* (itself standard library only), which answers the checkout holding the folder a chat works in, so the connect script, which runs inside the time Claude Code gives a headers helper, imports it without loading the framework.

- **Purpose:** Start, name, and stop the processes the framework keeps, the same way on Windows and elsewhere.
- **Seam (terms):** BackgroundStart, PythonInterpreter, ExclusivePort, RunningProcess, ProcessNotStopped, StarterBoundJob, JobNotMade, ClaudeChatProcess, CappedLogFile, LogTimestamp, `REPORT_DATE_FORMAT`, AnswerReads (`ANSWER_READS`), ServedAnswers, HeldForAnswer, LockFile, LockFileHeld, ServerDaemon, RunningServer, ServerDidNotStart, `is_desktop_spare`, `claude_config_folder`. The module is a toolkit, not one deep class: each class is a small tool for one job on this computer that its callers use directly, so every class is part of the seam by design, and a deep-module count that reads all of them as exposed reads the toolkit's purpose. A class added here is one more such tool. *ServerDaemon* is the one base class here, the shape every long-running server of the framework takes, built from the other tools (*ExclusivePort*, *CappedLogFile*, *LockFile*, *BackgroundStart*); the servers themselves live in the modules that serve, harness/hooks and harness/mcp.
- **Dependencies (one-way):** `harness/git` (*Checkout*, standard library only), so harness/hooks, harness/mcp, harness/installation, harness/agent_tools, harness/diagnostics, and the scripts all use it without depending on each other.

## Constraint

Start a background server with *BackgroundStart* and `PythonInterpreter().windowless`, and a hook command with `PythonInterpreter().console`: `pythonw.exe` drops stdout.
