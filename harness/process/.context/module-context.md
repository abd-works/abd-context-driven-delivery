# harness/process
*BackgroundStart* starts a server that keeps running after the chat that started it, with no console window on Windows (`BackgroundStart(log).run(command, cwd, env)`, or its `creationflags` and `startupinfo` for a caller that starts the process itself); where the starter's Windows job refuses to let its children leave, as a chat's does, *Wmi* creates it through `Win32_Process.Create`, outside every job, running `outside_job_launcher.py`, which appends its output to the log. *PythonInterpreter* is the Python to start: `windowless` for a background server, `console` for a hook command whose JSON the IDE reads from stdout.
*RunningProcess* is a process on this computer by its id, asked whether it is still running (`alive`) and which ports it listens on (`listening_ports`), and stopped (`stop(wait_seconds)`), which waits for the process to exit or raises *ProcessNotStopped*; an id of 0 and this process's own id are never signalled. The hook server's lock file, *HookDaemon*, *McpDaemon*, and `scripts/instances.py` name processes this way.
*ExclusivePort* is the one port a long-running server may hold, claimed by an exclusive bind (`claim()`); `holder()` names the *RunningProcess* holding it, so a server that finds its port taken can tell what took it. Which process listens on which port is read from Windows' TCP table, or `ss` elsewhere, by a helper private to the module that *ExclusivePort* and *RunningProcess* ask.
*CappedLogFile* (`capped_log_file.py`) is a log file kept under a size (*LOG_SIZE_LIMIT_BYTES*, 4 MB): once it reaches it, `roll_when_full()` moves its lines to the previous file beside it (`server.log.1`), replacing an older one, so a log and its previous file never take much more than twice the size. The cdd server's and the hook daemon's output logs roll when they start, and a session's `session.log`, `session.err`, and hook logs before each line they write; a file another process holds open is left until the next write or start that finds it free, since Windows will not move it. Without it, logs written on every tool call or by a server that runs for weeks grew until they filled the disk.
The process classes live in one module, `process.py`, since each is a few lines about one process on this computer.
*ClaudeChatProcess* (`claude_chat_process.py`) is the Claude Code process a chat runs in, and the folder its session works in now, read from the session file Claude Code keeps for it; `from_ancestors()` finds it above the connect script, `from_header` and `from_connection` above a request to the cdd server. It uses only the standard library, so the connect script, which runs inside the time Claude Code gives a headers helper, imports it without loading the framework.

- **Purpose:** Start, name, and stop the processes the framework keeps, the same way on Windows and elsewhere.
- **Seam (terms):** BackgroundStart, PythonInterpreter, ExclusivePort, RunningProcess, ProcessNotStopped, ClaudeChatProcess, CappedLogFile, `is_desktop_spare`. The module is a toolkit, not one deep class: each class is a small tool for one job on this computer that its callers use directly, so every class is part of the seam by design, and a deep-module count that reads all of them as exposed reads the toolkit's purpose. A class added here is one more such tool, never a helper of another class here.
- **Dependencies (one-way):** none, so harness/hooks, harness/mcp, harness/agent_tools, harness/diagnostics, and the scripts all use it without depending on each other.

## Constraint

Start a background server with *BackgroundStart* and `PythonInterpreter().windowless`, and a hook command with `PythonInterpreter().console`: `pythonw.exe` drops stdout.
