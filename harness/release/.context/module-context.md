# harness/release
This module says which CDD version a chat runs, sets and releases the next one, never on red, and runs the slow test tiers on main on a cadence so a release knows they passed.

*CddVersion* tells a chat which CDD version it runs and how that stands against the latest release on origin (its newest `v*` tag), so the chat bar's version badge shows it green (current), yellow (a minor version behind) or red (a major version behind) and offers the update. A caller asks with the `cdd-version.check` MCP operation, which fetches origin's tags first, or through its TypeScript language adapter (`@cdd/harness/release/cdd-version`); the version is `major.minor` (*Version*) of the `version` in the served checkout's `pyproject.toml`, which *ProjectVersion* is the one reader and writer of, and how the two stand is a *VersionStanding*. When origin cannot be reached it reads the newest release tag as last fetched. Commits on main after a release do not make a chat behind, and the badge's update (`/install-latest`) merges that release, not the tip of main. `cdd-version.set_next` (`/version`) writes the next version into the `pyproject.toml` of the project the call names, the version given or the next minor, and refuses text that is not a version with *VersionNotValid*; nothing raises the version by itself.
`cdd-version.release` (`/release`) releases the version `/version` set, never on red (*CddRelease*): `/version` sets the number, `/release` only packages it and changes no file. It refuses with *ReleaseAlreadyTagged* when that version already has its tag, and with *ReleaseOnRed* unless the latest e2e and heavy runs passed on HEAD; previewed, it answers the version and its release notes (*ReleaseNotes*: the commits and the tickets moved to `.sessions/_complete` since the previous `v*` tag, or since the last change to `pyproject.toml` before the first tag); published, it pushes HEAD, tags it `v<version>`, pushes the tag, and runs `gh release create` with the GitHub command line in the project's folder, answering the release's url. The person is asked before publishing.
*TestCadence* runs the slow tiers on main on a cadence, heavy every hour and e2e every day (*TestTier*), one at a time. Nothing keeps time: every `server-health.report` calls `start_due`, which starts the overdue tier in a background process (`python -m harness.release.test_runs <tier> <checkout> <record folder> --started <when the cadence recorded the run>`, *TestRunner*, the boundary to `scripts/test.ps1`) for the repository's own folder while it has main checked out (`main_checkout`); that process goes on with the run the cadence recorded, so the two are one run. A tier does not run in the checkout's own folder, which goes on changing: it runs in a detached git worktree at the commit the run records (*RunWorktree*, under `test-run-worktrees/` in the cdd home, removed when the run ends), which borrows the checkout's `node_modules` folders by link, copies the language adapters its install wrote (`.claude/language-adapters`, copied so that nothing reaches the person's own installed folder), and brings the scheduled e2e run's captures back to the checkout. A run by hand therefore tests HEAD as committed, not uncommitted edits. Each run (*TestRun*) names its checkout, its commit, and the process that runs it by its id together with when that process started, since the system gives an ended process's id to a later one; a run is live only while that process runs, and killing it ends its `test.ps1` and the specs under it (a *StarterBoundJob* of `harness/process`). A run started while another is live, on any checkout, waits and says each time what it waits for. The runs are kept in `test-runs.json` in the cdd home (*TestRunRecord*, one per checkout: the latest run of each tier with the run before it, so a failure after a pass is a new failure, and a run on a ticket's worktree leaves main's result alone). The file is put in place whole, so a reader never meets half a record, and a file that holds something else is refused with *TestRunRecordUnreadable*, which names the file and what it holds, and is never written over. The report lists the latest of each tier under `test_runs`, the health band shows them, and the chat raises a toast once for each new failure.

*DesktopWalkQuestion* (`desktop_walk_question.py`) is what the cadence asks the person when it starts an e2e run on its timer in a checkout that holds desktop story tests (`*_story.desktop.md`): whether to run the desktop walk now, which takes their screen and keyboard. The e2e run starts at once whatever the answer. `server-health.report` holds the open question as `desktop_walk_question`, the chat bar draws it as a dialog, and `server-health.answer_desktop_walk(run_id, is_yes)` takes the first answer any chat gives and tells that chat whether to run the question's command, `/desktop-walk`. On no, or no answer within ten minutes, nothing is walked, and the e2e run's summary says the walk was not run and why. A run a person starts by hand asks nothing.

- **Purpose:** Say which CDD version a chat runs, set and release the next version, and keep the heavy and e2e tiers running on main, so a release is published only on green.
- **Seam (terms):** CddVersion, Version, VersionStanding, VersionNotValid, ProjectVersion, CddRelease, ReleaseNotes, ReleaseOnRed, ReleaseAlreadyTagged, GitHubCli, GitHubCliError, TestCadence, DesktopWalkQuestion, TestTier, TestRun, RunOutcome, TestRunRecord, TestRunRecordUnreadable, TestRunner, RunWorktree, `main_checkout`, `default_record_folder`; the MCP operations `cdd-version.check`, `cdd-version.read`, `cdd-version.set_next` (`/version`), and `cdd-version.release` (`/release`); the command `python -m harness.release.test_runs <tier> <checkout> <record folder>`
- **Dependencies (one-way):** harness/agent_tools, harness/installation, harness/mcp (*CddHome*, where the record is kept), harness/process (*BackgroundStart*, *PythonInterpreter*, *RunningProcess*, *StarterBoundJob*), harness/git (*Git*, *RepoConnectError*), harness/e2e_review (*ScheduledReview*, which the cadence starts on the screens of the daily e2e run). harness/diagnostics reads the cadence for the server health report; nothing here imports it.
