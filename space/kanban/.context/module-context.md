# space/kanban
*Board* shows every work session in a repository as a *Ticket* on a kanban, so a person can see at a glance what each session has done and what it needs next. Its *Columns* are the *Backlog*, three *Stages* (Discovery, Specification, Implementation), and *Complete*. A *Stage* splits into In progress and Done and carries a WIP limit, set with `stage.set_wip_limit`. `board.show` returns the whole board, `board.folders` lists the folders a person can choose as a workpath, and `board.help(practice)` returns a *Help* for one of the board's practices, and `fidelity-progress.help` one for a fidelity: its practice, its stage, its overview, guidance, and rules, and its page on the forge as the catalog generator names it. A stage sends the fidelities it requires as the fidelities themselves, each with its formats and default format.

A *Ticket* is one session. `ticket.create` opens one. It is placed by its *FidelityProgress*: which of Generate and Validate are done on each fidelity its stage requires; a fidelity is done once its latest validate passes. A person moves it on with `ticket.move_next`, back with `ticket.move_previous`, straight into a stage's In progress or Done with `ticket.move_to`, and off the stages with `ticket.close` or `ticket.archive`. `ticket.activate` makes it the session the agent works in, after committing, pushing, or merging the ticket being left and opening the ticket's own worktree, with its branch, when the person asks: the repository's own folder stays on main, and the session folders not yet committed are committed on main and pushed first; `ticket.branch` returns the ticket's own *Branch*, which says whether it exists and whether it is checked out, and `ticket.open_worktree` opens the ticket's own worktree. What a dialog offers is answered by the ticket, as what will be done now: `ticket.leave_choices` and `ticket.close_choices` answer *LeaveChoices*, what leaving it for another or closing it can do with its work (a handoff always, a commit and push of its work branch while that is checked out, and, when leaving for another, a merge of that branch while it is not the default branch), with those chosen at first; `ticket.open_choices` answers *OpenChoices*: its own worktree while it has none, the only way a ticket opens. Every ticket's session folder, its record, stays in the repository's own `.sessions` on main, and its worktree's branch carries only the work. `board.open_tickets` names the tickets a person can switch to (by name, since their columns send them whole; `harness/chat-ui/.context/cdr/0002`), `board.active` sends the active ticket whole, the board's port is written once in `app/packages/session-board/ports.json`, which its server and `BOARD_APP_PORTS` (an *AppPorts*, read once) read, and `board_app.py` makes and registers the apps the board's server serves: `KANBAN_APP` and `STORY_UI_APP` (an *App* of harness/diagnostics each, the Story UI editor's folder being `cdd_guidance/practices/stories/app` and its page `/story-map`), which the server health report lists and the chat bar's status row opens, and a ticket's `agent_context` is what the agent is told about it. A ticket names the connected *Chat* working on it (`working_chat`), the one in its worktree, so the board sends its commands there. `ticket.format_choices` answers an action bar's format chips over some of the ticket's fidelities, `ticket.overlay_choices` answers the pattern overlays a person can choose for the ticket's session (*OverlayChoice*: every registered pattern, its icon, its first and last letter, and whether the session chose it), and `ticket.choose_overlays` keeps a new choice in the session and applies it to its graph, refusing a name that is no pattern with *NotAPatternError*, and a ticket's *StageWork* (`stage_work`) says how far its work in each stage has got taken together, for a stage head's bar. `ticket.violations` returns a *Report* of the rules broken on the ticket's stage. A fidelity's progress gives the command for each action its stage offers (`commands`): it names the ticket's session.json and no format, so the action works in the format the fidelity keeps. The chat bar and the CDD Kanban app send those commands; the board adds `format=` only for the formats its chips pick. The Generate action renders an earlier fidelity into a new format before it generates.

`fidelity-progress.report`, `fidelity-progress.files`, and `fidelity-progress.help` read one fidelity's validation report, files, and help. A *ReportFile* knows which of its practice's rules it answers for, and each *ReportRule* holds the fidelity and the *Rule* itself.

A person keeps a ticket up to date on the board: `ticket.edit_text` writes what its work is about in the idea file its session folder keeps, `ticket.tag` tags its session, `ticket.delete` removes it and its session folder, and `ticket.move_before` keeps it where it was dragged in its column. A ticket can hold child tickets: `ticket.add_child` opens one, `ticket.reassign_parent` gives a ticket another parent or none, and `ticket.pull_out` makes a child a card of its own that keeps its parent. A parent shows in the stage of its child furthest back and moves only with its children.

A *BacklogItem* is an idea that is not a session yet. `backlog-item.create` writes one, and `backlog-item.start` opens it as a ticket in Discovery and moves the item's file into the ticket's session folder, where the idea stays until it becomes lasting context. `backlog-item.edit_text` rewrites its text and `backlog-item.move_before` keeps it where it was dragged in the Backlog.

- **Purpose:** See every session's progress through the delivery stages, and move sessions through them, from an agent's tools or from the CDD Kanban app.
- **Seam (terms):** Board, Column, Stage, Ticket, FidelityProgress, StageWork, FormatChoice, OverlayChoice, BoardFidelity, LeaveChoices, OpenChoices, BacklogItem, Help, Report; the MCP operations `board.*`, `stage.*`, `ticket.*`, `fidelity-progress.*`, and `backlog-item.*`; `@language_adapter(language="typescript")` on `Board`, `Stage`, `Ticket`, `FidelityProgress`, and `BacklogItem`, so the CDD Kanban app and the chat bar reach the same tools as typed objects
- **Dependencies (one-way):** harness/agent_tools, harness/installation, harness/mcp, harness/guidance (*PracticeGuidance*, *FidelityGuidance*, *Rule*, *PracticeCatalogue*), harness/chat (*Chat*, the chats connected now), harness/markdown (*Format* and its groups), harness/catalog_generator (*CatalogPractice* and *CatalogFidelity*, which name each practice's and fidelity's page, label, and skill), harness/graph (*SavedGraph*, the one reader of the graph saved beside a report, and *Violation*), harness/guidance/stages (the stage names), space/session, space/repo, space/session (*FileEntry*). It sits in space because it tracks the work, beside the session and repo it reads. No Python module imports the board, so none of them may come to depend on it.

The CDD Kanban app's TypeScript (`app/src/kanban`) runs one way at run time: `board/` is the page's composition root (*BoardPage* wires every client and view), and imports from `ticket/`, which imports from `chat/` and `backlog-item/`; all of them draw on `shared/` (the page's store and its state shapes, `useBoard`, the brand's colours and wording, the icons, the field a card opens from an icon, and the stage head), which imports none of them. Naming a class for a type only (`import type`) is erased and is no run-time dependency. `package-direction.spec.ts` checks it.

## Constraint

Read a board from a repository; one board read reads each ticket, backlog item, and worktree from `.sessions/` and git once, and a change made through the board (a ticket opened, moved between folders, closed, reopened, or given a worktree) makes it read them again. Move a ticket only through `ticket.move_next`, `ticket.move_previous`, `ticket.move_to`, `ticket.close`, and `ticket.archive`, so every move is kept in the ticket's session.json (`stage`, `stage_mark`), with a line in its session log, or is a folder move that the ticket reads back.

Store only what cannot be read from the work: a ticket's title, scope, parent, whether it was pulled out of its parent, tags, workpath, turned-off practices, and each practice root, in its `session.json`, its text in its session folder's `<name>.md`, and the WIP limits and the order a person put each column's cards in, in `.sessions/_board.json`. Never store a ticket's progress or column; they come from the session log, so a move made by the agent and one made on the board give the same answer.

Progress counts only actions recorded in the session log. A fidelity's files existing is shown on the files list, but it does not mark Generate done. Validate and Review are allowed once any action on a fidelity is recorded or a file it declares is already there, as often as a person wants to check the same output again. Render waits for output too, since it converts it. The board and the chat bar read `allowed_actions`, the format chips, the leave, open, and close choices, a ticket's chat, and each fidelity's `commands` from Python, and add no rule of their own.

Never delete a backlog item's file: it is the only copy of the idea, so starting the item moves it instead.
