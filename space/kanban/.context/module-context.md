# space/kanban
*Board* shows every work session in a repository as a *Ticket* on a kanban, so a person can see at a glance what each session has done and what it needs next. Its *Columns* are the *Backlog*, three *Stages* (Discovery, Specification, Implementation), and *Complete*. A *Stage* splits into In progress and Done and carries a WIP limit, set with `stage.set_wip_limit`. `board.show` returns the whole board, `board.folders` lists the folders a person can choose as a workpath, and `board.help(practice)` returns a *Help* for one of the board's practices, and `fidelity-progress.help` one for a fidelity: its practice, its stage, its overview, guidance, and rules, and its page on the forge as the catalog generator names it. A stage sends the fidelities it requires as the fidelities themselves, each with its formats and default format.

A *Ticket* is one session. `ticket.create` opens one. It is placed by its *FidelityProgress*: which of Generate, Validate, and Review are done on each fidelity its stage requires. A person moves it on with `ticket.move_next`, back with `ticket.move_previous`, straight into a stage's In progress or Done with `ticket.move_to`, and off the stages with `ticket.close` or `ticket.archive`. `ticket.activate` makes it the session the agent works in, after committing, pushing, or merging the ticket being left and creating the branch or worktree the person asks for; `ticket.branch` returns the ticket's own *Branch*, which says whether it exists and whether it is checked out, and `ticket.open_worktree` opens the ticket's own worktree. What a dialog offers is answered by the ticket, as what will be done now: `ticket.leave_choices` and `ticket.close_choices` answer *LeaveChoices*, what leaving it for another or closing it can do with its work (a handoff always, a commit and push of its work branch while that is checked out, and, when leaving for another, a merge of that branch while it is not the default branch), with those chosen at first; `ticket.open_choices` answers *OpenChoices*, the branch and worktree it does not have yet. `board.open_tickets` names the tickets a person can switch to (by name, since their columns send them whole; `harness/chat-ui/.context/cdr/0002`), `board.active` sends the active ticket whole, the board's port is written once in `app/packages/session-board/ports.json`, which its server and *BoardAppPorts* read and which `board.py` registers with server health, and a ticket's `agent_context` is what the agent is told about it. A ticket names the connected *Chat* working on it (`working_chat`), the one in its worktree, so the board sends its commands there. `ticket.format_choices` answers an action bar's format chips over some of the ticket's fidelities, and a ticket's *StageWork* (`stage_work`) says how far its work in each stage has got taken together, for a stage head's bar. `ticket.violations` returns a *Report* of the rules broken on the ticket's stage. A fidelity's progress gives the command for each action its stage offers (`commands`): it names the ticket's session.json and no format, so the action works in the format the fidelity keeps. The chat bar and the Session Board app send those commands; the board adds `format=` only for the formats its chips pick. The Generate action renders an earlier fidelity into a new format before it generates.

`fidelity-progress.report`, `fidelity-progress.files`, `fidelity-progress.help`, and `fidelity-progress.finish_review` read one fidelity's validation report, files, and help, and record that a person reviewed it. A *ReportFile* knows which of its practice's rules it answers for, and each *ReportRule* holds the fidelity and the *Rule* itself.

A *BacklogItem* is an idea that is not a session yet. `backlog-item.create` writes one, and `backlog-item.start` opens it as a ticket in Discovery and moves the item's file into the ticket's session folder, where the idea stays until it becomes lasting context.

- **Purpose:** See every session's progress through the delivery stages, and move sessions through them, from an agent's tools or from the Session Board app.
- **Seam (terms):** Board, Column, Stage, Ticket, FidelityProgress, StageWork, FormatChoice, FormatGroup, LeaveChoices, OpenChoices, BacklogItem, Help, Report; the MCP operations `board.*`, `stage.*`, `ticket.*`, `fidelity-progress.*`, and `backlog-item.*`; `@language_adapter(language="typescript")` on `Board`, `Stage`, `Ticket`, `FidelityProgress`, and `BacklogItem`, so the Session Board app and the chat bar reach the same tools as typed objects
- **Dependencies (one-way):** harness/agent_tools, harness/installation, harness/mcp, harness/guidance (*PracticeGuidance*, *FidelityGuidance*, *Rule*, *PracticeCatalogue*), harness/chat (*Chat*, the chats connected now), harness/markdown (*Format* and its groups), harness/catalog_generator (*CatalogPractice*, which names each practice's and fidelity's page), harness/graph (the rule checks a report lists), harness/guidance/stages (the stage names), cdd_guidance/actions/validate (the saved graph reader, imported through `sys.path` as `validate`), space/session, space/repo, space/session (*FileEntry*). It sits in space because it tracks the work, beside the session and repo it reads. No Python module imports the board, so none of them may come to depend on it.

## Constraint

Read a board from a repository; one board read reads each ticket, backlog item, and worktree from `.sessions/` and git once, and a change made through the board (a ticket opened, moved between folders, closed, reopened, or given a worktree) makes it read them again. Move a ticket only through `ticket.move_next`, `ticket.move_previous`, `ticket.move_to`, `ticket.close`, and `ticket.archive`, so every move is a line in the session log or a folder move that the ticket reads back.

Store only what cannot be read from the work: a ticket's title, scope, parent, workpath, turned-off practices, and each practice root, in its `session.json`, and the WIP limits in `.sessions/_board.json`. Never store a ticket's progress or column; they come from the session log, so a move made by the agent and one made on the board give the same answer.

Progress counts only actions recorded in the session log. A fidelity's files existing is shown on the files list, but it does not mark Generate done. Validate and Review are allowed once any action on a fidelity is recorded or a file it declares is already there, as often as a person wants to check the same output again. Render waits for output too, since it converts it. The board and the chat bar read `allowed_actions`, the format chips, the leave, open, and close choices, a ticket's chat, and each fidelity's `commands` from Python, and add no rule of their own.

Never delete a backlog item's file: it is the only copy of the idea, so starting the item moves it instead.
