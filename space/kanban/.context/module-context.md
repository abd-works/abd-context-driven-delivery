# space/kanban
*Board* shows every work session in a repository as a *Ticket* on a kanban, so a person can see at a glance what each session has done and what it needs next. Its *Columns* are the *Backlog*, three *Stages* (Discovery, Specification, Implementation), and *Complete*. A *Stage* splits into In progress and Done and carries a WIP limit, set with `stage.set_wip_limit`. `board.show` returns the whole board, `board.folders` lists the folders a person can choose as a workpath, and `board.help(practice)` returns a *Help* for one of the board's practices, and `fidelity-progress.help` one for a fidelity: its practice, its stage, its overview, guidance, and rules, and its page on the forge as the catalog generator names it. A stage sends the fidelities it requires as the fidelities themselves, each with its formats and default format. A ticket whose `session.json` does not read, such as one a crash cut off half way, is on no column: `Board.unreadable` lists each as an *UnreadableSessionFile*, its file and what is wrong in it, while every other ticket shows as it is, so one damaged file never empties the board and is never written over.

A *Ticket* is one session. `ticket.create` opens one. It is placed by its *FidelityProgress*: which of Generate and Validate are done on each fidelity its stage requires; a fidelity is done once its latest validate passes. A person moves it on with `ticket.move_next`, back with `ticket.move_previous`, straight into a stage's In progress or Done with `ticket.move_to`, and off the stages with `ticket.close` or `ticket.archive`. `ticket.activate` opens it in its own worktree, where its own chat works on it: the worktree it has, else a new one on its own branch, made when missing. The chat that asks keeps its own session, the repository's own folder stays on main, and the session folders not yet committed are committed on main and pushed first; `ticket.branch` returns the ticket's own *Branch*, which says whether it exists and whether it is checked out. What a dialog offers is answered by the ticket, as what will be done now: `ticket.close_choices` answers *LeaveChoices*, what closing it can do with its work (a handoff always, a commit and push of the branch its work is on while a checkout has it, and, for its own branch, a merge into the default branch), none chosen at first, so closing does only what the person chooses. Every ticket's session folder, its record, stays in the repository's own `.sessions` on main, and its worktree's branch carries only the work. `board.open_tickets` names the tickets a person can switch to (by name, since their columns send them whole; `harness/chat-ui/.context/cdr/0002`), `board.active` sends the active ticket whole, the board's port is written once in `app/packages/session-board/ports.json`, which its server and `BOARD_APP_PORTS` (an *AppPorts*, read once) read, and `board_app.py` makes and registers the apps the board's server serves: `KANBAN_APP` and `STORY_UI_APP` (an *App* of harness/apps each, sharing `BOARD_SERVER`, the *AppServer* that runs `packages/session-board/serve.ts`; the Story UI editor's folder is `cdd_guidance/practices/stories/app` and its page `/story-map`), which the server health report lists and the chat bar's status row opens, and `board_app.py` sets the Story UI editor on the Stories practice (`Stories.editor = STORY_UI_APP`), so the board overview's *BoardPractice* sends each practice's `editor` (the chat bar's file viewer shows an editor tile on every file of a practice that has one) and each *BoardFidelity* sends `editor` on its practice's first fidelity only (the board's editor widget on every ticket's Stories story-map row), and a ticket's `agent_context` is what the agent is told about it. A ticket names the connected *Chat* working on it (`working_chat`), the one in its worktree, so the board sends its commands there. `ticket.format_choices` answers an action bar's format chips over some of the ticket's fidelities, `ticket.overlay_choices` answers the pattern overlays a person can choose for the ticket's session (*OverlayChoice*: every registered pattern, its icon, its first and last letter, and whether the session chose it), and `ticket.choose_overlays` keeps a new choice in the session and applies it to its graph, refusing a name that is no pattern with *NotAPatternError*, and a ticket's *StageWork* (`stage_work`) says how far its work in each stage has got taken together, for a stage head's bar. `ticket.violations` returns a *Report* of the rules broken on the ticket's stage. A fidelity's progress gives the command for each action its stage offers (`commands`): it names the ticket's session.json and no format, so the action works in the format the fidelity keeps. The chat bar and the CDD Kanban app send those commands; the board adds `format=` only for the formats its chips pick. The Generate action renders an earlier fidelity into a new format before it generates.

`fidelity-progress.report`, `fidelity-progress.files`, and `fidelity-progress.help` read one fidelity's validation report, files, and help. A *ReportFile* knows which of its practice's rules it answers for, and each *ReportRule* holds the fidelity and the *Rule* itself, described from its practice: a saved report points at each rule's text instead of copying it, and the graph saved beside it keeps only its violations and the nodes they were found on, which is all the board reads. It reads the agent's judgment with *Judgment* from `space/session/validation/validation_judgment.py`, which the session's violation history reads too.

A person accepts a violation as it is with `fidelity-progress.accept_violation` and takes that back with `fidelity-progress.reopen_violation`, each naming the violation as the report showed it (rule, message, location, line, node_id) and answering the report read again; a violation the latest report does not list is refused with *ViolationNotInReportError*, and a fidelity with no report with *NoReportToAcceptInError*. The acceptance is kept by space/session's *AcceptedViolations*, which alone decides what it covers. A *Report* leaves accepted violations out of `rules` and `violation_count` and lists them under `accepted` with `accepted_count`; a *ReportFile* matches each on the violation as its finder names it (a *ListedViolation* holds that and the violation as shown). A fidelity whose latest report names only accepted violations is done (`FidelityProgress.with_accepted_left_out`), and the progress cache keeps the accepted count beside the violation count, both worked out again when `.context/violations-accepted.json` changes. The board's report panel has Accept beside Fix and False on each violation and a closed list of the accepted ones with Take back; it sends the violation to those two operations and draws the answer.

A person keeps a ticket up to date on the board: `ticket.edit_text` writes what its work is about in the idea file its session folder keeps, `ticket.tag` tags its session, both refused for main, the default session, with `MainStaysOpenError`, as its close, archive, and delete are; `ticket.delete` removes it and its session folder, and `ticket.move_before` keeps it where it was dragged in its column. A ticket can hold child tickets: `ticket.add_child` opens one, `ticket.reassign_parent` gives a ticket another parent or none, and `ticket.pull_out` makes a child a card of its own that keeps its parent. A parent shows in the stage of its child furthest back and moves only with its children.

A *BacklogItem* is an idea that is not a session yet. `backlog-item.create` writes one, and `backlog-item.start` opens it as a ticket in Discovery and moves the item's file into the ticket's session folder, where the idea stays until it becomes lasting context. `backlog-item.edit_text` rewrites its text, and `backlog-item.move_before` and `backlog-item.move_after` keep it where it was dragged in the Backlog. Backlog items nest one level: `backlog-item.nest_under` moves an item's file into its parent's folder, `_backlog/<parent>/`, where `<parent>.md` holds the parent's text and every other markdown file is a child, and `backlog-item.leave_parent` moves it back out. A folder that keeps a session.json is a ticket's work, not a parent, so it neither takes children nor becomes one. Starting a parent starts its children as story tickets that are its children.

*ProgressCache* (`progress_cache.py`, `PROGRESS_CACHES.of(session)`, one for each session the board reads, in its work folder, held by *HeldProgressCaches* for as long as the session is) keeps, in the session's `progress-cache.json`, the answers about each fidelity that are slow to work out on every board read: whether a file it declares is there, and how many violations its latest report names. `of(fidelity).answer(question, key, work_out)` gives the kept answer while its key is unchanged, else works it out and keeps it; the board keys an answer on what Generate and Validate change, so a move works nothing out again. A missing or unreadable file only means the answers are worked out again. The board is its only reader, so it is the board's; it registers `**/progress-cache.json` with the session's saves (`SessionSaves.leave_out`), so no save of the session folders commits one.

*BoardPractices* (`board_practices.py`) are the practices a checkout's board works through, each as the catalog shows it (*CatalogPractice*): made once for each checkout's sessions with `PracticeCatalogue.create_all()` and held by *HeldBoardPractices* (`BOARD_PRACTICES.of(sessions)`) for as long as those sessions are, since the board is made again for every call; they answer a practice by its class (`of`, `works_through`) or its key (`keyed`), and raise *PracticeNotFoundError* for one the board does not have. The Files app's graph view examples (`graph_view_examples.py`, `graph_view_rule_examples.py`) seed sessions as the board's examples do, and sit beside them.

- **Purpose:** See every session's progress through the delivery stages, and move sessions through them, from an agent's tools or from the CDD Kanban app.
- **Seam (terms):** BacklogFolder (`board.backlog_folder`: `idea_files`, `place_of`), IdeaPlace (`move_under`, `move_out`), Leaving, TicketPrompts, ViolationPrompts, Board (its parts: BoardFile `board.shared`, the board file's WIP limits, card order, and fix sending; CardPlacement `board.placement`, the cards it places of the kinds the package hands `CARD_KINDS.place`, finding a ticket by name (`placement.ticket`, `ticket_called`), opening one (`open_ticket`), and starting a new read (`reread`); BoardReads `board.reads`, what the current read found, a backlog item by title among it (`reads.backlog_item_called`)), Column, Stage, Ticket (its tools declared by job on `@hosted_only` bases mixed in ahead of Card, `cdr/0004`), FidelityProgress (made from a RequiredFidelity and the LoggedWork its log names), StageWork, FormatChoice (on space/session/practices' FormatGroup), Report (from a ReportSource, with its SavedGraphStanding), OverlayChoice, BoardFidelity, LeaveChoices, BacklogItem, Help, Report, CardName (`for_new_card()`), UnreadableSessionFile (`Board.unreadable`), BoardPractices (`BOARD_PRACTICES.of(sessions)`), PracticeNotFoundError, ProgressCache (`PROGRESS_CACHES.of(session).of(fidelity).answer`), FidelityAnswers, `board.placement.free_name_for(title)`; the MCP operations `board.*`, `stage.*`, `ticket.*`, `fidelity-progress.*`, and `backlog-item.*`; `@language_adapter(language="typescript")` on `Board`, `Stage`, `Ticket`, `FidelityProgress`, and `BacklogItem`, so the CDD Kanban app and the chat bar reach the same tools as typed objects
- **Dependencies (one-way):** harness/agent_tools, harness/installation, harness/mcp, harness/guidance (*PracticeGuidance*, *FidelityGuidance*, *Rule*, *PracticeCatalogue*), harness/chat (*Chat*, the chats connected now), harness/markdown (*Format* and its groups), harness/catalog_generator (*CatalogPractice* and *CatalogFidelity*, which name each practice's and fidelity's page, label, and skill), harness/graph (*SavedGraph*, the one reader of the graph saved beside a report, and *Violation*), harness/guidance/stages (the stage names), space/session, space/session/files (*FileEntry*), space/session/practices, space/session/validation, space/repo, harness/process (*LogTimestamp*). It sits in space because it tracks the work, beside the session and repo it reads. No Python module imports the board, so none of them may come to depend on it.

The CDD Kanban app's TypeScript (`app/src/kanban`) runs one way at run time: `board/` is the page's composition root (*BoardPage* wires every client and view), and imports from `ticket/`, which imports from `chat/` and `backlog-item/`; all of them draw on `shared/` (the page's store and its state shapes, `useBoard`, the brand's colours and wording, the icons, the field a card opens from an icon, and the stage head), which imports none of them. Naming a class for a type only (`import type`) is erased and is no run-time dependency. `package-direction.spec.ts` checks it.

The page reaches the CDD domain only through the generated `{Object}ClientGenerated` classes and the page's subclasses of them, all posting through *BoardApi*, the page's one `CddApi`; it keeps no route path, fetch, or domain rule of its own. The board's server (`app/packages/session-board/app.ts`) mounts only the generated routes under `/api` (`API_ROOT` in `app/src/session-board/board-server-paths.ts`) and no route of its own: a ticket's new chat opens through `chats.open` (`ChatsClientGenerated.open`), and Update installs the Kanban app again through `app.install` (`EditorAppClient.kanban`). The board shows no file itself: a card's or a tile's files button, the details' session folder, workpath and handoff links, a ticket's text, and a violation's place in a report each open the Files app (`EditorAppClient.openFilesOn(ticket, place)`, harness/files_app) on the ticket's session.json, naming the fidelities or the folder to list and the file and line to open; the page's build is read from the static page the server serves. *EditorAppClient* opens any *App* on a project: the Story UI editor from the story-map row, and the Graph app from the header and each ticket's graph widget. While the cdd server does not answer, the page says so and how to start it, and draws no column, ticket, or band of an earlier read. Every failure on the page goes through *PageFailures* (`fail(failure, context)`, `serverDown` for the band across the page): a refused or failed call through *BoardApi*, a build check that gets no answer, a link naming nothing the board shows, a view that throws (`PageFailureView`), and anything nothing caught (`main.tsx` listens for the window's `error` and `unhandledrejection`). It is shown on the page and sent with `Chat.send('failure', {failure, context})` to the chat that opened the page (its `?chat=` link), never to a chat picked in the chat list; each failure text goes to that chat once, so the reads every two seconds meeting it again send it once. A page no chat opened only shows it, and a failure to tell the chat is shown, never sent again. `app/src/session-board/web-domain-access.spec.ts` checks the calls and routes.

## Constraint

Read a board from a repository; one board read reads each ticket, backlog item, and worktree from `.sessions/` and git once, and a change made through the board (a ticket opened, moved between folders, closed, reopened, or given a worktree) makes it read them again. Move a ticket only through `ticket.move_next`, `ticket.move_previous`, `ticket.move_to`, `ticket.close`, and `ticket.archive`, so every move is kept in the ticket's session.json (`stage`, `stage_mark`), with a line in its session log, or is a folder move that the ticket reads back.

Store only what cannot be read from the work: a ticket's title, scope, parent, whether it was pulled out of its parent, tags, workpath, turned-off practices, and each practice root, in its `session.json`, its text in its session folder's `<name>.md`, and the WIP limits and the order a person put each column's cards in, in `.sessions/_board.json`. Never store a ticket's progress or column; they come from the session log, so a move made by the agent and one made on the board give the same answer.

Progress counts only actions recorded in the session log. A fidelity's files existing is shown on the files list, but it does not mark Generate done. Validate and Review are allowed once any action on a fidelity is recorded or a file it declares is already there, as often as a person wants to check the same output again. Render waits for output too, since it converts it. The board and the chat bar read `allowed_actions`, the format chips, the leave, open, and close choices, a ticket's chat, and each fidelity's `commands` from Python, and add no rule of their own.

Never delete a backlog item's file: it is the only copy of the idea, so starting the item moves it instead. Never write over one either: a new card's name comes from its title through `CardName` (`card_name.py`), which refuses a title that gives no name (`TitleNamesNothingError`) or too long a one (`TitleTooLongError`), and a name already taken is refused (`TicketNameTakenError` for a session, main included; `BacklogItemTakenError` for an idea's file) before any folder, file, or branch is made. `board.placement.free_name_for(title)` answers the name a new ticket gets and makes the taken-name refusal, and a child ticket's name goes through it as any card's does; a name is at most `NAME_LENGTH_LIMIT` (64) characters, since it is the ticket's session folder, its branch, and part of every path in its worktree.

Close a ticket in this order, in `Ticket.close`: its work committed where it is and its branch merged (`TicketCheckout.save_work`), then its worktree and branch removed (`TicketCheckout.leave_branch`), then its session ended and its record moved. A merge git refuses, or a worktree a running program holds open, then stops the close with the ticket still open, and what is uncommitted in the repository's own folder is never committed for a ticket that has its own worktree. Archiving or deleting a ticket first removes its own worktree, its work committed and pushed on its branch, which stays (`TicketCheckout.free_worktree`), so no checkout is left that no card reaches. A folder in the way of a ticket's worktree is refused by name (`TicketWorktreeBlockedError`).
