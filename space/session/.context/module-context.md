# space/session
*Session* is one named piece of work in a project — a board ticket's work, or `main`, which works on the whole repository — so every action, log line, handoff, and validation report lands in the folder of the work it belongs to. A session lives in `.sessions/{name}/`: its `session.json` (title, scope, parent, whether it was pulled out of that parent, tags, workpath, and practice roots), its idea file `<name>.md` (`text`, `keep_text(text)`, an *IdeaFile*: a heading and the text under it), its `session.log`, its handoffs, and its validation reports. `set_parent(parent)`, `mark_pulled_out()`, `add_tag(word)`, and `open_child(title, scope)` keep a board ticket's hierarchy and tags; `remove()` deletes its folder. A closed session moves to `.sessions/_complete/{name}/`. A session is one object for each session folder, which its *Sessions* hold, and what it keeps on disk is read from its folder each time a caller asks for it, so a switch or a close made by another chat or by the hook server is seen at once; its `session.json` (`session.fields`), which one board read asks thousands of times, is held and read again only once the file's last-written time or size changes (*HeldJsonFile*, harness/installation).

*Sessions* are the work sessions of one checkout and which of them is open. `Sessions(project)` holds the checkout holding the project (`sessions.repo`, `Repo.of_project`, the one Repo this process holds for that checkout), and every session it loads or creates is made with those sessions (`Session(sessions)`, `session.sessions`) and holds that repository (`session.repo`), so a session closes, moves, and lists its files without building either again. A chat in a ticket's own worktree works on that ticket, found from the worktree's branch, whatever any chat chose to open. A chat in the repository's own folder keeps its open session in *WorkState* (`sessions.open_state(chat)`), kept by the cdd server under `~/.cdd` and never in the checkout. `Sessions(project).current()` and `Sessions(project).switch(name, workpath)` are the only operations that read or change which session is open; `load(folder)` and `with_file(session_file)` read a session without opening it, `named(name)` and `all()` find the board's sessions, `create(name, workpath, title=, scope=, parent=)` makes a session for later without opening it, and `close(session)` makes main the open one again when that session was open. Every checkout's sessions use the repository's own `.sessions`, in its main clone (`sessions.folder`), so a chat in a ticket's linked worktree logs into the folder the board reads, and the ticket's branch carries only its work. A session moved to the closed sessions, the archive, or the backlog, or reopened, moves its folder and stays the same object.

The *workpath* is the folder a session works in; its practices write under it and its graph is opened on it. `Session.graph` is the session's knowledge graph (harness/graph's *Graph*). `Session.overlays` names the patterns the session overlays on that graph, kept in its session.json; `choose_overlays` replaces them and applies them to the graph at once, and a graph made later applies them when it opens. The sessions that loaded a session hold one *Session* object per session folder (`sessions.load(folder)` answers it, and a session moved to another folder stays that object), and every call in the session, from any chat, works on it: it makes its graph and its one instance of each practice (made with `PracticeCatalogue.create_all()`) once, under a lock, so two calls that first ask at once wait for the one the first makes, and every call in the session works on the same graph and the same practices and none rebuilds them. A session holds no chat: a call's chat is the call's own, and the lines a call writes go through `session.log.by(call.chat)`. The process holds the sessions of each project it serves (*CallSessions*, `Sessions.of_project(project)`), so the kept sessions last for as long as the cdd server runs. A new graph reads back the graph saved in its root's `.context/graph.json` (`Graph.open_saved`), so a session opened again, such as a ticket just activated, shows what was loaded in it before rather than an empty graph. When a session's root moves, it makes its graph and practices again on the new root. An action that writes files refreshes it with exactly those files (`GuidanceAction.wrote`, or `graph.refresh` from the agent); nothing watches the files. An empty workpath is the whole repository. `Session.work_root` is that folder, worked out in one place: sketches, grill answers, partitions, each practice's folder, and the file manager all start from it.

*PracticeSessionOutput* is what one practice has in one session: the session's one instance of the practice (`guidance`), whether it is on, and the folder it writes under. `session.practice("stories")` returns it. An action works on that same practice: it holds the fidelity its guidance names (`GuidanceAction.fidelity_of`) and never moves the practice's current fidelity, which stays the one the practice was made at, and gives the format it names to that fidelity, which keeps it; so another call on another fidelity of the same practice changes nothing it reads. The line it logs names that fidelity: it hands the log the fidelity's *FidelitySessionOutput*, the one the fidelity holds, whose `practice` answers the practice's name and folder and whose `fidelity` its name and format; the log takes no other kind, and a practice worked at no fidelity is named on no line. The practice works in the session through `PracticeGuidance.work_in`, which gives each of its fidelities, through `FidelityGuidance.work_in`, its *FidelitySessionOutput*: where that fidelity writes each format in the session, the files it declares there, the format it last used, and its reports folder. Where a practice writes is kept in one place, its session's `session.json` (`outputs`), else it is the practice's default: the folder the project's `.context/config.json` (`session.context_config`, made once) names for it, else the guidance's own default folder. A fidelity reads and saves its part of the practice's `session.json` through the practice's public `chosen_outputs`, `saved`, and `save`. The session makes its practices once, with its graph; a validate is logged for the call that ran it (`session.log.by(call.chat).validation(worked, violations)`, which a guidance action reaches as its `log`), so the line points at that call's chat.

*SessionLog* (`session.log`) is the session's `session.log` and `session.err`: one line per action, tool call, note, and loop marker, stamped with a *LogTimestamp* (UTC, to the second; the one time format every log a session keeps uses, and the board's last-activity times, the prompt log, and the toasts use it too), each ending with a pointer to the chat that caused it. A *Loop* is one context–generate–evaluate cycle marked in the log, so the lines of one cycle can be read back together with the chat that produced them. Each line points at the chat that caused it — the *ChatPointer* (harness/agent_tools) of the tool call that wrote it, through the *ChatLog* that call writes with (`session.log.by(call.chat)`), else `no-chat`; never a chat the server's environment names, which would point one chat's line at another — so `session.read_loop` can put that chat's words back under the line. A session tool that writes a line, such as `session.mark_loop` or `session.append_log`, takes the call it answers, which the framework hands it as it hands `project`. The rules a hook gave the agent (*InjectedRules*, made once with the log) wait in the session's folder until the next log line names them, because the hook server notes them and the cdd server writes that line. *ChatInjections* (`session.chat_injections`) keep the rules a hook gave each chat of the session in its `chat-injections` folder and replay them on that chat's next prompt, never another chat's; the hook server asks the session of each event for them. How an agent keeps the log is `SESSION-LOG.md`, which `sessions.switch` answers with. *SessionFiles* (`session.session_files`) are the files a session works with: the ones in its folder, and any file of its repository it reads. They are the one place a path a call names is checked: `existing(named)` answers the path once something is there, `from_root(named)` writes it from the session's root, as the session's graph names its files, and `in_root(path)` says whether a path lies under that root; each refuses with *NamedPathNotFoundError*, which names the path, the project it was read from, and the root when the root refused it, so the Validate, Grill, and Context Index actions never work on nothing and report it as a clean result; the files a practice declares are each fidelity's own, through its *FidelitySessionOutput*, which searches the session's file manager named from the project's top with each declared path's glob (*DeclaredFile*, harness/guidance) and keeps the files its fidelity declares (`FidelityGuidance.declares(path, format)`).

*FileManager* lists and reads the files under a session's roots — the folder each of its practices works in — so every application shows files the same way instead of each object growing a read operation of its own. `session.session_files.file_manager` is the session's, held in memory and made again only when its roots change; a tool call loads it with `FileManager.load(call=...)`, from the session open in the call's project (`call.session`). A session reads through two file managers because paths are named from two tops: its own, named from its workpath, which a page lists and reads, and one named from the project's top (*SessionFiles*), which reads and finds the files the board names that way. `sessions.file_manager` lists the folders anywhere in the checkout, named from its top, for the board's folder picker. *Folder* is a listed folder and its entries, folders first; *FolderEntry* is one entry with its path and size. *FileEntry* is a declared file with its path from the project and whether it exists. *FileText* is a file's path and its text. The MCP tools are `file-manager.list(folder)` and `file-manager.read(path)`; the board's TypeScript reaches them through the language adapter the installer deploys.

A ticket's record is kept on main so every chat and worktree reads the same board. A session saves itself: each write to its folder (`save_fields`, `keep_text`, `keep_file`, a move of its folder, `remove`) queues the save of that change and returns at once, so a caller such as a board ticket only says what changes. *SessionSaves* (`sessions.saves`, one for each repository's `.sessions`, shared by its main checkout and every worktree) commits the session folders on main and pushes main on a thread of its own, half a second after a change so every file it writes goes in one commit, several waiting saves in one commit, and not while a merge is in progress in the repository's own folder, which a commit would conclude. `saves.later(message)` queues a save of something in `.sessions` that is no session's own, such as a Backlog item or the board's card order; `saves.now(message)` waits for the queued saves and saves in the caller's thread, for work that needs main committed before it goes on (opening a ticket's worktree, closing or archiving it), and raises git's refusal. Before it commits, it makes sure the session folders' own `.gitignore` lists `**/progress-cache.json`, so no save commits a progress cache in a project whose own `.gitignore` does not name it. A queued save git refuses is kept as `saves.failure`, a *SaveFailure* naming the changes not saved and what git said, until a save succeeds; `saves.retry()` queues them again. The changes stay on disk, so the board works on them meanwhile.

*ProgressCache* (`session.progress_cache`, made when the session is given its folder) keeps, in the session's `progress-cache.json`, the answers about each fidelity that are slow to work out on every board read: whether a file it declares is there, and how many violations its latest report names. `answer(fidelity, question, key, work_out)` gives the kept answer while its key is unchanged, else works it out and keeps it; the board keys an answer on what Generate and Validate change, so a move works nothing out again. A missing or unreadable file only means the answers are worked out again.

A *handoff* is a compact account of a session — what it achieved, what was learned, and where the next agent starts — so a fresh agent can continue the work without rereading the whole chat. *Handoffs* (`session.handoffs`, made when the session is given its folder) write each one as a new `handoff-{timestamp}.md` in the session's folder; `Session.latest_handoff` names the newest. A practice's `PracticeSessionOutput.design_view` is the Claude Design link recorded for the latest version of the design canvas under the folder it writes under (*CanvasVersions* of harness/design_canvas; the UX practice's), which the chat bar's file viewer opens; empty while the practice is off or none is recorded. The instructions `session.handoff_session(next_focus)` read the handoff format (`HANDOFF-FORMAT.md`, through `session.read_handoff_format`), draft the handoff, and call `session.write_handoff`.

A *Context Decision Record* (CDR) is a short, numbered markdown file that records a design choice a later reader would otherwise question: one that is hard to reverse, surprising without its context, and a real trade-off. *DecisionRecords* (`Session.decision_records`, made again when the workpath moves) are a session's records, `.context/cdr/{NNNN}-{slug}.md` under its workpath, each numbered one past the highest; `CDR-FORMAT.md` beside this module is their template. `session.read_cdr_format`, `session.list_cdrs(session)`, and `session.write_cdr(session, slug, paths)` read the format, list the records, and write one; the instructions `session.record_decisions_session(session)` wrap an action's turn so records are offered as decisions are made.

*CallSessions* holds the sessions of every checkout the process serves, each made once and held by the checkout's top, as its one Repo is (`Sessions.of_project`), so a call naming a folder inside the checkout reaches the same sessions; it is how a tool call opens its sessions: `sessions.py` registers it with *ToolCall* when it is imported, so `call.session` is the session open in the call's project and `call.session_named(session_file)` the one a board command names, each the one object its sessions hold, and `ToolCall.session_in(project)` the session open in a project for work that serves no call, such as a hook event (`HookPayload.session`) or a diagnostics probe, while the framework never imports this module. `Session.from_file`, `PracticeSessionOutput.load`, and `FileManager.load` take the call they serve and find their session through it, so session.py, practice_session_output.py, and file_manager.py never import sessions.py, which imports them.

*ThrowawayProject* is an empty project a spec works in, so the actions a spec runs write to their own session log instead of the log of whoever is working in the repository.

The MCP tools `sessions.current` and `sessions.switch` act on the project the call names. Every `session.*` tool acts on the session whose `session.json` its required `session` argument names (a path from the project): `session.close`, `session.choose_workpath`, `session.folder_files`, `session.read_file`, `session.mark_loop`, `session.read_loop`, `session.append_log`, `session.write_handoff`, `session.read_handoff_format`, `session.read_cdr_format`, `session.list_cdrs`, and `session.write_cdr`, and the instructions `session.handoff_session` and `session.record_decisions_session`; each finds its session and calls one operation on it or on its log, files, handoffs, or decision records. The file manager publishes `file-manager.list` and `file-manager.read`. Per practice there are `practice-session-output.enable`, `practice-session-output.choose_root`, and `practice-session-output.use_default_root`; `session-diagnostics.session_diagnostics` probes the session log through the live MCP host. The commands `/current-session`, `/switch-session`, `/close-session`, `/mark-loop`, `/read-loop`, and `/append-log` call them, and the skills `space-session-handoff-session` and `space-session-record-decisions-session` run the two instructions.

- **Purpose:** Keep the state of one piece of work — where it works, which practices it uses and where they write, the files it works with, the log of what was done, the handoff the next agent resumes from, and the reasons behind hard-to-reverse choices — so any chat or tool can pick the work up from its folder.
- **Seam (terms):** Session (`path_named(path)` and `document_named(content, paths)`, which read a path a call names from the session's project, never the cdd server's working folder), IdeaFile, Sessions, SessionSaves (`later`, `now`, `retry`, `failure`), SaveFailure, ProgressCache (`answer`), PracticeSessionOutput, FidelitySessionOutput, SessionLog, ChatLog, LogTimestamp, InjectedRules, Loop, LogEntry, ChatInjections, CallSessions, SessionFiles (`existing`, `from_root`, `in_root`), NamedPathNotFoundError, FileManager, Folder, FolderEntry, FileEntry, FileText, PathOutsideRootsError, Handoffs, DecisionRecords, ThrowawayProject, `file-manager.list`, `file-manager.read`, `sessions.current`, `sessions.switch`, `session.close`, `session.choose_workpath`, `session.folder_files`, `session.read_file`, `session.mark_loop`, `session.read_loop`, `session.append_log`, `session.write_handoff`, `session.read_handoff_format`, `session.handoff_session`, `session.read_cdr_format`, `session.list_cdrs`, `session.write_cdr`, `session.record_decisions_session`, `practice-session-output.enable`, `practice-session-output.choose_root`, `practice-session-output.use_default_root`, `session-diagnostics.session_diagnostics`
- **Dependencies (one-way):** `space/work_state` (*WorkState*), `space/repo` (*Repo*), `harness/agent_tools` (*ToolCall*, which this module registers *CallSessions* with, and *ChatPointer*), `harness/installation` (*ContextConfig*, `@language_adapter` for the file manager's TypeScript client, and *InstallDiagnostics*, the diagnostics file the session diagnostics write), `harness/diagnostics` (*CallDiagnostics*, which the session diagnostics are, so they write into the install of the project their call names), `harness/mcp`, `harness/hooks` (*HookPayload* and *HookResult*, which *ChatInjections* read), `harness/guidance` (*PracticeCatalogue*), `harness/catalog_generator` (*CatalogPractice*, the catalog's view of each practice: `Sessions.board_practices` holds one *BoardPractices* for the checkout's session board, made once since the board is made for every call, which answers a practice by its class or its key), `harness/graph`, `harness/annotations` (*Name*), `cdd_guidance/actions` (*Generate* and *Validate*, in the session diagnostics probe). None of them imports this module back: agent BDD reaches a session through `ToolCall.session_in`. Inside the module, sessions.py imports session.py, which imports the files below it; none imports back.

## Constraint

Name the session work is for. Every `session.*` tool takes the session's `session.json` as its `session` argument and refuses an empty or missing one with `SessionNotFoundError`, so work asked for one ticket never lands in whichever session a chat has open; ask `sessions.current` for the open session's `session_file` when the user names none. Only `sessions.switch` changes the open session, and only `sessions.current` and `ToolCall.session` read it. Read another session with `Sessions.load`, `Sessions.with_file`, `Session.from_file(session, call)`, or `Sessions.named`, which do not open it. Write to a session's log through `session.log.by(chat)`, never by editing `session.log`. Draft a handoff or a decision record to a file and pass its path in `paths`; do not put its body on an MCP call. Offer a decision record only when all three criteria hold, write it as soon as the decision is made, and never invent or batch decisions. Write large or temporary outputs (graph JSON, probes, reports) under the session's folder, not beside the work. Name a file manager's paths from the session's workpath: a path outside the session's roots raises *PathOutsideRootsError*, so a caller cannot read the rest of the disk through a session, and `read` returns no text for a file that is gone, such as one deleted since a page listed it; check `FileText.text` rather than expecting an error. Specs that run actions open a *ThrowawayProject* and close it after each example.
