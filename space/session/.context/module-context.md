# space/session
*Session* is one named piece of work in a project — a board ticket's work, or `main`, which works on the whole repository — so every action, log line, handoff, and validation report lands in the folder of the work it belongs to. A session lives in `.sessions/{name}/`: its `session.json` (title, scope, parent, workpath, and practice roots), its `session.log`, its handoffs, and its validation reports. A closed session moves to `.sessions/_complete/{name}/`. A session is read from its folder each time a caller asks for it, so a switch or a close made by another chat or by the hook server is seen at once; no session object is held between calls. What the cdd server does hold between calls is each session's graph and practices, by the session's folder (see below).

*Sessions* are the work sessions of one checkout and which of them is open. The open session is saved in one place, `session` in the checkout's `.sessions/session.json` (through *WorkState*). `Sessions(project).current()` and `Sessions(project).switch(name, workpath)` are the only operations that read or change which session is open; `Sessions.saved` reads it, `named(name)` and `all()` find the board's sessions, `create(name, workpath, title=, scope=, parent=)` makes a session for later without opening it, and `close(session)` makes main the open one again when that session was open. A ticket's session lives in the main checkout's `.sessions`, so a chat in the ticket's linked worktree logs into the folder the board reads.

The *workpath* is the folder a session works in; its practices write under it and its graph is opened on it. `Session.graph` is the session's knowledge graph (harness/graph's *Graph*): the cdd server holds one per session in memory, by the session's folder, from the session's first call on, so every call in the session works on the same graph and none rebuilds it from disk. The graph holds the session's one instance of each practice (made with `PracticeCatalogue.create_all()`), which is the same object every action in the session works with, so there is no second copy of a practice per call. A session whose root moves gets a new graph and new practices on the new root. An action that writes files refreshes it with exactly those files (`GuidanceAction.wrote`, or `graph.refresh` from the agent); nothing watches the files. An empty workpath is the whole repository. `Session.root` is that folder, worked out in one place: sketches, grill answers, partitions, each practice's folder, and the file manager all start from it.

*PracticeSessionOutput* is what one practice has in one session: the session's one instance of the practice (`guidance`), whether it is on, and the folder it writes under. `session.practice("stories")` returns it. An action works on that same practice: it works at the fidelity its guidance names (`PracticeGuidance.work_at`), and gives the format it names to that fidelity, which keeps it; the action reads the fidelity it works at once, when it lists its guidance (`GuidanceAction.fidelity_of`), so another call on another fidelity of the same practice does not change what it checks. The practice works in the session through `PracticeGuidance.work_in`, which gives each of its fidelities, through `FidelityGuidance.work_in`, its *FidelitySessionOutput*: where that fidelity writes each format in the session, the files it declares there, the format it last used, and its reports folder. Where a practice writes is kept in one place, its session's `session.json` (`outputs`), else it is the practice's default: the folder the project's `.context/config.json` names for it, else the guidance's own default folder.

*SessionLog* (`session.log`) is the session's `session.log` and `session.err`: one timestamped line per action, tool call, note, and loop marker, each ending with a pointer to the chat that caused it. A *Loop* is one context–generate–evaluate cycle marked in the log, so the lines of one cycle can be read back together with the chat that produced them. Each line points at the chat that caused it — the *ChatPointer* (harness/agent_tools) of the tool call the session was opened for (`Session.chat`), else `no-chat`; never a chat the server's environment names, which would point one chat's line at another — so `session.read_loop` can put that chat's words back under the line. The rules a hook gave the agent (*InjectedRules*) wait in the session's folder until the next log line names them, because the hook server notes them and the cdd server writes that line. How an agent keeps the log is `SESSION-LOG.md`, which `sessions.switch` answers with. *SessionFiles* (`session.session_files`) are the files a session works with: the ones in its folder, and any file of its repository it reads; the files a practice declares are each fidelity's own, through its *FidelitySessionOutput*.

A *handoff* is a compact account of a session — what it achieved, what was learned, and where the next agent starts — so a fresh agent can continue the work without rereading the whole chat. *Handoffs* (`session.handoffs`) write each one as a new `handoff-{timestamp}.md` in the session's folder; `Session.latest_handoff` names the newest. The instructions `session.handoff_session(next_focus)` read the handoff format (`HANDOFF-FORMAT.md`, through `session.read_handoff_format`), draft the handoff, and call `session.write_handoff`.

A *Context Decision Record* (CDR) is a short, numbered markdown file that records a design choice a later reader would otherwise question: one that is hard to reverse, surprising without its context, and a real trade-off. *DecisionRecords* (`Session.decision_records`) are a session's records, `.context/cdr/{NNNN}-{slug}.md` under its workpath, each numbered one past the highest; `CDR-FORMAT.md` beside this module is their template. `session.read_cdr_format`, `session.list_cdrs(session)`, and `session.write_cdr(session, slug, paths)` read the format, list the records, and write one; the instructions `session.record_decisions_session(session)` wrap an action's turn so records are offered as decisions are made.

*CallSessions* is how a tool call opens its sessions: `sessions.py` registers it with *ToolCall* when it is imported, so `call.session` is the session open in the call's project and `call.session_named(session_file)` the one a board command names, each opened for that call's chat, while the framework never imports this module.

*ThrowawayProject* is an empty project a spec works in, so the actions a spec runs write to their own session log instead of the log of whoever is working in the repository.

The MCP tools `sessions.current` and `sessions.switch` act on the project the call names. Every `session.*` tool acts on the session whose `session.json` its required `session` argument names (a path from the project): `session.close`, `session.choose_workpath`, `session.folder_files`, `session.read_file`, `session.mark_loop`, `session.read_loop`, `session.append_log`, `session.write_handoff`, `session.read_handoff_format`, `session.read_cdr_format`, `session.list_cdrs`, and `session.write_cdr`, and the instructions `session.handoff_session` and `session.record_decisions_session`; each finds its session and calls one operation on it or on its log, files, handoffs, or decision records. Per practice there are `practice-session-output.enable`, `practice-session-output.choose_root`, and `practice-session-output.use_default_root`; `session-diagnostics.session_diagnostics` probes the session log through the live MCP host. The commands `/current-session`, `/switch-session`, `/close-session`, `/mark-loop`, `/read-loop`, and `/append-log` call them, and the skills `space-session-handoff-session` and `space-session-record-decisions-session` run the two instructions.

- **Purpose:** Keep the state of one piece of work — where it works, which practices it uses and where they write, the log of what was done, the handoff the next agent resumes from, and the reasons behind hard-to-reverse choices — so any chat or tool can pick the work up from its folder.
- **Seam (terms):** Session (`path_named(path)` and `document_named(content, paths)`, which read a path a call names from the session's project, never the cdd server's working folder), Sessions, PracticeSessionOutput, FidelitySessionOutput, SessionLog, InjectedRules, Loop, LogEntry, CallSessions, SessionFiles, Handoffs, DecisionRecords, ThrowawayProject, `sessions.current`, `sessions.switch`, `session.close`, `session.choose_workpath`, `session.folder_files`, `session.read_file`, `session.mark_loop`, `session.read_loop`, `session.append_log`, `session.write_handoff`, `session.read_handoff_format`, `session.handoff_session`, `session.read_cdr_format`, `session.list_cdrs`, `session.write_cdr`, `session.record_decisions_session`, `practice-session-output.enable`, `practice-session-output.choose_root`, `practice-session-output.use_default_root`, `session-diagnostics.session_diagnostics`
- **Dependencies (one-way):** `space/work_state` (*WorkState*), `space/repo` (*Repo*), `tools/file_manager`, `harness/agent_tools` (*ToolCall*, which this module registers *CallSessions* with, and *ChatPointer*), `harness/installation` (*ContextConfig*), `harness/mcp`, `harness/guidance` (*PracticeCatalogue*, *ActionCatalogue*), `harness/graph`, `harness/installer` (*Installer*, whose diagnostics file the session diagnostics write), `harness/name`, `cdd_guidance/actions` (*Generate* and *Validate*, in the session diagnostics probe). None of them imports this module back.

## Constraint

Name the session work is for. Every `session.*` tool takes the session's `session.json` as its `session` argument and refuses an empty or missing one with `SessionNotFoundError`, so work asked for one ticket never lands in whichever session a chat has open; ask `sessions.current` for the open session's `session_file` when the user names none. Only `sessions.switch` changes the open session, and only `sessions.current`, `Sessions.saved`, and `ToolCall.session` read it. Read another session with `Session.load`, `Session.from_file(session, project)`, or `Sessions.named`, which do not open it. Write to a session's log through `session.log`, never by editing `session.log`. Draft a handoff or a decision record to a file and pass its path in `paths`; do not put its body on an MCP call. Offer a decision record only when all three criteria hold, write it as soon as the decision is made, and never invent or batch decisions. Write large or temporary outputs (graph JSON, probes, reports) under the session's folder, not beside the work. Specs that run actions open a *ThrowawayProject* and close it after each example.
