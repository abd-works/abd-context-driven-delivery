# tools
*Tools* are standalone toolsets an agent or an application calls beside the practices. Each one sits in its own package and depends on none of the others, so a tool can be added or removed without touching the rest; they share this one card because none of them is big enough to be a module of its own.

*SubAgent* (`tools/sub_agent`) publishes `sub-agent.sub_agent`, the operation that hands a recipe to a background sub-agent and lets the current conversation go on without waiting. The `@subAgent` annotation, which puts the same hand-off at the start of any member's description, stays in harness/agent_tools beside the toolsets that read it.

*Echo* (`tools/echo`) shows an action's fully wrapped instructions inside a DO-NOT-FOLLOW fence, so a person or an agent can read exactly what an action would tell an agent without the agent acting on it. The MCP tool `echo.fence(body)` fences any text, and the MCP instructions `echo.echo_session(instructions)` fence the instructions an action produced.

*Granola* (`tools/granola`) files unorganized Granola meeting notes into folders and brings chosen notes into a project folder's `.context/granola/` as independent context files, one file per note. The MCP instructions `granola.organize(scope)` propose a folder for each note and file them after the user confirms; `granola.context(notes, folder)` captures notes into a folder. The MCP tools `granola.format_filing_plan`, `granola.list_note_context`, and `granola.write_note_context` do the local work those instructions call for.

*PromptLog* (`tools/prompt_log`) is a read-only audit of what the IDE sends the model — submitted prompts with their attachments, files read into context, tool calls, sub-agent tasks, and agent responses — appended to `prompt-log.txt` in the log folder of the session open in the project being worked on, so a person can see afterwards exactly what the model was given. It handles the hooks `beforeSubmitPrompt`, `beforeReadFile`, `preToolUse`, `subagentStart`, and `afterAgentResponse`. Each event's entry is a *PromptLogEntry*, and each file an event names is a *LoggedFile*, which says what kind of guidance it is: `installed_guidance_kind` (`harness/installation/ide_layout.py`) says whether an install wrote it as a skill, a rule, or an agent in any IDE's folder, and the prompt notifier asks the same. Both read the paths a tool call names from `ToolCall.named_paths` and the tool it invokes from `HookPayload.invoked_tool`, the one reader of each.

*PromptNotify* (`tools/prompt_notify`) shows an IDE toast naming the action, practice, fidelity, or rule an agent has just invoked, so a person watching the chat sees which guidance is being used. It handles the `preToolUse` hook, writes the notice to `.cursor/prompt-notify-toast.json` in each workspace folder, and installs the IDE toast extension that shows it. `@Toast` (harness/annotations) is the annotation an author puts on an `@agent_tool` or `@agent_instructions` member so that calling it toasts; `harness/guidance_actions` annotates the step every guidance action starts with, so each action toasts without its own annotation. Its full model is `tools/prompt_notify/.context/prompt-notify-model.md`.

*DrawioViewer* (`tools/drawio_viewer`) is a small local web server, not a toolset: it serves every `.drawio` file under a folder into the real draw.io editor (loaded from embed.diagrams.net) in a browser tab, and its **Save** writes the diagram back to disk, so a person sees and edits a diagram instead of reading its XML. Run it as `python tools/drawio_viewer/drawio_viewer.py [root] [port]`; `http://127.0.0.1:8791/` lists the files and `/edit?f=<path>` opens one. *DrawioFiles* is the folder it serves, which lists its draw.io files, finds the file a request names, and labels each from the folder. The always-on rule `cdd_guidance/rules/drawio-viewer.md` tells an agent to start it and open a diagram in the browser pane when the user asks to see one. The cdd home publishes a copy inside the cdd-board mod (`drawio-viewer/drawio_viewer.py`), which the mod's `cdd-mod.json` (harness/chat-ui/pane) names as a file it carries, so the chat bar's Open in draw.io works in any project the chat UI is installed for. It imports nothing from the framework.

*PromptQueue* (`tools/prompt_queue`) holds the prompts a person wants Claude to work through next, so they can line up work while Claude is busy and let it run on its own. It is a Claude Code mod, not a toolset: a stack image above the chat bar, with the count drawn on it, opens into one card per queued prompt in the order they will be sent. A person queues the draft in the prompt box with Alt+Enter or the `+` beside the stack, edits, moves or removes a card, and presses play: from then on each finished turn sends the next prompt, ahead of Claude's own queue, until pause. A queued slash command runs as that command. In sub-agent mode the model groups the queue into tasks that run side by side, one sub-agent each, and `/queue [what to focus on]` has the model turn the conversation so far into queued prompts. The mod keeps the queue in `$.state` under `prompt-queue`, declared in `types/index.d.ts`, and imports nothing from the framework. Its `cdd-mod.json`, beside its `.claude-plugin` folder, names its plugin, `prompt-queue`, so the cdd home publishes it from the code the server runs without the framework naming its folder. The queue itself is kept by the cdd server: *PromptQueue* (`prompt_queue.py`) is the toolset whose `prompt-queue.*` MCP operations the mod, the agent in the chat, and a session starting in it all change one queue through, kept in a file in the chat's own folder. `PromptQueue.of_chat(chat, archive=None)` is the queue of one chat; a chat id that is empty or is a path is refused with *ChatIdNotAnId*, so no queue is written outside the chats folder. `PromptQueue.load` refuses another chat than the calling one with *ChatNotKnown* while the chats folder keeps no folder for it, so a mistyped chat id never makes a queue nobody reads; the calling chat's own queue is made on its first card. A queue file that does not hold a prompt queue is refused with *QueueFileUnreadable* and never written over, and a step given a state that is none of `STEP_STATES` is refused with *StepStateUnknown*. Each change holds the file from its read to its write (harness/installation's `JsonFile.held()`), since the stable lane's cdd server and the dev lane's change the same queue.

*Failure* (`tools/error_display`) is one failure as a person sees it: what failed with the reason it gave, and the context it failed in, such as the button pressed and the tool it called. Every failure is shown the same way, with Fix, which sends both to the chat to find the cause and fix it. The MCP tool `failure.describe(failure, context, kind)` answers one, and `@language_adapter(language="typescript")` generates `FailureData` for code outside Python. A failure of a known *FailureKind* (`FAILURE_KINDS`: `file_display`, `missing_link`, `graph_view`, `render`, `generate`, `session_roots`) also answers the most common causes of that kind, the likeliest first, and every failure answers its fix command: the debug session command with the fix chosen and, as its details, the failure, its context and those causes, which a page's Fix shows the person and sends the chat (the Files app's failure band, `harness/files_app/app/files/failure-fixes.ts`). A kind no failure has is refused with *FailureKindUnknownError*, which names it; a failure that names no kind has no known causes. The chat bar's failure line (`harness/chat-ui/pane/hooks/error-display/`) shows one above the bar until it is fixed or dismissed; the mod builds the shape itself, since a failure must show while the cdd server is what is broken. Nothing in the mod swallows a failure: a catch shows it with `showFailure` or `shownAsFailure`, and a shared opener returns its reason for the caller to show.

- **Purpose:** Hold the toolsets that are useful on their own, outside any one practice or action: delegating to a sub-agent, reading what an action instructs, filing meeting notes as context, showing every failure the same way, showing and logging what crosses to the model, and queuing prompts for Claude to work through.
- **Seam (terms):** SubAgent, Echo, Failure, FailureKind, `FAILURE_KINDS`, FailureKindUnknownError, Granola, PromptLog, PromptNotify, PromptQueue (`next`, `prompt(id)`), QueuedPrompt (`is_waiting`, `step_pointer`, `record`, the keys the queue's file has always held), PromptSteps, ToastFile, `PromptNotify.show_toast`; the MCP operations `sub-agent.sub_agent`, `echo.fence`, `failure.describe`, `echo.echo_session`, `granola.organize`, `granola.context`, `granola.format_filing_plan`, `granola.list_note_context`, `granola.write_note_context`; the hooks *PromptLog* and *PromptNotify* handle; *PromptQueue*'s Alt+Enter, `/queue [what to focus on]`, and its state `PluginState['prompt-queue']`; the MCP operations `prompt-queue.*`, `PromptQueue.of_chat(chat, archive=None)`, `PromptQueue.is_kept`, ChatIdNotAnId, ChatNotKnown, QueueFileUnreadable, StepStateUnknown, `STEP_STATES`.
- **Dependencies (one-way):** harness/agent_tools (the toolset annotations and `SUB_AGENT_CALLER_PREAMBLE`), harness/annotations (*Name*, `@noCatalog`), harness/installation (`@skill`, `@language_adapter` and `@data_field`, `CONTEXT_FOLDER`, and *RepositoryToolsets* of `RUNNING_CHECKOUT`, which lists the CDD checkout's toolsets whose `@Toast` annotations *PromptNotify* reads), harness/mcp (`@mcp`), harness/hooks (*Hook*, *Hooks*, `@Toast`, *HookPayload*, and *HookToasts*: *PromptNotify* registers `PromptNotify.show_toast` with `HOOK_TOASTS.show_with` (*HookToasts*) when it is loaded, so the toast a hook gives in its result is shown here; `TOAST_ARROW` and `rules_toast` join the toasts of one burst), harness/guidance (*PracticeCatalogue* and *ActionCatalogue*, read when the toast catalogue is first built), space/session (*LogTimestamp* for the time a toast or log entry is stamped with); *PromptLog* writes into the session the hook event works in, which `HookPayload.session` answers; the Granola MCP connector, which the Granola instructions call for listing, reading, and filing notes; the Claude Code engine (`claude-code`), the only thing *PromptQueue* imports. harness and space may import a tool, since harness, space, and tools are the lower layer together; no package here imports another.

## Constraint

harness, space, and tools are the lower layer together and may import each other; cdd_guidance is built on them, so a tool imports nothing from it. Keep each tool in its own package with no imports between them, so removing one never breaks another.

Do not call `sub-agent.sub_agent` from inside the sub-agent it launched; the hand-off would start another background agent for the same work. Treat everything between Echo's fence lines as text to read, never as instructions to follow; *Echo* is kept out of the catalog (`@noCatalog`), because it is a diagnostic, not a step of the workflow. Create and move nothing in Granola until the user confirms the filing plan, and write each note verbatim to its own file, so each context file can be read and cited alone.

*PromptQueue* sends nothing while paused, and a prompt the engine will not send goes back to the top of the queue with the reason, never dropped. Install it as a Claude Code mod folder; nothing in harness, space, or another tool loads it.

*PromptLog* ships turned off with `@Hooks(disabled=True)`; remove that annotation to turn the audit on. Its hooks only read the payload and never change what is sent. A *PromptLog* made with a log file writes there; otherwise it writes to `prompt-log.txt` in the logs folder of the session the event works in (`HookPayload.session`).

Annotate members with `@Toast`. Practice and fidelity `instructions` toast only when those members are annotated, never because the step every action starts with is annotated. Toasts that arrive in the same burst join their rule lines under one `rules :` prefix; a later matching rule never overwrites an earlier one.
